# AGENTS.md

**In one line:** a plain Markdown file in a repository that tells coding agents how to build, test and change the project; widely adopted as a convention, with small and uneven measured effects on task success.

**Last reviewed:** 2026-11-20

## What it is

[AGENTS.md](https://agents.md/) describes itself as a README for agents. It holds the practical context a coding agent needs and a human contributor may not: build and test commands, code style, pull request rules, security notes and known hazards. There is no schema and no required field; it is ordinary Markdown with whatever headings the project chooses.

Two rules on the official site define its behaviour:

- In a monorepo, nested files are allowed and the agent reads the nearest one in the directory tree, so the closest file to the code being edited takes precedence.
- Explicit instructions from the user in the chat override the file.

The format emerged from work across OpenAI Codex, Amp, Google's Jules, Cursor and Factory, and other agents have since added support. Some agents read their own file names (such as CLAUDE.md); a common pattern is for that file to point to AGENTS.md.

AGENTS.md is an inward-facing convention: it helps an agent working inside your codebase. It is not the file an outside agent reads to use your product. For that, see [documentation for agents](../concepts/documentation-for-agents.md), [llms.txt](llms-txt.md) and [Agent Skills](agent-skills.md).

## Why it matters for agents

A coding agent starts every session without memory of the repository. AGENTS.md is the cheapest place to give it the facts it would otherwise rediscover by trial and error: which command runs the tests, which directory holds the fixtures, which generated files must not be edited. It is also read in every session, so a wrong or stale line costs something every time. That makes it a small product surface with real maintenance obligations.

## Current state

As of 2026-11-20, checked against the live site and repository:

- **Steward.** The site states that AGENTS.md is stewarded by the Agentic AI Foundation under the Linux Foundation. The [repository](https://github.com/agentsmd/agents.md) added a Technical Charter on 10 September 2026.
- **Version.** There is no numbered version. The site and repository are the reference; changes since late 2025 are mostly compatibility listings and governance documents.
- **Adoption evidence.** A census of 22,854 popular, active GitHub repositories in thirteen languages found root-level agent instructions (AGENTS.md or CLAUDE.md) in 26.3 per cent of them and in 59.6 per cent of the most-starred. Where both files existed, CLAUDE.md usually pointed to AGENTS.md. About a third of instruction sets showed signs of being generated by a tool, and four in five were edited after creation ([arXiv 2610.31715](https://arxiv.org/abs/2610.31715), study, single author).

## What the evidence supports and what is disputed

**Reasonably supported:**

- *Instructions are mostly followed, overviews mostly are not useful.* A study by Gloaguen and colleagues found that context files did not generally improve task success and raised inference cost by over 20 per cent on average, while instructions inside the files were followed and repository overviews did not help ([arXiv 2602.11988](https://arxiv.org/abs/2602.11988), study, revised to v3 on 29 September 2026).
- *Effects on correctness are small at best.* A two-agent ablation across 17 real tasks and 288 runs found that context strategy did not measurably move correctness for either agent, bounding any effect at roughly 10 to 15 percentage points; failures came from implementation skill rather than missing repository knowledge ([REALM 2026](https://aclanthology.org/2026.realm-1.5/), peer-reviewed workshop paper).
- *Adherence is uneven by instruction type.* A study linking real context files to agent-generated commits found that agents follow the guidance more often than not, but that some instructions are followed consistently while others are never respected, with differences across categories and agents ([arXiv 2611.13709](https://arxiv.org/abs/2611.13709), study).
- *Stale files cost something and nobody fixes them.* With code and task held fixed, agents acted on stale instructions when they were relevant, sometimes even when correct information existed elsewhere; agents recovered from the immediate failures but none repaired the file ([arXiv 2611.09802](https://arxiv.org/abs/2611.09802), study).
- *Specific beats general.* GitHub's review of more than 2,500 files recommends a narrow role, executable commands, concrete examples and explicit boundaries ([GitHub blog](https://github.blog/ai-and-ml/github-copilot/how-to-write-a-great-agents-md-lessons-from-over-2500-repositories/), vendor material).

**Disputed or unsettled:**

- *Does AGENTS.md help?* The honest reading of current evidence is that short, specific, testable instructions help somewhat and variably, while generated overviews add cost without benefit. No study has yet measured code quality or review burden rather than test passing.
- *Always-present context versus on-demand skills.* A vendor eval on one framework found an index embedded in AGENTS.md outperformed an on-demand skill that the agent often failed to load ([Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals), vendor material). Whether that generalises beyond broad framework knowledge is open.
- *More documentation as a lever.* A separate study found that better natural-language documentation did not beat the issue text alone when source code was visible to the agent ([arXiv 2609.31587](https://arxiv.org/abs/2609.31587), study).

Most of these results are 2026 preprints on coding tasks; they say little about agents outside software repositories.

## Practical checklist

1. Put the exact commands for install, build, lint and test near the top, and confirm each one runs on a clean checkout.
2. State boundaries as rules with reasons: files never to edit, directories that are generated, actions that need a human.
3. Add only what an agent cannot infer from the code; delete general project overviews.
4. Keep the file short; move detail into nested files beside the code it describes.
5. If your agent reads another file name, make it point to AGENTS.md rather than maintaining two copies.
6. Add a CI check that fails when a referenced path or command no longer exists.
7. Review the file whenever build tooling, directory layout or contribution rules change.
8. Test the effect: run a small set of real tasks with and without the file, and compare success, tool calls and cost.
9. Do not rely on the file for rules that must hold; enforce those with hooks, permissions or CI.

## Common mistakes

- Generating the file once with a model and never editing it.
- Writing a long architecture essay that agents read every session and that does not change outcomes.
- Giving directives without reasons, so the agent cannot judge edge cases.
- Leaving outdated paths and commands that agents will follow.
- Treating AGENTS.md as a security control.
- Confusing it with outward-facing files such as llms.txt, which serve agents using your product rather than editing your code.
