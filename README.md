# Awesome Agent Experience (AX)

A curated public library for **agent experience**: the design of product, documentation, API, tool, protocol, evaluation, and recovery surfaces so AI agents can discover, understand, safely use, and repair workflows on behalf of people.

This list is intentionally narrow. It is about **software agent experience**: web agents, tool-using LLMs, MCP/API surfaces, evaluation harnesses, retrieval, human control, and operational recovery. It is not about call-center agent experience, real-estate agents, talent agents, or generic customer-experience copy.

The field framing includes the independent opinion essay [Introducing AX: Why Agent Experience Matters](https://biilmann.blog/articles/introducing-ax/). This repository is maintained by the same author as the [Agent Experience Readiness Rubric](https://agentexperience.tech/insights/agent-readiness-rubric/); that link is provided as same-maintainer context, not as neutral endorsement.

## Scope criteria

A source belongs here when it helps answer at least one of these questions:

- Can an agent discover the right surface, instruction, tool, or document?
- Can an agent select and call tools with clear schemas, examples, and error boundaries?
- Can humans inspect, approve, interrupt, or recover the agent's work?
- Can teams evaluate agent workflows in a reproducible way?
- Can the same surface stay useful as models, tools, and protocols change?

A source does **not** belong here if it is only a launch announcement, generic AI-agent marketing, SEO filler, private experiment, paid placement, or unlicensed copy of someone else's work.

## How to read this list

Sections follow a reader's path: what AX is, how agents find and read a surface, how they call tools, which protocols carry identity, payments and approval, how to secure and evaluate the result, and where neighbouring catalogues take over. Each entry shows its source type and publication year (omitted when the source states none), a reason it matters, and a limitation. The limitation is part of the entry: read it before citing the source as evidence.

Vendor guides and scanners are included when they carry concrete, checkable guidance, and are labelled as vendor material in their limitations. Readiness scanners are listed as instruments, not as proof: none of those listed here has published evidence that a higher score predicts agent task success. GEO and AI search research is kept in its own adjacent section because it studies how answer engines cite content, which overlaps with, but is not the same as, whether an agent can complete a task.

## Start here

- **If you are defining the field:** read Introducing AX and One Year of AX, then Principles of AX and the six DX-to-AX areas from Resend, and compare them with the scope criteria above.
- **If you publish a website or documentation:** read llms.txt, Markdown for Agents, Content Signals, WebMCP and ARD, then Designing Agent-Ready Websites for a controlled before-and-after study, and the Documentation for agents section (AGENTS.md, Agent Skills, Agent Plugins).
- **If you build tools, APIs or MCP servers:** read Anthropic's tool-writing guide, the MCP tools and client best-practice pages, OpenAPI, JSON Schema and Arazzo, then the tool-description and tool-selection research (smell-aware descriptions, BiasBusters, Schema First, Skill Shadowing).
- **If agents act for your users:** read the identity section (RFC 9421, Web Bot Auth, the IETF agent authentication draft, Auth.md), the commerce protocols if money moves, and Consent Integrity and Loopjacking before designing approval screens.
- **If you own production risk:** start with MCP security best practices, Exposed by Design and A First Look at MCP security, then The Framing Gap for why surface-level prompt-injection defences are not enough.
- **If you run evaluations or readiness checks:** read Benchmarking the Benchmarks, the Agentic Benchmark Checklist and Protocol Validity before trusting any score, then choose benchmarks and readiness instruments with their limitations in mind.
- **If you need breadth rather than curation:** use the Related lists section for MCP servers, Agent Skills, browser agents and computer-use tooling.

## Agent experience framing

- [Introducing AX: Why Agent Experience Matters](<https://biilmann.blog/articles/introducing-ax/>) (essay, 2025): A public opinion frame for AX as a discipline, useful because it states that agent-facing surfaces deserve product-design attention rather than being treated as incidental automation glue. _Limit: This is a framing essay, not a benchmark or standard; cite it as an opinionated field definition, not as proof of outcomes or ownership._
- [One Year of AX](<https://biilmann.blog/articles/one-year-of-ax/>) (essay, 2026): A one-year follow-up to the founding AX essay that regroups the idea into four pillars (access, context, tools and orchestration), giving a compact vocabulary for auditing a product surface. _Limit: Written by the same author as the original essay, so it is an update to one framing rather than independent validation that the four pillars are complete or correct._
- [AX in Practice: Real-World Examples from Netlify and the Industry](<https://biilmann.blog/articles/ax-in-practice/>) (essay, 2025): Turns the AX framing into named production patterns, including agent-first onboarding that lets an agent create a resource before a human claims it, and bidirectional links between agents and human work queues. _Limit: Adopter examples are reported by a platform founder about his own and partner products; the article does not measure whether the patterns change outcomes._
- [What is AX (Agent Experience) and how to improve it](<https://resend.com/blog/agent-experience>) (essay, 2025): Maps familiar developer-experience concerns onto agents across six practical areas (onboarding, documentation, SDKs, audit logs, API keys and role-based access), useful as a checklist for platform teams. _Limit: A vendor blog post drawn from one email platform's perspective; the six areas are the author's own grouping rather than the result of a study._
- [Principles of AX](<https://agentexperience.ax/concepts/principles-of-ax/>) (essay): States a short set of community AX principles, including treating agents as delegates of people and recording agent actions separately from human ones, which helps teams agree on design intent before choosing tools. _Limit: The site is hosted and largely written by Netlify staff despite its community framing, and it says itself that the principles may change as practice matures._
- [From Human Interfaces to Agent Interfaces: Rethinking Software Design in the Age of AI-Native Systems](<https://arxiv.org/abs/2603.20300>) (paper, 2026): A position paper that names agent interfaces and invocable capabilities as a design discipline distinct from human-facing UX and conventional API design, giving the field an academic framing to cite. _Limit: Conceptual and argumentative only; none of the proposed principles are measured against real systems in the paper._

## Discovery and agent-readable web

- [llms.txt: The /llms.txt file, v2](<https://llmstxt.org/>) (specification, 2024): Documents a proposed Markdown-based website discovery convention for helping language models and agents find the most relevant human-authored pages. _Limit: It is a proposal rather than an enforced web standard, so teams should treat it as one discoverability surface among several._
- [Agentic Resource Discovery (ARD) specification, v0.91](<https://agenticresourcediscovery.org/spec/>) (specification, 2026): The dated, multi-vendor v0.91 proposal (authored across Google, Microsoft, and Hugging Face) distinguishes a plain catalogue entry from a stricter ARD entry built for search-based discovery beyond an LLM's context window. _Limit: Status is explicitly Proposal, not final; it delegates authentication and distribution to the underlying agent or tool protocol rather than defining them itself._
- [WebMCP (Draft Community Group Report)](<https://webmachinelearning.github.io/webmcp/>) (specification, 2026): Defines the document.modelContext API for exposing client-side tools to agents and gives a detailed public security taxonomy for agent-callable web pages, covering tool poisoning, output injection, and over-parameterised data leakage. _Limit: Published by a W3C Community Group; the spec itself states it is not a W3C Standard nor on the Standards Track, so treat it as an active proposal, not settled browser behaviour._
- [Markdown for Agents](<https://developers.cloudflare.com/fundamentals/reference/markdown-for-agents/>) (specification, 2026): Documents an HTTP content-negotiation pattern, an Accept: text/markdown request, for serving agents an edge-converted Markdown page, with a precise, checkable policy on which headers are preserved, recalculated, or dropped. _Limit: The feature is limited to paid Cloudflare plans and to HTML-to-Markdown conversion of responses under 2 MB; it does not establish whether AI crawlers actually send the Accept header in practice._
- [Designing Agent-Ready Websites for AI Web Agents](<https://arxiv.org/abs/2607.12056>) (paper, 2026): Runs a controlled before/after e-commerce experiment across three browser-agent models and 300 task runs, finding an otherwise-identical agent-ready site raised strict task success from about 49 percent to about 89 percent. _Limit: The experiment uses one e-commerce site design and three specific browser-agent models; results may not transfer directly to other site types or to agent models released after the study._
- [Accessible Rich Internet Applications (WAI-ARIA) 1.2](<https://www.w3.org/TR/wai-aria-1.2/>) (specification, 2023): Defines roles, states, and properties for accessible web interfaces; AX uses this as relevant machine-readable UI semantics, not as a shortcut to agent success. _Limit: Correct ARIA use is necessary for accessibility in many interfaces, but it does not guarantee that an agent can complete a workflow._
- [Web Content Accessibility Guidelines (WCAG) 2.2](<https://www.w3.org/TR/WCAG22/>) (specification, 2023): Sets human accessibility requirements for perceivable, operable, understandable, and robust web content; AX relevance is an inference because agent tooling often benefits from the same explicit structure. _Limit: WCAG conformance is not equivalent to agent readiness and should not be cited as evidence that agents will operate a product reliably._
- [llms-txt (reference repository)](<https://github.com/AnswerDotAI/llms-txt>) (repository, 2024): The proposal authors' own repository, with the source of the specification site and Python tooling to parse and expand llms.txt files, which is the practical companion to the llms.txt entry above. _Limit: Reflects the proposal authors' implementation; it does not test whether any given agent or answer engine actually requests or uses the file._
- [Content Signals Policy](<https://contentsignals.org/>) (specification, 2025): Extends robots.txt with separate machine-readable preferences for search, AI input and AI training, so a site can distinguish being indexed from being fetched by a live agent from being used as training data. _Limit: It expresses a preference rather than enforcing one, and it depends on crawler operators choosing to honour the signal._
- [NLWeb](<https://github.com/nlweb-ai/NLWeb>) (repository, 2025): Reference implementation for giving a website a natural-language query endpoint built on its existing Schema.org data, with every instance also exposed as an MCP server, a concrete pattern for making content queryable by agents. _Limit: Useful results depend on structured data that is already present and accurate, and this pass found no independent evidence on deployment or outcomes._
- [Build agent-friendly websites](<https://web.dev/articles/ai-agent-site-ux>) (documentation, 2026): Browser-vendor guidance that treats agents as a new kind of site visitor and translates that into concrete markup and interaction advice, including semantic structure, predictable forms and stable state changes. _Limit: Framed around Chrome's own agentic browsing features, so some recommendations reflect one browser vendor's direction rather than a cross-browser standard._
- [Make your site readable by AI agents](<https://vercel.com/kb/guide/make-your-site-readable-by-ai-agents>) (documentation, 2026): Combines an observational trace study of 1,033 agent runs across 25 sites with controlled fetch probes, then turns the results into specific advice on server rendering, Markdown responses and llms.txt. _Limit: Vendor research run with a partner lab on a small set of sites; the study design and recommendations are shaped by one hosting platform and have not been independently replicated._
- [Building the Web for Agents: A Declarative Framework for Agent-Web Interaction](<https://arxiv.org/abs/2511.11287>) (paper, 2025): Proposes HTML elements that let a page declare agent-callable actions and relevant state directly in markup, so agents do not have to infer affordances from visual layout. _Limit: A short feasibility study with a small developer group, not evidence of production adoption, robustness or behaviour under adversarial use._
- [Web Agents Should Use Typed Actions Instead of Click-Based Browsing](<https://arxiv.org/abs/2602.17245>) (paper, 2026): Argues for typed web actions with documented preconditions, postconditions and policy tags as a more reliable and auditable interface for agents than click-based page automation. _Limit: A position paper without an implementation or benchmark; its value depends on site owners and standards bodies building the layer it describes._
- [Affora: A Design System for Agent-Friendly Interfaces](<https://arxiv.org/abs/2609.19125>) (paper, 2026): An evaluated design system bridging human UX and agent use, whose controlled studies indicate that agent performance follows preserved interaction meaning rather than visual style. _Limit: Its benefit appears mainly where an interface had a matching deficit, and the authors describe the workflow case-study evidence as preliminary._
- [terms.txt: A Consent and Compensation Protocol for Agentic Web Access](<https://arxiv.org/abs/2609.11152>) (paper, 2026): Proposes a successor to robots.txt that combines per-path access terms with signed agent identity, delegation tokens and HTTP 402 payment negotiation, framing agent access as a consent and compensation question. _Limit: A proposal with a reference implementation, not an adopted standard; it only works if both site operators and agent vendors implement it._

## Documentation for agents

- [AGENTS.md](<https://agents.md/>) (specification, 2026): A deliberately unstructured Markdown convention for repository-level agent instructions, now governed by the Agentic AI Foundation under the Linux Foundation rather than a single vendor, with adoption checkable via a linked GitHub code search. _Limit: Has no required fields or schema, so file quality varies widely between projects; the specification itself does not address how a poorly written file affects agent task success._
- [Agent Skills specification](<https://agentskills.io/specification>) (specification): Defines the SKILL.md package format (a directory with YAML frontmatter, instructions and optional scripts and references) that many coding agents load on demand, now a common way for products to ship usage knowledge to agents. _Limit: The format does not verify the quality or safety of a skill; installing a third-party skill can mean running its instructions and code._
- [Agent Plugins Specification 1.0.0](<https://agent-plugins.org/specification>) (specification, 2026): A published, versioned specification with conformance requirements for packaging skills, MCP servers and client extensions into one portable plugin, useful for teams that ship agent-facing capabilities to several clients. _Limit: Very new at retrieval time; there is no independent evidence yet on how consistently clients implement the conformance checklist._
- [Agent Skills Discovery RFC](<https://github.com/cloudflare/agent-skills-discovery-rfc>) (specification, 2026): Proposes a well-known URI index so an agent can discover the skills a site publishes, extending the RFC 8615 discovery pattern to agent skills. _Limit: An RFC-stage proposal from one company; the index shape may change and it has no standards-body status._
- [How to write a great agents.md: Lessons from over 2,500 repositories](<https://github.blog/ai-and-ml/github-copilot/how-to-write-a-great-agents-md-lessons-from-over-2500-repositories/>) (essay, 2025): Draws authoring patterns from a large sample of real agent instruction files, such as naming exact commands, stating boundaries and giving concrete examples, which is practical advice the AGENTS.md convention itself leaves open. _Limit: Written about GitHub Copilot custom agent files, which overlap with but are not identical to the cross-vendor AGENTS.md convention, and the analysis method is not published in detail._
- [AGENTS.md outperforms skills in our agent evals](<https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals>) (essay, 2026): Reports an internal evaluation in which a compressed documentation index placed in AGENTS.md outperformed on-demand skills for framework-specific coding tasks, a useful counterweight to skills-first advice. _Limit: A single vendor, a single framework and the vendor's own evaluation set; the result is not shown to generalise to other stacks or agents._
- [Effective context engineering for AI agents](<https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents>) (essay, 2025): Explains how to treat an agent's context as a finite budget, covering just-in-time retrieval, compaction and structured notes, which informs how documentation and tool output should be shaped for agents. _Limit: Written from one model provider's internal practice; specific patterns may not transfer unchanged to other models or agent harnesses._

## Tool use, tool descriptions and MCP

### Tool design guides

- [Writing effective tools for agents — with agents](<https://www.anthropic.com/engineering/writing-tools-for-agents>) (essay, 2025): Lays out a concrete build-evaluate-refine loop for tool design, realistic multi-step evaluation tasks followed by using an agent to analyse transcripts, with five practical principles and a quantified example cutting one tool's response from 206 to 72 tokens. _Limit: All worked examples are Anthropic's own internal Slack and Asana tools; it does not address cross-vendor tool catalogues, discovery, or MCP registries._
- [Designing Agent-Friendly APIs](<https://www.pinecone.io/blog/designing-agent-friendly-apis/>) (essay, 2026): Sets out six API design principles for agent callers, including treating errors as guidance, budgeting the reader's context and making the interface self-describing, with worked failure examples. _Limit: A vendor engineering post without an accompanying controlled evaluation of the six principles._
- [Steps toward great agent experience every API provider can take today](<https://www.stainless.com/blog/steps-toward-great-agent-experience-every-api-provider-can-take-today/>) (essay, 2026): Argues that specific, actionable error bodies and machine-readable API descriptions are part of an API's contract with agents, with concrete before-and-after examples an API team can apply. _Limit: Written by an SDK-generation vendor and illustrated with its own examples rather than a controlled comparison._
- [Agentic Experience Is the New Developer Experience](<https://nx.dev/blog/making-nx-agent-ready>) (essay, 2026): A command-line perspective on AX that describes structured output, idempotent commands, managed context and informative errors as design goals for tools that agents call from a terminal. _Limit: Describes one vendor's own product decisions; the principles are not tested against other command-line tools._

### Research on tool use and selection

- [ReAct: Synergizing Reasoning and Acting in Language Models](<https://arxiv.org/abs/2210.03629>) (paper, 2022): Connects reasoning traces with actions, making it a useful starting point for interfaces that expose why an agent chose a tool and what happened next. _Limit: Primarily a prompting and evaluation paper; it does not by itself specify production observability, permissioning, or recovery contracts._
- [Toolformer: Language Models Can Teach Themselves to Use Tools](<https://arxiv.org/abs/2302.04761>) (paper, 2023): Frames tool use as something models can learn from demonstrations, which is central to designing tool descriptions and examples that agents can actually use. _Limit: Uses a bounded set of tools and self-supervised data generation; production tool ecosystems add security, latency, and changing-schema problems._
- [ToolLLM: Facilitating Large Language Models to Master 16000+ Real-world APIs](<https://arxiv.org/abs/2307.16789>) (paper, 2023): Shows how large tool corpora and tool-use data shape agent behaviour, supporting AX work on catalogue structure and retrieval-friendly tool metadata. _Limit: Large catalogues can hide quality variance; practical AX also needs clear scope boundaries, deprecation signals, and safe failure modes._
- [The Devil Is in the Interface: Evaluating How Tool Architecture Shapes Coding Agent Behavior](<https://arxiv.org/abs/2608.11386>) (paper, 2026): Runs 11,700 trajectories across three model actors and six tool architectures, from a bare bash tool to structured interfaces, showing that how tools are organised and exposed changes agent behaviour even when raw capability is held constant. _Limit: Findings come from repository-level issue-fixing tasks with specific model actors; whether the same architecture ranking holds for other task domains is not tested here._
- [DOCSCHISEL: Adaptive Tool Documentation Optimization Framework for LLM Agents](<https://arxiv.org/abs/2608.10037>) (paper, 2026): Shows that no single fixed tool-documentation format generalises across tasks, models, and agent designs, then proposes a framework that analyses failed execution traces to iteratively add, remove, or refine documentation fields per tool. _Limit: The proposed framework requires access to an agent's failed execution traces to iterate on, which is not available to every team publishing a tool or API._
- [From Docs to Descriptions: Smell-Aware Evaluation of MCP Server Descriptions](<https://arxiv.org/abs/2602.18914>) (paper, 2026): Defines 18 documentation 'smell' categories across four quality dimensions, applies them to 10,831 real MCP servers, and runs a mutation study showing that injecting or fixing smells measurably changes which tool an agent selects. _Limit: The mutation study shows description smells move selection outcomes in the tested setup; it does not rank which individual smells matter most across every model._
- [More Skills, Worse Agents? Skill Shadowing Degrades Performance When Expanding Skill Libraries](<https://arxiv.org/abs/2605.24050>) (paper, 2026): Decomposes agent performance degradation from growing tool or skill libraries into a wrong-selection component, named skill shadowing, versus a context-overhead component, and estimates both empirically on a library scaling to 202 skills. _Limit: Findings come from one scaling experiment up to 202 skills; whether the same shadowing-versus-overhead split holds at far larger catalogue sizes is not established._
- [ToolChoiceConfusion: Causal Minimal Tool Filtering for Reliable LLM Agents](<https://arxiv.org/abs/2606.06284>) (paper, 2026): Argues topical relevance alone is not enough to decide which tools to expose at each step, and tests a precondition-aware filtering method across 2,448 task-method-model runs, cutting token cost roughly 90 percent without hurting task success. _Limit: Evaluated with 100 tools and four backend models in a controlled multi-step task set; real production catalogues and model mixes may behave differently._
- [SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering](<https://arxiv.org/abs/2405.15793>) (paper, 2024): An early demonstration that the interface an agent uses to read and edit files is itself a lever on task success, shown by varying interface design while holding the model fixed. _Limit: Evaluated on repository-editing benchmarks with a hand-designed interface, so the size of the effect may be specific to that setting._
- [AXIS: Efficient Human-Agent-Computer Interaction with API-First LLM-Based Agents](<https://arxiv.org/abs/2409.17140>) (paper, 2024): Shows an agent that prefers application APIs over clicking through a graphical interface completing tasks faster with less user workload, supporting an API-first recommendation for agent-facing products. _Limit: Evaluated on one desktop application against one baseline; its automatic API discovery is not shown to generalise to other applications._
- [BiasBusters: Uncovering and Mitigating Tool Selection Bias in Large Language Models](<https://arxiv.org/abs/2510.00307>) (paper, 2025): Finds that models choosing between functionally equivalent tools from different providers show systematic preferences that small wording changes can shift, which matters for anyone publishing into a shared tool marketplace. _Limit: The sets of equivalent tools are constructed by the authors; real marketplaces rarely offer such clean alternatives._
- [Tools are under-documented: Simple Document Expansion Boosts Tool Retrieval](<https://arxiv.org/abs/2510.22670>) (paper, 2025): Uses a purpose-built benchmark to show that enriching sparse tool documentation with structured fields improves tool retrieval, evidence that under-documentation is a fixable cause of selection failures. _Limit: The enriched documentation is itself generated by a model, so it can encode errors or drift from what a tool actually does._
- [Learning to Rewrite Tool Descriptions for Reliable LLM-Agent Tool Use](<https://arxiv.org/abs/2602.20426>) (paper, 2026): Trains a rewriter that improves tool descriptions without needing per-tool execution traces and generalises to unseen tools, relevant to teams maintaining large catalogues of tool metadata. _Limit: Gains are reported on research benchmarks; behaviour on proprietary or highly specialised tool catalogues is not tested._
- [Schema First Tool APIs for LLM Agents: A Controlled Study of Tool Misuse, Recovery, and Budgeted Performance](<https://arxiv.org/abs/2603.13404>) (paper, 2026): A controlled pilot that isolates interface design and finds that JSON Schema contracts reduce malformed calls but not conceptually wrong ones, a useful check on the assumption that schemas alone fix tool misuse. _Limit: A small pilot on one local model in which end-task success stayed at zero in every condition, which limits conclusions about downstream outcomes._
- [Toollery: Scaling LLM Agents to Thousands of Skills and Tools](<https://arxiv.org/abs/2609.22218>) (paper, 2026): A training-free method that keeps online tool selection bounded to a small candidate set as catalogues grow, evaluated on a benchmark of tens of thousands of capabilities, relevant to large MCP and skill catalogues. _Limit: Benefits depend on how well generated intent queries cover the real workload and on provider-side prompt caching, both of which vary by deployment._

### Model Context Protocol

- [Model Context Protocol architecture overview](<https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture>) (specification, 2026): Gives the MCP mental model for hosts, clients, servers, tools, resources, prompts, and discovery, which is useful when designing agent-facing surfaces. _Limit: It is high-level documentation; implementation work still needs the specific dated specification pages and SDK behaviour._
- [Model Context Protocol tools specification](<https://modelcontextprotocol.io/specification/2026-07-28/server/tools>) (specification, 2026): Defines how MCP servers expose callable tools, including metadata and schemas that agents and clients use to understand possible actions. _Limit: The spec defines the contract shape; product teams still need to write clear names, descriptions, input schemas, examples, and error responses._
- [Model Context Protocol resources specification](<https://modelcontextprotocol.io/specification/2026-07-28/server/resources>) (specification, 2026): Defines the resource layer for exposing context such as files, data, and app-specific information to agent clients. _Limit: It does not choose the semantic taxonomy or freshness policy for a particular product's resources._
- [The MCP Registry](<https://modelcontextprotocol.io/registry/about>) (specification, 2026): Explains the official MCP Registry's architecture as metadata-only infrastructure meant for downstream aggregators rather than a store end-user MCP clients query directly, and documents its namespace-based publisher trust model. _Limit: The registry was in preview status at retrieval time, so behaviour may change before general availability, and it explicitly delegates security scanning to underlying package registries instead of performing its own._
- [MCP client best practices](<https://modelcontextprotocol.io/docs/2026-07-28/develop/clients/client-best-practices>) (documentation, 2026): Official guidance for MCP hosts on progressive tool discovery and on keeping large intermediate results out of the model context, the client-side counterpart to the server specifications above. _Limit: Pinned to the 2026-07-28 documentation set; it should be rechecked against newer dated releases of the protocol._
- [MCP Apps (ext-apps)](<https://github.com/modelcontextprotocol/ext-apps>) (specification, 2025): The official specification and SDK for an MCP extension that lets a server return interactive user interface inside the host, extending agent-facing surfaces from text results to embedded UI. _Limit: An extension rather than part of the core protocol, so support differs between MCP hosts._

## Protocols and machine-readable surfaces

- [OpenAPI Specification v3.2.0](<https://spec.openapis.org/oas/v3.2.0.html>) (specification, 2025): OpenAPI remains a practical bridge between HTTP APIs, developer docs, and agent-readable operation metadata. _Limit: An OpenAPI file can be syntactically valid while still being poor AX if operation names, examples, errors, and auth flows are unclear._
- [JSON Schema Draft 2020-12](<https://json-schema.org/draft/2020-12>) (specification, 2020): JSON Schema is a foundation for tool input contracts, structured outputs, API validation, and agent-readable constraints. _Limit: Schemas need examples, semantics, and versioning discipline; validation alone does not explain intent._
- [Arazzo Specification v1.1.0](<https://spec.openapis.org/arazzo/v1.1.0.html>) (specification, 2026): Describes sequences of API calls that achieve an outcome, including success criteria and failure actions, which is the workflow and recovery layer that per-endpoint OpenAPI descriptions leave an agent to infer. _Limit: Less widely published than OpenAPI, and it describes workflows without executing them; an agent still needs a separate way to run the calls._
- [Agent2Agent (A2A) Protocol specification](<https://a2a-protocol.org/latest/specification/>) (specification, 2025): Defines agent cards for capability discovery and a task-based exchange for delegating work between independently built agents, the agent-to-agent layer that MCP does not address. _Limit: The latest URL tracks a moving version, and published adoption figures come from the project itself rather than independent measurement._
- [AG-UI: Agent-User Interaction Protocol](<https://docs.ag-ui.com/introduction>) (specification, 2025): An open, event-based protocol for streaming agent state, UI intents and user input between an agent backend and a user-facing application, relevant to keeping people informed while an agent works. _Limit: Governed by its originating project rather than a standards body, and support varies by agent framework._
- [Agent Communication Protocols (agentproto) working group charter](<https://datatracker.ietf.org/doc/charter-ietf-agentproto/00-03/>) (specification, 2026): Tracks the IETF process for a working group on user-to-agent, agent-to-agent and agent-to-tool communication, a standards-track venue with more procedural weight than the many individual agent drafts. _Limit: A proposed charter under review at retrieval time; its scope was contested and is expected to change before any working group is formed._
- [A Survey of AI Agent Protocols](<https://arxiv.org/abs/2504.16736>) (paper, 2025): Compares agent protocols along shared dimensions, giving one place to understand design choices across MCP, A2A and related proposals before reading each specification. _Limit: A 2025 survey that predates several later protocols, including the commerce and payment protocols listed below._

## Agent identity and authorization

- [WorkOS FGA: The authorization layer for AI agents](<https://workos.com/blog/agents-need-authorization-not-just-authentication>) (essay, 2026): Distinguishes on-behalf-of agents, which need scope attenuation under the acting user's own permissions, from autonomous agents, which need fine-grained scope rather than broad client-credential grants, using worked confused-deputy and shared-context scenarios. _Limit: A vendor architecture piece promoting WorkOS Fine-Grained Authorization; its one supporting statistic, an average 47-day stale-credential lifetime, is uncited in the retrieved text._
- [Agent Registration with Auth.md](<https://workos.com/blog/agent-registration-with-auth-md>) (specification, 2026): Proposes an open protocol, a discoverable /auth.md document plus three HTTP endpoints extending RFC 9728 Protected Resource Metadata, for an agent to register a new user on their behalf, a gap OAuth's browser-consent flow does not cover. _Limit: Adoption outside WorkOS's own ecosystem is unstated in the source; as an author-organisation announcement, independent implementation evidence is still needed._

## Agentic commerce and payments

- [Agentic Commerce Protocol (ACP)](<https://github.com/agentic-commerce-protocol/agentic-commerce-protocol>) (specification, 2025): The specification repository for an open checkout protocol in which an agent passes a scoped payment token while the merchant remains merchant of record, with schemas and a changelog. _Limit: Maintained by two companies at retrieval time, and implementing it does not by itself list a merchant on any AI shopping surface._
- [Agent Payments Protocol (AP2)](<https://ap2-protocol.org/>) (specification, 2025): Specifies signed mandates that record what a person authorised an agent to buy, aimed at verifiable authorisation for payments and offered as an extension to A2A and UCP. _Limit: Partner counts are supplied by the sponsors, and independent evidence of production use was not found in this pass._
- [Universal Commerce Protocol (UCP)](<https://ucp.dev/>) (specification): An open specification for agentic commerce covering discovery, checkout and post-purchase steps, with a public repository, SDKs and reference implementations. _Limit: Written from its sponsoring companies' perspective, and cross-protocol interoperability testing is not documented on the site._
- [x402](<https://github.com/x402-foundation/x402>) (specification, 2025): An HTTP-native payment protocol built around the 402 Payment Required status code, so an agent can pay for a request in the same exchange, a different mechanism from checkout-based protocols. _Limit: Early deployments centre on stablecoin settlement, which brings custody and regulatory considerations that card-based checkout does not._

## Human control, approval and recovery

- [What You Approve Is What Executes: Consent Integrity for Black-Box LLM Agents](<https://arxiv.org/abs/2606.02668>) (paper, 2026): Names the missing 'Consent Integrity' property for agent approval dialogs, the action shown must be rendered by a trusted mediator from the real action rather than the agent's own narration, and tests a prototype against 1,330 trusted-tool abuse techniques. _Limit: The prototype analyser, renderer, and execution binder is a research system tested on the GTFOBins and tldr corpora, not a deployed product feature available to adopt directly._
- [Loopjacking: Hijacking Human-in-the-Loop Approval](<https://arxiv.org/abs/2609.21081>) (paper, 2026): Defines Loopjacking as any case where the operation a human approves does not match what a system actually executes, and reproduces both representation-based and post-approval state-substitution variants in named, released agent products. _Limit: The paper names a purposive set of tested products rather than a random or exhaustive sample, so prevalence across the wider agent-product ecosystem is not established._
- [Oversight Has a Capacity: Calibrating Agent Guards to a Subjective, Fatiguing Human](<https://arxiv.org/abs/2606.08919>) (paper, 2026): Measures inter-reviewer agreement on a hand-labelled set of 125 adversarially-weighted agent actions and models the human reviewer as fatiguing under escalation load, finding that more oversight can reduce realised safety past a point. _Limit: The reviewer-fatigue model and the 125-action labelled set are the authors' own construction; whether the same capacity limit holds for other review populations or action types is not tested._
- [Design Principles for Human-Agent Interaction](<https://arxiv.org/abs/2606.20630>) (paper, 2026): Proposes principles across the stages of an agent interaction, including when things go wrong, and applies them to existing agent systems, separating graceful failure from raw task completion as a design goal. _Limit: A position paper with an illustrative rather than statistically validated evaluation._
- [Delegating or Doing? Understanding User Behavior in Hybrid Human-Agent Interfaces](<https://arxiv.org/abs/2608.19551>) (paper, 2026): A 73-participant study of an interface with an MCP-connected assistant finding that assistance reduced interaction effort but not task time, and that the choice to delegate followed personal disposition more than task risk. _Limit: One application and one participant pool, so findings about who delegates may not generalise to other domains._
- [GoEX: Perspectives and Designs Towards a Runtime for Autonomous LLM Applications](<https://arxiv.org/abs/2404.06921>) (paper, 2024): Proposes post-facto validation, undo and damage confinement for actions an agent has already taken, a reference design for recovery when review happens after execution. _Limit: A research runtime, not a hardened dependency; teams still have to define undo semantics for their own actions._
- [Human-in-the-loop (OpenAI Agents SDK)](<https://openai.github.io/openai-agents-python/human_in_the_loop/>) (documentation): Documents how an agent run pauses for approval of sensitive tool calls and resumes from saved state, a concrete framework-level pattern for approval gates. _Limit: Specific to one SDK's run and approval model, so the mechanism does not transfer directly to other frameworks._

## Security for agent-facing surfaces

- [Exposed by Design: A Dynamic Security Assessment of Internet-Facing MCP Servers at Scale](<https://arxiv.org/abs/2608.00150>) (paper, 2026): Combines passive discovery across eleven data sources with active dynamic testing of 414 production MCP servers, providing scale evidence that most audited public servers currently ship without authentication. _Limit: The audited sample, 640 confirmed and 414 tested servers found across four July 2026 measurement runs, is a snapshot of internet-facing MCP servers rather than a comprehensive census of the ecosystem._
- [Breaking the Protocol: Security Analysis of the Model Context Protocol Specification](<https://arxiv.org/abs/2601.17549>) (paper, 2026): Argues MCP's security gaps are architectural, naming missing capability attestation and unauthenticated bidirectional sampling as protocol-level issues, then tests 847 attack scenarios across five server implementations to support the claim. _Limit: The proposed MCPSec mitigation is the authors' own backward-compatible extension, not an adopted part of the MCP specification, so its real-world deployment status is unverified here._
- [Model Context Protocol security best practices](<https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices>) (specification, 2026): Collects security guidance for tool exposure, trust boundaries, and defensive defaults in MCP-connected agent systems. _Limit: Security guidance is implementation-sensitive; teams still need product-specific threat models and operational review._
- [A First Look at the Security Issues in the Model Context Protocol Ecosystem](<https://arxiv.org/abs/2510.16558>) (paper, 2025): Analyses tens of thousands of MCP servers across several registries and describes a two-stage risk: weak registry vetting admits bad servers, then attacker-controlled tool metadata steers the model. _Limit: Registry practices change quickly, and the accompanying scanner's heuristics are not claimed to be complete._
- [VIPER-MCP: Detecting and Exploiting Taint-Style Vulnerabilities in Model Context Protocol Servers](<https://arxiv.org/abs/2605.21392>) (paper, 2026): An automated auditing method run over a large set of MCP server repositories that confirmed previously unknown exploitable vulnerabilities, evidence that server code, not only descriptions, needs review. _Limit: The reported findings are a lower bound shaped by the method's heuristics, not an estimate of total ecosystem exposure._
- [From Component Manipulation to System Compromise: Understanding and Detecting Malicious MCP Servers](<https://arxiv.org/abs/2604.01905>) (paper, 2026): Builds a dataset of malicious MCP server proofs of concept and shows attacks spread across tools, resources and prompts, informing detection before and during execution. _Limit: The dataset is researcher-authored rather than drawn from attacks observed in the wild, and real-world detection was demonstrated on few servers._
- [Mitigating Taint-Style Vulnerabilities in MCP Servers via Security-Aware Tool Descriptions](<https://arxiv.org/abs/2607.07461>) (paper, 2026): Tests adding behavioural risk guidance to tool descriptions as a low-cost mitigation, linking description quality to security outcomes as well as usability. _Limit: A description-level mitigation reduces the chance of triggering a flaw but cannot fix the underlying code._
- [Prompt Injection Attacks on Agentic Coding Assistants: A Systematic Analysis of Vulnerabilities in Skills, Tools, and Protocol Ecosystems](<https://arxiv.org/abs/2601.17548>) (paper, 2026): Systematises published work on prompt injection against coding agents into a taxonomy covering skills, tools and protocol ecosystems, a map of the attack surface that agent-facing content creates. _Limit: A synthesis of existing studies rather than new experiments, so its figures inherit the limits of the underlying work._
- [The Framing Gap: Indirect Prompt-Injection Exfiltration Defeats Surface-Level Defenses in Tool-Using Agents](<https://arxiv.org/abs/2608.27092>) (paper, 2026): Shows that reframing the same exfiltration request can move attack success from none to all attempts for one model, and that destination allow-lists and capability isolation close the gap where model-level fixes do not. _Limit: Run in a synthetic laboratory setting with mock tools rather than a production deployment._
- [Agent Browser Shield](<https://github.com/pixiebrix/agent-browser-shield>) (tool, 2026): An open-source browser extension that filters pages before an agent reads them, removing likely prompt injection, masking personal data and stripping dark patterns, a practical mitigation for browsing agents. _Limit: An alpha prototype whose rules may change; its published measurement is a small token benchmark, and blocking effectiveness is not independently evaluated._

## Evaluation

### Benchmarks

- [WebArena: A Realistic Web Environment for Building Autonomous Agents](<https://arxiv.org/abs/2307.13854>) (paper, 2023): Models web agents against realistic sites, showing why navigation, site state, and task context matter for agent-facing web design. _Limit: Self-hosted benchmark environments are useful for repeatability, but live websites change and need ongoing monitoring._
- [Mind2Web: Towards a Generalist Agent for the Web](<https://arxiv.org/abs/2306.06070>) (paper, 2023): Focuses on mapping natural-language goals to web actions, which is a core AX concern for documentation, labels, and machine-readable task affordances. _Limit: Dataset-driven results should be treated as evidence about task representation, not as a universal recipe for every website._
- [τ-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains](<https://arxiv.org/abs/2406.12045>) (paper, 2024): Centres user-agent-tool interaction, making it especially relevant to AX work on handoffs, clarifications, and domain state. _Limit: Domain simulations still simplify messy real systems; use it to guide evaluation design, not to claim production readiness._
- [AgentBoard: An Analytical Evaluation Board of Multi-turn LLM Agents](<https://arxiv.org/abs/2401.13178>) (paper, 2024): Supports analysis of multi-turn agent behaviour rather than only recording a final success or failure, which helps AX reviews separate failure stages. _Limit: Benchmark assumptions can age quickly as tools, models, and web environments change, so it should not be treated as a universal scorecard._
- [StableToolBench: Towards Stable Large-Scale Benchmarking on Tool Learning of Large Language Models](<https://arxiv.org/abs/2403.07714>) (paper, 2024): Calls attention to benchmark stability for tool learning, a necessary concern when tracking whether AX changes move an evaluation in a repeatable way. _Limit: Stability controls evaluation noise; it does not decide which product affordances matter to a given audience._
- [AgentBench: Evaluating LLMs as Agents](<https://arxiv.org/abs/2308.03688>) (paper, 2023): An early multi-environment agent benchmark spanning operating system, database, web and game settings, still used as a reference design for broad agent evaluation. _Limit: Scores were measured on 2023 models and are dated, even though the environments are still reused._
- [OSWorld: Benchmarking Multimodal Agents for Open-Ended Tasks in Real Computer Environments](<https://arxiv.org/abs/2404.07972>) (paper, 2024): Evaluates agents on open-ended tasks in full desktop environments using screenshots and accessibility trees, extending evaluation beyond the browser to whole applications. _Limit: Desktop environments are costly to run at scale, and results may not transfer across operating systems or application versions._
- [ST-WebAgentBench: A Benchmark for Evaluating Safety and Trustworthiness in Web Agents](<https://arxiv.org/abs/2410.06703>) (paper, 2024): Adds policy compliance and safety to web-agent evaluation in enterprise-style tasks, so a run is judged on whether it stayed within rules as well as whether it finished. _Limit: Built on one browser environment framework and a fixed policy set, which bounds what kinds of unsafe behaviour it can detect._
- [τ²-Bench: Evaluating Conversational Agents in a Dual-Control Environment](<https://arxiv.org/abs/2506.07982>) (paper, 2025): Extends τ-bench so that both the simulated user and the agent can change a shared environment through tools, surfacing coordination failures that single-control benchmarks miss. _Limit: Two-party dual control is still a simplification of real systems where several actors change state at once._
- [WebArena-Verified](<https://github.com/ServiceNow/webarena-verified>) (repository, 2025): A verified release of WebArena in which tasks, reference answers and evaluators were reviewed, with deterministic scoring and offline evaluation from network traces for reproducible web-agent results. _Limit: Verification is limited to the WebArena task set and its self-hosted sites; it does not add new site types._
- [ClawBench](<https://github.com/TIGER-AI-Lab/ClawBench>) (repository, 2026): Evaluates browser agents on everyday tasks across about 160 live websites, intercepting the final submission so agents use real sites without completing real transactions. _Limit: Live sites change, so task validity drifts over time in a way a self-hosted benchmark avoids._
- [LiveMCPBench: Can Agents Navigate an Ocean of MCP Tools?](<https://arxiv.org/abs/2508.01780>) (paper, 2025): Tests agents against many real MCP servers and tools at once and finds retrieval of the right tool is a main failure point, which ties evaluation directly to catalogue and description design. _Limit: A curated task set scored partly by a model judge; a later validity audit in this list examines this benchmark family._
- [MCP-Atlas: A Large-Scale Benchmark for Tool-Use Competency with Real MCP Servers](<https://arxiv.org/abs/2602.00933>) (paper, 2026): Scores tasks on real MCP servers against required factual claims rather than one expected call path, with a failure taxonomy that separates tool-call errors from reasoning and stopping errors. _Limit: A private test split is withheld, so the full results cannot be independently replicated._
- [Berkeley Function Calling Leaderboard (BFCL)](<https://gorilla.cs.berkeley.edu/leaderboard.html>) (benchmark): An academic leaderboard for function-calling accuracy covering single, parallel and multi-turn calls, with later versions adding agentic tasks, widely used as a shared reference for tool-calling ability. _Limit: A periodically updated leaderboard subject to the reproducibility concerns raised in the validity audits below; treat single-run rankings with caution._

### Evaluation tooling

- [METR Task Standard](<https://github.com/METR/task-standard>) (specification, 2024): A common format for packaging agent evaluation tasks (environment, instructions and optional scoring) so tasks written by one party can run in another party's harness, with adaptors for existing suites. _Limit: Standardises packaging, not task quality, and the repository had not been updated for some time at retrieval._
- [Inspect Evals](<https://github.com/UKGovernmentBEIS/inspect_evals>) (repository, 2024): A maintained collection of benchmark implementations for the Inspect framework from the UK AI Security Institute, letting teams run many agent evaluations through one harness instead of reimplementing each. _Limit: Coverage depends on contributions, so newer benchmarks can lag behind their original release._
- [Langfuse](<https://github.com/langfuse/langfuse>) (tool, 2023): Open-source tracing, evaluation and prompt management for LLM and agent applications, supporting the practice of recording every agent run so failures can be reviewed and turned into test cases. _Limit: Self-hosting at scale is an operational commitment, and tracing records what happened without judging whether it was correct._

### Methodology and validity

- [Benchmarking the Benchmarks: A Validity Audit of Tool-Calling Evaluation](<https://arxiv.org/abs/2607.02577>) (paper, 2026): Audits four major tool-calling benchmark families against 496 expert-reviewed tasks and finds that repeating one benchmark's own setup 23 times produced an 18.9-point score spread, large enough to flip leaderboard conclusions. _Limit: The audit covers four named benchmark families (BFCL v4, tau2-Bench, LiveMCPBench, MCP-Atlas); it does not establish that every tool-calling benchmark has comparable reproducibility problems._
- [Establishing Best Practices for Building Rigorous Agentic Benchmarks](<https://arxiv.org/abs/2507.02825>) (paper, 2025): Introduces a checklist for task validity, outcome validity and reporting in agent benchmarks, drawn from problems found in published benchmarks, giving teams a pre-publication review tool. _Limit: A methodological checklist; it does not by itself re-score widely used benchmarks end to end._
- [Evaluation and Benchmarking of LLM Agents: A Survey](<https://arxiv.org/abs/2507.21504>) (paper, 2025): Organises agent evaluation work by what is evaluated and how, which helps a team find the existing benchmark or method that fits a specific AX question. _Limit: A survey that summarises rather than resolves disagreements between the methods it covers._
- [Do Agent Benchmarks Measure Capability? Protocol Validity in the Age of Agentic AI](<https://arxiv.org/abs/2607.22368>) (paper, 2026): Audits agent traces across many benchmarks and finds reward hacking and protocol exploitation inflating scores on some, a failure mode distinct from ordinary evaluator noise. _Limit: Covers a named set of benchmarks; prevalence elsewhere in the field is not estimated._
- [The Double Measurement Confound in Agent Benchmarks: De-Scaffolding, Ground-Truth Scoring, and Reliability Beyond the Mean](<https://arxiv.org/abs/2609.09218>) (paper, 2026): Names a confound in which a fixed scaffold makes execution-critical decisions and a scorer may not reflect correctness, and shows that repairing both changes what a leaderboard appears to show. _Limit: The repair protocol is demonstrated mainly on one benchmark, and applying it elsewhere needs bespoke work._
- [Beyond Pass@k: Measuring Reliability and Security of Agentic Code Generation](<https://arxiv.org/abs/2608.14711>) (paper, 2026): Identifies a common miscalculation of pass@k that can greatly inflate reported agent scores, and proposes reliability and security measures to report alongside it. _Limit: The live pilot is very small, and the authors describe the practical effect of their security-adjusted metric as unresolved._
- [Demystifying evals for AI agents](<https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents>) (essay, 2026): A practitioner walkthrough of building agent evaluations, covering task design, graders and reading transcripts, which complements the academic validity work in this section. _Limit: Based on one model provider's internal practice rather than an independently validated method._

## GEO and AI search (adjacent)

- [GEO: Generative Engine Optimization](<https://arxiv.org/abs/2311.09735>) (paper, 2023): The paper that named generative engine optimisation and introduced a benchmark for measuring how content changes affect visibility in AI-generated answers, the starting point for most later GEO work. _Limit: Visibility gains were measured on the paper's own benchmark and engines at the time, not on current production answer engines._

- [When Optimization Becomes Manipulation: Defending Generative Search against Malicious Generative Engine Optimization](<https://arxiv.org/abs/2609.02964>) (paper, 2026): Describes automated, agent-driven content manipulation aimed at answer engines and proposes a defence that reduces attack success without penalising benign content. _Limit: Evaluated against attack families the authors built, so novel manipulation strategies remain untested._
- [Optimizing your website for generative AI features on Google Search](<https://developers.google.com/search/docs/fundamentals/ai-optimization-guide>) (documentation): Primary guidance from one search engine on its AI features, which states that tactics such as content chunking or llms.txt files are unnecessary for its Search, a useful corrective to GEO marketing claims. _Limit: Covers one search engine only and says nothing about how other answer engines or agents treat the same signals._
