# Awesome Agent Experience (AX)

A curated public library for **agent experience**: the design of product, documentation, API, tool, protocol, evaluation, and recovery surfaces so AI agents can discover, understand, safely use, and repair workflows on behalf of people.

New to the field? The [Agent Experience Wiki](docs/wiki/README.md) explains the ideas behind these sources in plain, sourced pages: a [getting-started guide](docs/wiki/getting-started.md), a ten-module [learning path](docs/wiki/learning-path.md), a [glossary](docs/wiki/glossary.md), a [standards tracker](docs/wiki/standards-tracker.md), and one page per concept and per standard.

This list is intentionally narrow. It is about **software agent experience**: web agents, tool-using LLMs, MCP/API surfaces, evaluation harnesses, retrieval, human control, and operational recovery. It is not about call-center agent experience, real-estate agents, talent agents, or generic customer-experience copy.

The field framing includes the independent opinion essay [Introducing AX: Why Agent Experience Matters](https://biilmann.blog/articles/introducing-ax/). This repository is maintained by the same author as the [Open Agent-Readiness Rubric](https://agentexperience.tech/insights/agent-readiness-rubric/) (v0.3 draft, with a [JSON version](https://agentexperience.tech/agent-readiness-rubric.json)), and the same site publishes an [AX evidence register](https://agentexperience.tech/evidence/) of public findings (with a [JSON download](https://agentexperience.tech/evidence.json)) and the [ax-check rules](https://agentexperience.tech/checks/) behind that rubric; those links are provided as same-maintainer context, not as neutral endorsement.

## Scope criteria

A source belongs here when it helps answer at least one of these questions:

- Can an agent discover the right surface, instruction, tool, or document?
- Can an agent select and call tools with clear schemas, examples, and error boundaries?
- Can humans inspect, approve, interrupt, or recover the agent's work?
- Can teams evaluate agent workflows in a reproducible way?
- Can the same surface stay useful as models, tools, and protocols change?

A source does **not** belong here if it is only a launch announcement, generic AI-agent marketing, SEO filler, private experiment, paid placement, or unlicensed copy of someone else's work.

## How to read this list

Sections follow a reader's path: what AX is, how agents find and read a surface, how they call tools, how context is managed and handed over, which protocols carry identity, payments and approval, how to secure, observe and evaluate the result, and where neighbouring catalogues take over. Each entry shows its source type and publication year (omitted when the source states none), a reason it matters, and a limitation. The limitation is part of the entry: read it before citing the source as evidence.

Vendor guides and scanners are included when they carry concrete, checkable guidance, and are labelled as vendor material in their limitations. Readiness scanners are listed as instruments, not as proof: none of those listed here has published evidence that a higher score predicts agent task success. GEO and AI search research is kept in its own adjacent section because it studies how answer engines cite content, which overlaps with, but is not the same as, whether an agent can complete a task.

## Start here

- **If you are new to AX:** read the wiki's [Getting started](docs/wiki/getting-started.md) page and run its first audit on your own product, then follow the [learning path](docs/wiki/learning-path.md). Concept pages such as [tool design](docs/wiki/concepts/tool-design.md) and [human approval and control](docs/wiki/concepts/human-approval-and-control.md) link back to the entries below.
- **If you are defining the field:** read Introducing AX and One Year of AX, then Principles of AX and the six DX-to-AX areas from Resend, and compare them with the scope criteria above.
- **If you publish a website or documentation:** read llms.txt, Markdown for Agents, Content Signals, WebMCP and ARD, then Designing Agent-Ready Websites for a controlled before-and-after study, and the Documentation for agents section (AGENTS.md, Agent Skills, Agent Plugins).
- **If you build tools, APIs or MCP servers:** read Anthropic's tool-writing guide, the MCP tools and client best-practice pages, OpenAPI, JSON Schema and Arazzo, then the tool-description and tool-selection research (smell-aware descriptions, BiasBusters, Schema First, Skill Shadowing).
- **If agents act for your users:** read the identity section (RFC 9421, Web Bot Auth, the IETF agent authentication draft, Auth.md), the commerce protocols if money moves, and Consent Integrity and Loopjacking before designing approval screens.
- **If your surface feeds long-running agents:** read the Context, memory and handoffs section, then the Observability and traces section for the OpenTelemetry conventions that let you see which tools and context an agent was given.
- **If you own production risk:** start with MCP security best practices, Exposed by Design and A First Look at MCP security, then The Framing Gap for why surface-level prompt-injection defences are not enough.
- **If you run evaluations or readiness checks:** read Benchmarking the Benchmarks, the Agentic Benchmark Checklist and Protocol Validity before trusting any score, then choose benchmarks and readiness instruments with their limitations in mind.
- **If you need breadth rather than curation:** use the Related lists section for MCP servers, Agent Skills, browser agents and computer-use tooling.

## Agent experience framing

- [Introducing AX: Why Agent Experience Matters](<https://biilmann.blog/articles/introducing-ax/>) (essay, 2025): A public opinion frame for AX as a discipline, useful because it states that agent-facing surfaces deserve product-design attention rather than being treated as incidental automation glue. _Limit: This is a framing essay, not a benchmark or standard; cite it as an opinionated field definition, not as proof of outcomes or ownership._
- [One Year of AX](<https://biilmann.blog/articles/one-year-of-ax/>) (essay, 2026): A one-year follow-up to the founding AX essay that regroups the idea into four pillars (access, context, tools and orchestration), giving a compact vocabulary for auditing a product surface. _Limit: Written by the same author as the original essay, so it is an update to one framing rather than independent validation that the four pillars are complete or correct._
- [AX in Practice: Real-World Examples from Netlify and the Industry](<https://biilmann.blog/articles/ax-in-practice/>) (essay, 2025): Turns the AX framing into named production patterns, including agent-first onboarding that lets an agent create a resource before a human claims it, and bidirectional links between agents and human work queues. _Limit: Adopter examples are reported by a platform founder about his own and partner products; the article does not measure whether the patterns change outcomes._
- [How Vercel ships for agents](<https://2027.dev/blog/how-vercel-ships-for-agents>) (essay, 2026): A case study that groups one platform's agent-facing changes into six patterns, including version-matched docs referenced from AGENTS.md, Markdown 404 pages that suggest nearby URLs, non-interactive CLI defaults when an agent is detected, and deploy-before-signup claim flows. _Limit: Written by a company that sells agent testing, in collaboration with the platform it describes; its eval figures are the platform's own, and it does not measure whether the patterns transfer to other products._
- [What is AX (Agent Experience) and how to improve it](<https://resend.com/blog/agent-experience>) (essay, 2025): Maps familiar developer-experience concerns onto agents across six practical areas (onboarding, documentation, SDKs, audit logs, API keys and role-based access), useful as a checklist for platform teams. _Limit: A vendor blog post drawn from one email platform's perspective; the six areas are the author's own grouping rather than the result of a study._
- [Principles of AX](<https://agentexperience.ax/concepts/principles-of-ax/>) (essay): States a short set of community AX principles, including treating agents as delegates of people and recording agent actions separately from human ones, which helps teams agree on design intent before choosing tools. _Limit: The site is hosted and largely written by Netlify staff despite its community framing, and it says itself that the principles may change as practice matures._
- [AI Agents as Users](<https://www.nngroup.com/articles/ai-agents-as-users/>) (essay, 2026): A UX research firm's argument that agents are users in a functional sense, contrasting screenshot, accessibility-tree and API interaction, and setting out when a product may reasonably choose not to serve agents. _Limit: An opinion article with no new study behind it; its near-term advice is largely existing accessibility practice, and its remarks on token costs are general rather than measured._
- [From Human Interfaces to Agent Interfaces: Rethinking Software Design in the Age of AI-Native Systems](<https://arxiv.org/abs/2603.20300>) (paper, 2026): A position paper that names agent interfaces and invocable capabilities as a design discipline distinct from human-facing UX and conventional API design, giving the field an academic framing to cite. _Limit: Conceptual and argumentative only; none of the proposed principles are measured against real systems in the paper._
- [What is Agent Experience (AX)?](<https://developer.microsoft.com/blog/what-is-agent-experience-ax/>) (essay, 2026): A platform vendor's definition of AX that splits measurement into propensity (does the agent choose your technology) and efficacy (does it use it correctly), adds task cost, and names working terms such as bare baseline, lift and drag, and agent profile. _Limit: Vendor framing illustrated almost entirely with coding agents on Microsoft's own developer products and small run counts, typically five per condition, so its figures hold only for the agent profiles it measured._
- [W3C and the State of the Web in the AI Era](<https://www.w3.org/2026/10/w3c-and-state-of-web-in-ai-era.html>) (essay, 2026): A W3C Strategy Team discussion paper that maps current and proposed W3C work touching agents (WebMCP, agent identity and delegation, consent, payments, accessibility semantics) and proposes a nine-point declaration in which an agent acting for a person is a user agent that owes that person loyalty, and consequential actions need real human consent. It also suggests that each working group document what agents need next to what the person needs, with the person's needs winning on conflict, which gives practitioners one view of where web standards work on agents is heading. _Limit: A discussion paper prepared for TPAC 2026 that seeks feedback, not a consensus W3C position or a standard; its traffic figures come from different vendors' own networks and are not comparable with each other._
- [Stop Getting Good at Protocols. Get Good at Agent Experience.](<https://www.oreilly.com/radar/stop-getting-good-at-protocols-get-good-at-agent-experience/>) (essay, 2026): Argues that agent protocols are interchangeable packaging and sets out a five-step AX practice: find out from traffic which agents reach your service, infer which tasks customers delegate, watch agents attempt those tasks, change the product where agents consistently assume different behaviour, and guard the result with automated scoring in CI. It connects the definitional essays in this section to an evaluation routine a team can adopt. _Limit: An opinion piece by a Netlify executive that recommends AXIS, a scoring framework the author's employer maintains, and its remarks on Netlify outcomes are not backed by published figures._

## Discovery and agent-readable web

- [llms.txt: The /llms.txt file, v2](<https://llmstxt.org/>) (specification, 2024): Documents a proposed Markdown-based website discovery convention for helping language models and agents find the most relevant human-authored pages. _Limit: It is a proposal rather than an enforced web standard, so teams should treat it as one discoverability surface among several._
- [Agentic Resource Discovery (ARD) specification, v0.91](<https://agenticresourcediscovery.org/spec/>) (specification, 2026): The dated, multi-vendor v0.91 proposal (authored across Google, Microsoft, and Hugging Face) distinguishes a plain catalogue entry from a stricter ARD entry built for search-based discovery beyond an LLM's context window. _Limit: Status is explicitly Proposal, not final; it delegates authentication and distribution to the underlying agent or tool protocol rather than defining them itself._
- [WebMCP (Draft Community Group Report)](<https://webmachinelearning.github.io/webmcp/>) (specification, 2026): Defines the document.modelContext API for exposing client-side tools to agents and gives a detailed public security taxonomy for agent-callable web pages, covering tool poisoning, output injection, and over-parameterised data leakage. _Limit: Published by a W3C Community Group; the spec itself states it is not a W3C Standard nor on the Standards Track. A draft W3C Agentic Web Working Group charter names it as the initial input to a 'Site Capabilities for Agents' deliverable, but that charter is not yet approved, so treat this as an active proposal, not settled browser behaviour._
- [Markdown for Agents](<https://developers.cloudflare.com/fundamentals/reference/markdown-for-agents/>) (specification, 2026): Documents an HTTP content-negotiation pattern, an Accept: text/markdown request, for serving agents an edge-converted Markdown page, with a precise, checkable policy on which headers are preserved, recalculated, or dropped. _Limit: The feature is limited to paid Cloudflare plans and to HTML-to-Markdown conversion of responses under 2 MB; it does not establish whether AI crawlers actually send the Accept header in practice._
- [Designing Agent-Ready Websites for AI Web Agents](<https://arxiv.org/abs/2607.12056>) (paper, 2026): Runs a controlled before/after e-commerce experiment across three browser-agent models and 300 task runs, finding an otherwise-identical agent-ready site raised strict task success from about 49 percent to about 89 percent. _Limit: The experiment uses one e-commerce site design and three specific browser-agent models; results may not transfer directly to other site types or to agent models released after the study._
- [Accessible Rich Internet Applications (WAI-ARIA) 1.2](<https://www.w3.org/TR/wai-aria-1.2/>) (specification, 2023): Defines roles, states, and properties for accessible web interfaces; AX uses this as relevant machine-readable UI semantics, not as a shortcut to agent success. _Limit: Correct ARIA use is necessary for accessibility in many interfaces, but it does not guarantee that an agent can complete a workflow._
- [Web Content Accessibility Guidelines (WCAG) 2.2](<https://www.w3.org/TR/WCAG22/>) (specification, 2023): Sets human accessibility requirements for perceivable, operable, understandable, and robust web content; AX relevance is an inference because agent tooling often benefits from the same explicit structure. _Limit: WCAG conformance is not equivalent to agent readiness and should not be cited as evidence that agents will operate a product reliably._
- [llms-txt (reference repository)](<https://github.com/AnswerDotAI/llms-txt>) (repository, 2024): The proposal authors' own repository, with the source of the specification site and Python tooling to parse and expand llms.txt files, which is the practical companion to the llms.txt entry above. _Limit: Reflects the proposal authors' implementation; it does not test whether any given agent or answer engine actually requests or uses the file._
- [Content Signals Policy](<https://contentsignals.org/>) (specification, 2025): Extends robots.txt with separate machine-readable preferences for search, AI input and AI training, so a site can distinguish being indexed from being fetched by a live agent from being used as training data. _Limit: It expresses a preference rather than enforcing one, and it depends on crawler operators choosing to honour the signal._
- [NLWeb](<https://github.com/nlweb-ai/NLWeb>) (repository, 2025): Reference implementation for giving a website a natural-language query endpoint built on its existing Schema.org data, with every instance also exposed as an MCP server, a concrete pattern for making content queryable by agents. _Limit: Useful results depend on structured data that is already present and accurate, and this pass found no independent evidence on deployment or outcomes._
- [Build agent-friendly websites](<https://web.dev/articles/ai-agent-site-ux>) (documentation, 2026): Browser-vendor guidance that treats agents as a new kind of site visitor and translates that into concrete markup and interaction advice, including semantic structure, predictable forms and stable state changes. _Limit: Framed around Chrome's own agentic browsing features, so some recommendations reflect one browser vendor's direction rather than a cross-browser standard._
- [Make your site readable by AI agents](<https://vercel.com/kb/guide/make-your-site-readable-by-ai-agents>) (documentation, 2026): Combines an observational trace study of 1,033 agent runs across 25 sites with controlled fetch probes, then turns the results into specific advice on server rendering, Markdown responses and llms.txt. _Limit: Vendor research run with a partner lab on a small set of sites; the study design and recommendations are shaped by one hosting platform and have not been independently replicated._
- [Building the Web for Agents: A Declarative Framework for Agent-Web Interaction](<https://arxiv.org/abs/2511.11287>) (paper, 2025): Proposes HTML elements that let a page declare agent-callable actions and relevant state directly in markup, so agents do not have to infer affordances from visual layout. _Limit: A short feasibility study with a small developer group, not evidence of production adoption, robustness or behaviour under adversarial use._
- [Web Agents Should Use Typed Actions Instead of Click-Based Browsing](<https://arxiv.org/abs/2602.17245>) (paper, 2026): Argues for typed web actions with documented preconditions, postconditions and policy tags as a more reliable and auditable interface for agents than click-based page automation. _Limit: A position paper without an implementation or benchmark; its value depends on site owners and standards bodies building the layer it describes._
- [Affora: A Design System for Agent-Friendly Interfaces](<https://arxiv.org/abs/2609.19125>) (paper, 2026): An evaluated design system bridging human UX and agent use, whose controlled studies indicate that agent performance follows preserved interaction meaning rather than visual style. _Limit: Its benefit appears mainly where an interface had a matching deficit, and the authors describe the workflow case-study evidence as preliminary._
- [terms.txt: A Consent and Compensation Protocol for Agentic Web Access](<https://arxiv.org/abs/2609.11152>) (paper, 2026): Proposes a successor to robots.txt that combines per-path access terms with signed agent identity, delegation tokens and HTTP 402 payment negotiation, framing agent access as a consent and compensation question. _Limit: A proposal with a reference implementation, not an adopted standard; it only works if both site operators and agent vendors implement it._
- [AI Catalog](<https://ai-catalog.io/spec/>) (specification): A draft JSON format that lists MCP servers, A2A agents, skills, plugins and other AI artefacts by media type, with an optional signed trust manifest; the ARD specification above treats it as a plain catalogue, distinct from its own search-oriented entry. _Limit: The page calls itself a draft that may change at any time and carries no date; its well-known path also differs from ARD v0.91, which asks publishers to move from ai-catalog.json to ard.json._
- [AGENTS.TXT: Capability Declarations for Web Agents](<https://datatracker.ietf.org/doc/draft-car-agents-txt-wellknown/>) (specification, 2026): Proposes /.well-known/agents.txt and agents.json as a positive counterpart to robots.txt, in which a site declares the endpoints, protocols, authentication and rate limits agents may use, and explains how it relates to llms.txt and to MCP and A2A cards. _Limit: An individual Internet-Draft in the independent stream with no IETF endorsement or formal standing, expiring in December 2026 unless revised; an earlier draft under the same name lapsed without a revision._
- [Does anyone actually have an llms.txt? I checked millions of websites](<https://caseyrb.com/blog/state-of-llms-txt-adoption/>) (essay, 2026): Measures llms.txt adoption from the public HTTP Archive crawl: about 5.6 per cent of the top 10,000 sites had a valid file in June 2026, with little change by rank, and some platforms, notably Shopify, now publish one by default. _Limit: A single-author blog post that does not publish its queries; 'valid' means the file parses, not that it is useful, and presence says nothing about whether agents read the file._
- [A Vocabulary For Expressing AI Usage Preferences (draft-ietf-aipref-vocab-08)](<https://datatracker.ietf.org/doc/draft-ietf-aipref-vocab/>) (specification, 2026): The IETF AI Preferences working group's shared vocabulary for stating how automated systems may use content, with defined usage categories and rules for combining conflicting statements. It gives publishers one set of terms to reason about instead of a different token per crawler or vendor. _Limit: A working group Internet-Draft whose own note to readers says its contents do not yet reflect working group consensus, and preferences it expresses are not an enforcement mechanism._
- [Associating AI Usage Preferences with Content in HTTP (draft-ietf-aipref-attach-05)](<https://datatracker.ietf.org/doc/draft-ietf-aipref-attach/>) (specification, 2026): The companion to the aipref vocabulary, defining how a site attaches usage preferences to content through robots.txt rules and an HTTP header field. It is the place to check the concrete syntax a publisher would deploy, and it would update RFC 9309 (the Robots Exclusion Protocol) if approved. _Limit: A working group Internet-Draft still in progress; it defines how preferences are signalled, not whether any crawler or agent honours them._
- [Agentic Web Working Group Charter (draft)](<https://w3c.github.io/charter-drafts/2026/agenticweb-wg.html>) (specification): Sets out what a proposed W3C working group would standardise for agents on the web, with a 'Site Capabilities for Agents' deliverable that takes WebMCP as its initial input, plus scope items on agent identity and delegation, permissions on agent actions, outcome measurement and a threat model. Its explicit out-of-scope list (crawler controls, bot detection, model APIs, cryptographic authentication primitives) shows where other bodies are expected to lead. _Limit: A draft charter with placeholder start and end dates; nothing in it is an approved W3C deliverable and its scope may change before any charter vote._
- [WebMCP best practices (Chrome for Developers)](<https://developer.chrome.com/docs/ai/webmcp/best-practices>) (documentation, 2026): Concrete rules for exposing page actions to agents through WebMCP: register the whole tool surface or none of it, share one application service between the visible interface and the tools, only report success once application state matches, and define explicit commit points for cancellation. These are directly checkable in code review of a WebMCP integration. _Limit: Vendor documentation for an API in a Chrome origin trial that tracks a Community Group draft, so details may change; security guidance is kept on a separate page._
- [WebMCP tools (Chrome Labs)](<https://github.com/GoogleChromeLabs/webmcp-tools>) (repository, 2026): Chrome's companion repository for WebMCP, with a browser extension to inspect which tools a page exposes and their input schemas, an evals CLI for checking whether a model calls the right page tools for a given request, a polyfill, agent skills and imperative and declarative demos. It lets a site team test a WebMCP surface rather than only read the draft. _Limit: Experimental vendor tooling that tracks a draft API, and most of its evaluations depend on the LLM backends a team chooses, so results are not comparable across setups._
- [Agent Discovery in A2A](<https://a2a-protocol.org/latest/topics/agent-discovery/>) (documentation): Explains the ways a client locates an A2A Agent Card (a well-known URI on the agent's domain, curated registries, or direct configuration) and gives server and client guidance on protecting sensitive cards and on caching them with Cache-Control and ETag. It is the practical companion to the A2A specification for anyone publishing an agent that others should find. _Limit: Explanatory project documentation that defers to Section 8.6 of the specification for normative requirements, and it treats standardised registry interactions as future work._
- [A Survey of AI Agent Discovery Mechanisms (draft-jimenez-dawn-discovery-landscape-00)](<https://datatracker.ietf.org/doc/draft-jimenez-dawn-discovery-landscape/>) (specification, 2026): Compares agent discovery work at the IETF, AAIF, 3GPP and in open source by discovery model, scope, dynamism, cross-domain reach and semantic capability, and names the gaps and conflicts between them. A useful map before choosing between well-known files, DNS records and registries. _Limit: An individual Internet-Draft (revision 00, expiring January 2027) that surveys rather than specifies, and it states that it does not prescribe which mechanism to use._
- [DNS for AI Discovery (DNS-AID) (draft-mozleywilliams-dawn-dnsaid-00)](<https://datatracker.ietf.org/doc/draft-mozleywilliams-dawn-dnsaid/>) (specification, 2026): Specifies how an organisation can publish its agents in DNS using existing SVCB records, optionally with DNS-SD labels, DNSSEC and DANE, covering lookups where the caller knows the agent or only the organisation. It gives teams a domain-controlled discovery path that no third-party registry mediates and that needs no new record types. _Limit: An individual Internet-Draft (revision 00, November 2026) without working group adoption, and it leaves capability-based search, where the caller knows neither agent nor organisation, out of scope._
- [Allow Google-Agent traffic](<https://developers.google.com/crawling/docs/crawlers-fetchers/allow-google-agent>) (documentation): Shows how to verify a user-triggered agent by user agent, published IP list and an experimental Web Bot Auth signature, then lists the ways sites still block it after allowing it: allow rules ranked below ASN or bot rules, CAPTCHAs on search or form submission, blocks on XHR or API calls deeper in a journey, and per-IP rate limits on shared egress. It is a concrete checklist for site and security teams who intend to let agents complete tasks. _Limit: Vendor documentation written for one company's agent fetcher, with no stated publication date; the signature verification it describes is labelled an experiment._
- [Do Generative AI Assistants Respect robots.txt? Tracing Web Access Beyond Visible Answers](<https://arxiv.org/abs/2607.14447>) (paper, 2026): Tests ten search-capable assistants under four robots.txt conditions, using server logs and secret codes in target pages to separate what was actually fetched from what the answer showed. Site owners get a method they can reuse to check whether assistant fetchers honour access rules and can be attributed by user agent. _Limit: A preprint based on 200 trials at one point in time; assistant configurations and user agents change often, so per-assistant results may date quickly._
- [A Content Analysis of llms.txt Files from the July 2026 Crawl Archive](<https://commoncrawl.org/blog/a-content-analysis-of-llms-txt-files-from-the-july-2026-crawl-archive>) (dataset, 2026): Common Crawl seeded llms.txt and llms-full.txt requests into a large sample of hosts and analysed the roughly 584,000 non-empty files returned: about half follow the full specified structure, a share carry policy text the format never defined (rate limits, copyright, opt-outs), and some contain prompt injection. The released responses give a reusable baseline for what these files actually say, complementing the adoption count already listed. _Limit: Describes file contents from one crawl, not whether any AI system reads the files or changes behaviour because of them, and the authors state their abuse counts are deliberately conservative lower bounds._
- [We Analyzed 137K Sites: 97% of llms.txt Files Never Get Read](<https://ahrefs.com/blog/llmstxt-study>) (essay, 2026): Uses server logs from 137,000 domains to look at who requests llms.txt: most published files received no requests in a month, the requests that did arrive came largely from bots including coding agents, and no AI bot requested the file on sites that lacked one. It helps teams outside developer documentation decide how much effort the file deserves. _Limit: A vendor study limited to domains using the vendor's own analytics product and to one month of traffic; it counts fetches and does not test whether fetched files improved any agent task._
- [The Current State of Content Negotiation for AI Agents (Feb 2026)](<https://www.checklyhq.com/blog/state-of-ai-agent-content-negotation/>) (essay, 2026): Records the exact Accept and User-Agent headers that several coding agents' fetch tools sent to a header-echo endpoint, showing which ask for text/markdown and with what q-values. It answers a question the Markdown for Agents entry leaves open: whether negotiation alone reaches the agents a site's users run. _Limit: A vendor blog post capturing one snapshot of specific agent versions in February 2026; agent headers change between releases, so the results need re-running before they are relied on._
- [RFC 9727: api-catalog: A Well-Known URI and Link Relation to Help Discovery of APIs](<https://www.rfc-editor.org/info/rfc9727>) (specification, 2025): Defines /.well-known/api-catalog and a matching link relation that return a machine-readable index of a publisher's APIs with links to their descriptions and usage policies. It is a standards-track way for an agent to find a site's APIs without scraping a developer portal. _Limit: A general API discovery standard that predates and is not specific to AI agents; it lists APIs but says nothing about how an agent should choose between them._
- [MCP vs RAG vs NLWeb vs HTML: A Comparison of the Effectiveness and Efficiency of Different Agent Interfaces to the Web (Technical Report)](<https://arxiv.org/abs/2511.23281>) (paper, 2025): Runs the same shopping tasks, from product search to checkout, through agents using HTML browsing, RAG over crawled content, MCP web APIs and NLWeb on a testbed of simulated shops, and reports both task quality and token and runtime cost. It gives site owners a controlled comparison of what a structured agent interface offers over plain HTML. _Limit: A technical report on four simulated e-shops and a small set of models, so results may not transfer to real sites, other domains or later models._
- [AX is the New AEO](<https://arxiv.org/abs/2609.34951>) (paper, 2026): A large matched observational study (37,927 agent journeys over 1,056 businesses and four agent harnesses) comparing sites an agent can fetch and read with sites it cannot, measuring how much of each answer came from the business's own pages, how often it was recommended, accuracy against captured facts, and agent cost. It is one of the few public attempts to link site readability to agent outcomes at scale, and it releases analysis code and a data sample. _Limit: A vendor-authored preprint that groups sites using the authors' own readiness ranker and compares existing sites rather than intervening on them; the authors note content depth is not matched and that a before-and-after intervention study is still needed._
- [RFC 9727: api-catalog: A Well-Known URI and Link Relation to Help Discovery of APIs](<https://www.rfc-editor.org/rfc/rfc9727.html>) (specification, 2025): Defines /.well-known/api-catalog and an api-catalog link relation that point to a document listing a publisher's APIs, so an automated client can find them without guessing paths. It is a small, standards-track discovery file to publish alongside OpenAPI descriptions. _Limit: Handles discovery only and does not describe the APIs themselves, and the RFC gives no evidence about how widely agents read it._

## Documentation for agents

- [AGENTS.md](<https://agents.md/>) (specification, 2026): A deliberately unstructured Markdown convention for repository-level agent instructions, governed by the Agentic AI Foundation under the Linux Foundation rather than a single vendor (a Technical Charter was added to the repository in September 2026), with adoption checkable via a linked GitHub code search. _Limit: Has no required fields or schema, so file quality varies widely between projects; the specification itself does not address how a poorly written file affects agent task success._
- [Agent Skills specification](<https://agentskills.io/specification>) (specification): Defines the SKILL.md package format (a directory with YAML frontmatter, instructions and optional scripts and references) that many coding agents load on demand, now a common way for products to ship usage knowledge to agents. Since November 2026 the project has adopted a governance document placing it under LF Projects, and the site hosts companion guidance on optimising descriptions and evaluating skills. _Limit: The format does not verify the quality or safety of a skill; installing a third-party skill can mean running its instructions and code._
- [Agent Plugins Specification 1.0.0](<https://agent-plugins.org/specification>) (specification, 2026): A published, versioned specification with conformance requirements for packaging skills, MCP servers and client extensions into one portable plugin, useful for teams that ship agent-facing capabilities to several clients. _Limit: Very new at retrieval time; there is no independent evidence yet on how consistently clients implement the conformance checklist._
- [Agent Skills Discovery RFC](<https://github.com/cloudflare/agent-skills-discovery-rfc>) (specification, 2026): Proposes a well-known URI index so an agent can discover the skills a site publishes, extending the RFC 8615 discovery pattern to agent skills. _Limit: An RFC-stage proposal from one company; the index shape may change and it has no standards-body status._
- [Open Knowledge Format (OKF) specification, v0.2](<https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md>) (specification, 2026): Specifies a directory of Markdown files with YAML frontmatter as a portable bundle of curated knowledge for agents, with index and log files for progressive disclosure and fields for provenance, trust tier and freshness. _Limit: An early draft on a mutable main branch, published by Google Cloud with reference tooling centred on BigQuery; it targets internal data knowledge more than public product surfaces, and it reports no evidence on agent task outcomes._
- [How to write a great agents.md: Lessons from over 2,500 repositories](<https://github.blog/ai-and-ml/github-copilot/how-to-write-a-great-agents-md-lessons-from-over-2500-repositories/>) (essay, 2025): Draws authoring patterns from a large sample of real agent instruction files, such as naming exact commands, stating boundaries and giving concrete examples, which is practical advice the AGENTS.md convention itself leaves open. _Limit: Written about GitHub Copilot custom agent files, which overlap with but are not identical to the cross-vendor AGENTS.md convention, and the analysis method is not published in detail._
- [AGENTS.md outperforms skills in our agent evals](<https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals>) (essay, 2026): Reports an internal evaluation in which a compressed documentation index placed in AGENTS.md outperformed on-demand skills for framework-specific coding tasks, a useful counterweight to skills-first advice. _Limit: A single vendor, a single framework and the vendor's own evaluation set; the result is not shown to generalise to other stacks or agents._
- [Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?](<https://arxiv.org/abs/2602.11988>) (paper, 2026): A controlled test on SWE-bench tasks and a new benchmark built from repositories with developer-written context files: the files did not generally raise task success and added over 20 per cent to inference cost, although agents did follow their instructions. _Limit: Python repositories only, with success measured as issue resolution; the authors note that context files may matter more for less common languages and for qualities such as security, which they did not measure._
- [Skills over MCP (official MCP extension)](<https://modelcontextprotocol.io/extensions/skills/overview>) (specification): Defines how an MCP server can publish Agent Skills next to its tools (skills/list and skills/get, with files read through resources/read), with per-file SHA-256 manifests, origin tagging and a rule that reading SKILL.md does not by itself activate it. It gives a service a standard route for shipping its own workflow instructions to any host that implements the extension. _Limit: The extensions overview lists it as Beta with no stated destination and SDK and host support still being implemented; its digests prove consistency with the server manifest, not that the skill content is trustworthy._
- [What Open-Source Projects Tell Their Coding Agents: A Census of AGENTS.md and CLAUDE.md](<https://arxiv.org/abs/2610.31715>) (paper, 2026): A population-level baseline of root instruction files across 22,854 active repositories in thirteen languages, with released statement-level annotations, so a team can compare what its own file says (build, test, workflow and AI attribution rules) with what other projects actually write, including how rarely directives give a reason. _Limit: Single-author preprint that is descriptive only: it does not test whether any instruction changes agent behaviour, and the author reports that model annotators agreed with each other far more than with the human reviewer._
- [When Instruction Files Go Stale: Documentation Debt and Hidden Cost in Coding Agents](<https://arxiv.org/abs/2611.09802>) (paper, 2026): Holds code and task fixed while an instruction is left stale, corrected or removed, and shows at tool-call level that agents act on outdated guidance and do not repair the file afterwards. It is a concrete argument for giving AGENTS.md and CLAUDE.md the same review and checks as other maintained documentation. _Limit: Preprint covering three stale instructions, 22 tasks and two models; a cost difference was detectable for only one of the three instructions, so the measured effect is narrow._
- [Do They Do as They Are Told? Investigating Coding Agents' Adherence to Explicit Instructions in Context Files](<https://arxiv.org/abs/2611.13709>) (paper, 2026): Turns individual context-file instructions into executable checks and measures compliance in real agent-authored commits, showing that adherence splits between instructions that are consistently followed and ones that are never respected. Authors can use the categories to decide which rules to rewrite and which to enforce outside the file, for example in hooks or CI. _Limit: Preprint based on observational commit data rather than controlled runs, and only instructions that can be operationalised as scripts are measurable._
- [Do Context Files Help Coding Agents? A Two-Agent Ablation Study on Real Repositories](<https://aclanthology.org/2026.realm-1.5/>) (paper, 2026): A peer-reviewed workshop ablation across Claude Code and Codex that uses equivalence testing to bound any correctness effect of context files, with a failure triage suggesting agents fail on implementation rather than on missing repository knowledge. It also offers an explanation for contradictory earlier results (task difficulty bands differ by agent), which helps when reading other context-file studies. _Limit: Small task set (17 tasks from three repositories, 288 runs) and a correctness-only outcome, so it says little about cost, style or safety, and the null result is bounded at about 10 to 15 points rather than shown to be zero._
- [From Agent Behaviour to Agent-Friendly Documentation: An Empirical Study of How Coding Agents Discover, Read, and Write Technical Documentation](<https://arxiv.org/abs/2608.20195>) (paper, 2026): Uses public coding-agent session traces and agentic pull requests to show which documents agents actually touch (mostly instruction files and working notes, rarely API references) and tests two common assumptions about agent-friendly documentation, actionability and verifiability, against behaviour. The pipeline and event-level data are released for reuse. _Limit: Preprint built on two public datasets of coding sessions, so findings may not carry over to agents reading product or API documentation on the web, and the associations are observational._
- [Compact Documentation for Coding Agents: A Benchmark, an Optimizer, and Why It Does Not Transfer](<https://arxiv.org/abs/2609.31587>) (paper, 2026): Builds a roundtrip benchmark for code descriptions and an optimised description prompt, then reports, against a positive control, that better documentation did not help agents resolve issues when the source code was present. It helps teams aim documentation effort at surfaces where the agent cannot simply read the code. _Limit: Preprint limited to repository issue resolution across ten repositories and two model families; it says nothing about documentation for closed services or web APIs._
- [Signal or Noise? A Benchmark Study of Agent Skills in Web Development](<https://arxiv.org/abs/2608.23067>) (paper, 2026): Tests 31 public web development skills on 1,000 ordered tasks with a length-matched irrelevant control and component ablations, separating real skill effects from prompt-length effects. Its design (matched controls, per-model audits) is a template for checking whether a skill a team publishes helps at all. _Limit: Preprint confined to web development skills on the Web-Bench project set; its finding that injected skills often lowered pass rates and raised token cost may not hold in other domains._
- [From Anatomy to Smells: An Empirical Study of SKILL.md in Agent Skills](<https://arxiv.org/abs/2607.01456>) (paper, 2026): Provides a component taxonomy for SKILL.md files, a catalogue of skill smells drawn from published authoring guidance, and an automated detector, which gives skill authors a concrete review checklist and shows that smells tend to persist once introduced. _Limit: Preprint whose smells are defined as departures from guidance found in a multivocal review, not from measured effects on agent task success._
- [Making OpenAPI Documentation Agent-Ready: Detecting Documentation and REST Smells with a Multi-Agent LLM System](<https://arxiv.org/abs/2605.14312>) (paper, 2026): An industrial report in which 16 production APIs (about 600 endpoints) being exposed to agents through MCP were scanned for documentation and REST smells, with deficiencies found in every operation and practitioners largely agreeing. It is useful evidence that a structurally valid OpenAPI document is not the same as one an agent can plan with, and it describes the adoption changes the organisation made. _Limit: Static analysis of one organisation's APIs without live agent task runs, published as a short conference paper._
- [Optimizing skill descriptions (Agent Skills)](<https://agentskills.io/skill-creation/optimizing-descriptions>) (documentation): Explains that a skill only helps if its description causes it to be activated, and gives a testable method: labelled should-trigger and should-not-trigger queries, repeated runs, and a train and validation split to avoid overfitting the description. The sibling page on evaluating skill output (evals/evals.json, assertions and grading) completes the loop. _Limit: Guidance on the specification site rather than a study; its example trigger-detection script is written for one agent client and must be adapted, and no trigger rates are reported._
- [Skill authoring best practices (Claude Platform Docs)](<https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices>) (documentation): Concrete authoring rules for SKILL.md files: keep the body concise because it competes for context once loaded, match instruction specificity to how fragile the task is, write descriptions that say when the skill applies, and use progressive disclosure into one level of reference files. _Limit: Vendor documentation written for one model family, with worked examples but no published evaluation of how much each practice changes task success._
- [Docs URL Discovery Bench](<https://github.com/mintlify/docs-url-discovery-bench>) (benchmark): An open benchmark that proxies coding-agent fetches and compares four serving arms (HTML, Markdown, Markdown linking to llms.txt, Markdown with llms.txt inlined) on dead URLs, fetches, tokens and accuracy, with snapshots for deterministic replay. It isolates the effect of an index from the effect of Markdown, and teams can rerun it against their own documentation. _Limit: Vendor-built benchmark on 20 sites hosted by the same vendor with two primary agent harnesses (replicated on three further models); it measures retrieval waste rather than end-to-end task success._
- [State of Docs: Agents are your top readers](<https://buildwithfern.com/post/state-of-docs>) (essay, 2026): Nine months of request data from one documentation host with a stated counting method, showing agent requests concentrating on API reference, changelogs and Markdown routes, and llms.txt acting as an entry index before per-page Markdown; the host also reports dropping llms-full.txt. It is a useful counterpoint to trace studies of coding sessions, where API references are rarely read. _Limit: Vendor analysis of its own hosted sites with promotional sections; agent counts rest on a route-based rule rather than client identification, and the SDK success figure it cites is the vendor's own benchmark._
- [Modern Web Guidance](<https://github.com/GoogleChrome/modern-web-guidance>) (repository): Shows platform documentation owners delivering guidance to coding agents as installable, token-pruned skills, with content trimmed according to evals and a public eval dashboard, stewarded jointly by the Chrome, Edge, Firefox and MDN teams. It is a working model for documentation teams who want guidance to reach agents at the point of use. _Limit: Covers web platform development only, and its evals are run and reported by the project itself._

## Tool use, tool descriptions and MCP

### Tool design guides

- [Writing effective tools for agents — with agents](<https://www.anthropic.com/research/writing-tools-for-agents>) (essay, 2025): Lays out a concrete build-evaluate-refine loop for tool design, realistic multi-step evaluation tasks followed by using an agent to analyse transcripts, with five practical principles and a quantified example cutting one tool's response from 206 to 72 tokens. _Limit: All worked examples are Anthropic's own internal Slack and Asana tools; it does not address cross-vendor tool catalogues, discovery, or MCP registries._
- [Designing Agent-Friendly APIs](<https://www.pinecone.io/blog/designing-agent-friendly-apis/>) (essay, 2026): Sets out six API design principles for agent callers, including treating errors as guidance, budgeting the reader's context and making the interface self-describing, with worked failure examples. _Limit: A vendor engineering post without an accompanying controlled evaluation of the six principles._
- [Steps toward great agent experience every API provider can take today](<https://www.stainless.com/blog/steps-toward-great-agent-experience-every-api-provider-can-take-today/>) (essay, 2026): Argues that specific, actionable error bodies and machine-readable API descriptions are part of an API's contract with agents, with concrete before-and-after examples an API team can apply. _Limit: Written by an SDK-generation vendor and illustrated with its own examples rather than a controlled comparison._
- [Agentic Experience Is the New Developer Experience](<https://nx.dev/blog/making-nx-agent-ready>) (essay, 2026): A command-line perspective on AX that describes structured output, idempotent commands, managed context and informative errors as design goals for tools that agents call from a terminal. _Limit: Describes one vendor's own product decisions; the principles are not tested against other command-line tools._
- [AXI: Agent eXperience Interface](<https://github.com/kunchenguid/axi>) (repository, 2026): Ten design principles for command-line tools used by agents, such as minimal default fields, definitive empty states, structured errors without interactive prompts and next-step hints after each output, with reference implementations to inspect. _Limit: Its benchmark tables come from the maintainer's own runs with one model against its own wrappers, and its preferred compact output format (TOON) is a project choice rather than a shared standard._
- [Tool search](<https://developers.openai.com/api/docs/guides/tools-tool-search>) (documentation): OpenAI's version of letting the model search for tools instead of loading every definition: functions, namespaces or MCP servers are marked for deferred loading and found by a hosted or application-run search, with advice to group them in small, well-described namespaces. _Limit: Vendor documentation for recent models on one API, with no published token or accuracy figures; for a single deferred function the name and description stay visible and only the parameter schema is deferred._
- [Tool search tool](<https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool>) (documentation): Anthropic's version of the same pattern, in which deferred tools stay out of the context entirely until a regex or BM25 search returns them; read alongside the OpenAI guide, it shows that vendors differ in what the model sees before it searches. _Limit: Vendor documentation whose figures on token savings and tool-selection accuracy are the vendor's own and not linked to a published evaluation, and whose details apply only to the models it lists as supported._
- [Build your user's agentic workflows with WebMCP tools](<https://developer.chrome.com/docs/ai/webmcp/build-tools>) (documentation, 2026): A step-by-step method for choosing which tools a site should expose to agents: define the user goal and starting state, role-play the conversation to find each needed tool, return errors that tell the agent how to recover, bind approval of consequential actions to a short-lived grant over the exact plan, and test edits, undo, timeouts and idempotency-key replays. _Limit: Browser-vendor guidance for WebMCP, an experimental API in origin trial that the page says may change._
- [Code execution with MCP: Building more efficient agents](<https://www.anthropic.com/research/code-execution-with-mcp>) (essay, 2025): Explains why loading every MCP tool definition up front and passing every intermediate result through the model scales poorly, and describes presenting servers as a code API that the agent explores and calls from a sandbox, so it loads only what it needs and filters data before it reaches context. It frames the code mode pattern that later research tests. _Limit: Vendor engineering post whose token saving comes from one illustrative workflow rather than a benchmark, and the pattern adds the cost and risk of running generated code._
- [Spaces: A CLI Built for Humans and Agents](<https://mistral.ai/news/spaces>) (essay, 2026): A case study of an internal platform CLI reworked once coding agents became users: every interactive prompt gains a flag equivalent feeding one execution path, a non-interactive mode fails loudly instead of waiting on input, plugin registries are introspectable as JSON, each project gets a generated context.json and AGENTS.md, and working-directory and config assumptions become explicit inputs. Its closing checklist is short enough to use as a review list for other command-line tools. _Limit: Vendor engineering post about an internal tool; it describes one anecdotal agent run and makes no measured comparison of agent success before and after the changes._

### Research on tool use and selection

- [ReAct: Synergizing Reasoning and Acting in Language Models](<https://arxiv.org/abs/2210.03629>) (paper, 2022): Connects reasoning traces with actions, making it a useful starting point for interfaces that expose why an agent chose a tool and what happened next. _Limit: Primarily a prompting and evaluation paper; it does not by itself specify production observability, permissioning, or recovery contracts._
- [Toolformer: Language Models Can Teach Themselves to Use Tools](<https://arxiv.org/abs/2302.04761>) (paper, 2023): Frames tool use as something models can learn from demonstrations, which is central to designing tool descriptions and examples that agents can actually use. _Limit: Uses a bounded set of tools and self-supervised data generation; production tool ecosystems add security, latency, and changing-schema problems._
- [ToolLLM: Facilitating Large Language Models to Master 16000+ Real-world APIs](<https://arxiv.org/abs/2307.16789>) (paper, 2023): Shows how large tool corpora and tool-use data shape agent behaviour, supporting AX work on catalogue structure and retrieval-friendly tool metadata. _Limit: Large catalogues can hide quality variance; practical AX also needs clear scope boundaries, deprecation signals, and safe failure modes._
- [The Devil Is in the Interface: Evaluating How Tool Architecture Shapes Coding Agent Behavior](<https://arxiv.org/abs/2608.11386>) (paper, 2026): Runs 11,700 trajectories across three model actors and six tool architectures, from a bare bash tool to structured interfaces, showing that how tools are organised and exposed changes agent behaviour even when raw capability is held constant. _Limit: Findings come from repository-level issue-fixing tasks with specific model actors; whether the same architecture ranking holds for other task domains is not tested here._
- [DOCSCHISEL: Adaptive Tool Documentation Optimization Framework for LLM Agents](<https://arxiv.org/abs/2608.10037>) (paper, 2026): Shows that no single fixed tool-documentation format generalises across tasks, models, and agent designs, then proposes a framework that analyses failed execution traces to iteratively add, remove, or refine documentation fields per tool. _Limit: The proposed framework requires access to an agent's failed execution traces to iterate on, which is not available to every team publishing a tool or API._
- [From Docs to Descriptions: Smell-Aware Evaluation of MCP Server Descriptions](<https://arxiv.org/abs/2602.18914>) (paper, 2026): Defines 18 documentation 'smell' categories across four quality dimensions, applies them to 10,831 real MCP servers, and runs a mutation study showing that injecting or fixing smells measurably changes which tool an agent selects. _Limit: The mutation study shows description smells move selection outcomes in the tested setup; it does not rank which individual smells matter most across every model._
- [More Skills, Worse Agents? Skill Shadowing Degrades Performance When Expanding Skill Libraries](<https://arxiv.org/abs/2605.24050>) (paper, 2026): Decomposes agent performance degradation from growing tool or skill libraries into a wrong-selection component, named skill shadowing, versus a context-overhead component, and estimates both empirically on a library scaling to 202 skills. _Limit: Findings come from one scaling experiment up to 202 skills; whether the same shadowing-versus-overhead split holds at far larger catalogue sizes is not established._
- [ToolChoiceConfusion: Causal Minimal Tool Filtering for Reliable LLM Agents](<https://arxiv.org/abs/2606.06284>) (paper, 2026): Argues topical relevance alone is not enough to decide which tools to expose at each step, and tests a precondition-aware filtering method across 2,448 task-method-model runs, cutting token cost roughly 90 percent without hurting task success. _Limit: Evaluated with 100 tools and four backend models in a controlled multi-step task set; real production catalogues and model mixes may behave differently._
- [SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering](<https://arxiv.org/abs/2405.15793>) (paper, 2024): An early demonstration that the interface an agent uses to read and edit files is itself a lever on task success, shown by varying interface design while holding the model fixed. _Limit: Evaluated on repository-editing benchmarks with a hand-designed interface, so the size of the effect may be specific to that setting._
- [AXIS: Efficient Human-Agent-Computer Interaction with API-First LLM-Based Agents](<https://arxiv.org/abs/2409.17140>) (paper, 2024): Shows an agent that prefers application APIs over clicking through a graphical interface completing tasks faster with less user workload, supporting an API-first recommendation for agent-facing products. _Limit: Evaluated on one desktop application against one baseline; its automatic API discovery is not shown to generalise to other applications._
- [BiasBusters: Uncovering and Mitigating Tool Selection Bias in Large Language Models](<https://arxiv.org/abs/2510.00307>) (paper, 2025): Finds that models choosing between functionally equivalent tools from different providers show systematic preferences that small wording changes can shift, which matters for anyone publishing into a shared tool marketplace. _Limit: The sets of equivalent tools are constructed by the authors; real marketplaces rarely offer such clean alternatives._
- [Tools are under-documented: Simple Document Expansion Boosts Tool Retrieval](<https://arxiv.org/abs/2510.22670>) (paper, 2025): Uses a purpose-built benchmark to show that enriching sparse tool documentation with structured fields improves tool retrieval, evidence that under-documentation is a fixable cause of selection failures. _Limit: The enriched documentation is itself generated by a model, so it can encode errors or drift from what a tool actually does._
- [Learning to Rewrite Tool Descriptions for Reliable LLM-Agent Tool Use](<https://arxiv.org/abs/2602.20426>) (paper, 2026): Trains a rewriter that improves tool descriptions without needing per-tool execution traces and generalises to unseen tools, relevant to teams maintaining large catalogues of tool metadata. _Limit: Gains are reported on research benchmarks; behaviour on proprietary or highly specialised tool catalogues is not tested._
- [Schema First Tool APIs for LLM Agents: A Controlled Study of Tool Misuse, Recovery, and Budgeted Performance](<https://arxiv.org/abs/2603.13404>) (paper, 2026): A controlled pilot that isolates interface design and finds that JSON Schema contracts reduce malformed calls but not conceptually wrong ones, a useful check on the assumption that schemas alone fix tool misuse. _Limit: A small pilot on one local model in which end-task success stayed at zero in every condition, which limits conclusions about downstream outcomes._
- [Toollery: Scaling LLM Agents to Thousands of Skills and Tools](<https://arxiv.org/abs/2609.22218>) (paper, 2026): A training-free method that keeps online tool selection bounded to a small candidate set as catalogues grow, evaluated on a benchmark of tens of thousands of capabilities, relevant to large MCP and skill catalogues. _Limit: Benefits depend on how well generated intent queries cover the real workload and on provider-side prompt caching, both of which vary by deployment._
- [The Bitter Lesson of Tool Calling](<https://arxiv.org/abs/2608.06370>) (paper, 2026): Compares exposing tools as typed Python functions that the model calls from code with native JSON tool calls across 14 models on BFCL v4; calling from code matched or beat JSON for 11 of the 14 models, which bears on how tools are packaged for code-capable agents. _Limit: Results come from one benchmark and the authors' own harness for running generated code, so they show the approach works there rather than that it improves any particular product's tools._
- [The Scaffolding Matters More Than the Interface: A Controlled Comparison of MCP and CLI Tool Use Across Seven Agent Scaffoldings, Five Language Models, and One Software Task](<https://arxiv.org/abs/2608.08654>) (paper, 2026): Runs one software task through MCP and through a plain command line across seven agent scaffoldings and five models, checking the repository rather than the agent's own report; the scaffolding moved cost far more than the interface, and agents often ignored the one assigned. _Limit: One task of six git operations, as the title says; the paired MCP-to-CLI cost ratios were unstable, so they should not be read as general figures for either interface._
- [MCP-GRANITE Benchmark: GRANularity Interface TEsting for MCP-Based LLM Agents](<https://arxiv.org/abs/2609.24161>) (paper, 2026): Treats how finely functionality is split into tools as a controlled variable across 81 multi-step scenarios at four levels, from many primitives to one monolithic tool; at a well-matched granularity a 3.2B model beat a 20.9B model at a poor one. _Limit: Uses nine small, locally run models in edge and IoT scenarios, so the best granularity found here may not hold for large hosted models or for other domains._
- [SilentProbe: Measuring Silent Failure in Production APIs Used as Agent Tools](<https://arxiv.org/abs/2609.00035>) (paper, 2026): Shows why an HTTP 200 is not enough for agents: constraints written only in prose let a misunderstood query return an empty success, while schema-encoded constraints produced honest errors, and models in the agent loop rarely noticed the silent failure. _Limit: Several authors work for the aggregation service used to reach the 27 vendors' endpoints, a competing interest the paper declares, and live calls were limited to read-only endpoints reached through that one layer._
- [Hybrid Semantic Tool Discovery for Enterprise MCP Gateway: Architecture and Implementation](<https://arxiv.org/abs/2608.23992>) (paper, 2026): Describes a gateway pattern for large MCP estates: rather than loading over 2,000 tool schemas from more than 200 servers, the agent gets one meta-tool that searches the catalogue with combined keyword and vector retrieval and another that runs the chosen tool. _Limit: An experience report on one company's gateway and catalogue; retrieval quality rests on 45 usable queries written for that catalogue, and poorly described tools may be missed with no way to detect it._
- [Screenshots or Tools? Eliciting Tool Use and Managing Multimodal Context in Hybrid GUI-MCP Computer-Use Agents](<https://arxiv.org/abs/2608.03327>) (paper, 2026): On OSWorld-MCP, adding the same MCP tools helped a reasoning model and hurt a non-reasoning one, and even the reasoning model called a tool on under a quarter of the tasks where one applied: offering a tool does not mean the agent will use it well. _Limit: Compares two checkpoints of one 8-billion-parameter open model on one benchmark with five runs each, so the direction of the effect for other models and harnesses is not established._
- [MCP Error Messages Written for Developers Hurt the Most Capable Agents Most](<https://arxiv.org/abs/2609.35381>) (paper, 2026): Audits 3,001 error messages from 150 MCP servers and finds that most recovery steps assume a human (run a command, edit configuration, open a page, wait), then shows tool-only agents follow those steps literally. MCP authors get a testable rule: credential and rate-limit errors should name a server tool the agent can actually call next. _Limit: Preprint submitted to a journal, with the behavioural tests run on Berkeley Function Calling Leaderboard tasks using models from one vendor._
- [Which Metadata Matters for LLM Tool Selection in MCP? Evidence from Controlled Factor-Level Interventions](<https://arxiv.org/abs/2610.14334>) (paper, 2026): Changes one metadata factor at a time (server name, tool name, description or parameter schema) with tool positions balanced, after showing that functionally similar MCP tools often share names but differ in schema. Schema designers learn that the shape of the parameter schema can influence which tool is chosen before any call is made. _Limit: Preprint using five models and five tasks in a controlled selection setting, not observed production traffic._
- [Callability Is Not Operability: Controlled Interface Interventions for LLM Agents](<https://arxiv.org/abs/2608.23628>) (paper, 2026): Distinguishes a tool that accepts a valid call from one that tells the agent enough to continue safely (for example after a committed effect whose response was lost), and names interface mechanisms for the gap: selective capability discovery, execution lifecycle and recovery, explicit effect semantics, machine-readable results and postcondition checks. It gives tool designers a vocabulary and a controlled test bed (AFT-Bench) that varies only the interface. _Limit: Single-author preprint whose benchmark is a controlled framework built by the author rather than an independent suite._
- [AT-AT: Automatic Tool Optimization from Agent Traces](<https://arxiv.org/abs/2610.34679>) (paper, 2026): Takes the position of a tool provider who cannot change the agents that call its API or MCP server: a coding agent reads past trajectories and their evaluation results, then edits tool descriptions and, where allowed, implementations while the agents stay fixed. It is a concrete model for improving a shared tool surface from telemetry. _Limit: Preprint whose results on production MCP servers come from a single organisation and are reported only in summary._
- [Beyond Plain MCP: Do Decision Models and Code Mode Make Tool Use Cheaper and Faster?](<https://arxiv.org/abs/2611.19123>) (paper, 2026): A preregistered comparison of plain MCP tool calling, code mode (the agent writes scripts against tool stubs) and router layers that preselect tools, across 12 servers and up to 1,958 distractor tools. Gateway and SDK designers get a specific, testable variable: whether stubs declare the shape of what each tool returns. _Limit: Single-author preprint using three open-weight agents, so the results may not carry over to hosted frontier models._
- [Model Context Protocol (MCP) Tool Descriptions Are Smelly! Towards Improving AI Agent Efficiency with Augmented MCP Tool Descriptions](<https://arxiv.org/abs/2602.14878>) (paper, 2026): Derives six components of a tool description from prior work, turns them into a scoring rubric and a set of description smells, applies them to 856 tools on 103 MCP servers and then measures what augmenting the descriptions does to agent performance and cost. It helps authors weigh which parts of a description earn their tokens. _Limit: Preprint whose rubric scoring is itself model-assisted; it is a different study from the smell-aware evaluation paper already listed._
- [Tool Preferences in Agentic LLMs are Unreliable](<https://aclanthology.org/2025.emnlp-main.1060/>) (paper, 2025): Peer-reviewed evidence that editing a tool description, without changing what the tool does, can sharply shift how often models choose it over equivalent alternatives, tested across 17 models. It shows description wording is both a lever for providers and a reliability and fairness problem for registries and agent builders. _Limit: Measures selection between competing tools in controlled pairings rather than end-to-end task success._
- [Don't Adapt Small Language Models for Tools; Adapt Tool Schemas to the Models](<https://aclanthology.org/2026.acl-long.948/>) (paper, 2026): Identifies schema misalignment, where small models invent plausible tool names that the schema does not contain, and proposes a training-free renaming method (PA-Tool) that picks names the model is already familiar with. It is peer-reviewed support for treating tool and parameter naming as part of the interface design. _Limit: Evaluated on MetaTool and RoTBench with small models; it does not establish the effect on large hosted models._
- [Terminal Agents Suffice for Enterprise Automation](<https://arxiv.org/abs/2604.00073>) (paper, 2026): Compares a coding agent that has only a terminal and filesystem and calls platform APIs directly with MCP tool-augmented agents and GUI web agents on real enterprise systems. API providers get peer-reviewed evidence that a clean programmatic API with good documentation can serve as the agent surface without a bespoke tool layer. _Limit: Results depend on the enterprise platforms and backbone models chosen, and the comparison reflects how the authors built each alternative architecture._

### Model Context Protocol

- [Model Context Protocol architecture overview](<https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture>) (specification, 2026): Gives the MCP mental model for hosts, clients, servers, tools, resources, prompts, and discovery, which is useful when designing agent-facing surfaces. _Limit: It is high-level documentation; implementation work still needs the specific dated specification pages and SDK behaviour._
- [Model Context Protocol tools specification](<https://modelcontextprotocol.io/specification/2026-07-28/server/tools>) (specification, 2026): Defines how MCP servers expose callable tools, including metadata and schemas that agents and clients use to understand possible actions. _Limit: The spec defines the contract shape; product teams still need to write clear names, descriptions, input schemas, examples, and error responses._
- [Model Context Protocol resources specification](<https://modelcontextprotocol.io/specification/2026-07-28/server/resources>) (specification, 2026): Defines the resource layer for exposing context such as files, data, and app-specific information to agent clients. _Limit: It does not choose the semantic taxonomy or freshness policy for a particular product's resources._
- [The MCP Registry](<https://modelcontextprotocol.io/registry/about>) (specification, 2026): Explains the official MCP Registry's architecture as metadata-only infrastructure meant for downstream aggregators rather than a store end-user MCP clients query directly, and documents its namespace-based publisher trust model. _Limit: The registry was in preview status at retrieval time, so behaviour may change before general availability, and it explicitly delegates security scanning to underlying package registries instead of performing its own._
- [MCP client best practices](<https://modelcontextprotocol.io/docs/2026-07-28/develop/clients/client-best-practices>) (documentation, 2026): Official guidance for MCP hosts on progressive tool discovery and on keeping large intermediate results out of the model context, the client-side counterpart to the server specifications above. _Limit: Pinned to the 2026-07-28 documentation set; it should be rechecked against newer dated releases of the protocol._
- [MCP Apps (ext-apps)](<https://github.com/modelcontextprotocol/ext-apps>) (specification, 2025): The official specification and SDK for an MCP extension that lets a server return interactive user interface inside the host, extending agent-facing surfaces from text results to embedded UI. _Limit: An official extension rather than part of the core protocol; the MCP extensions overview lists it as Stable (fixed within a protocol revision), but support still differs between MCP hosts. Documentation is at modelcontextprotocol.io/extensions/apps/overview._
- [SEP-2127: MCP Server Cards - HTTP Server Discovery](<https://modelcontextprotocol.io/seps/2127-mcp-server-cards>) (specification, 2026): A Final Extensions Track proposal for a static, cacheable card that tells a client where a remote MCP server is, which transports and protocol versions it supports and who runs it, before connecting; tools are left out because they vary per user and session. _Limit: The page is a historical record of the accepted design; the normative schema now lives in the modelcontextprotocol/ext-server-card repository, where Server Cards are a Beta official extension with no destination yet stated, and a client still has to connect to learn what tools a server offers._
- [Model Context Protocol specification 2026-07-28: Key Changes](<https://modelcontextprotocol.io/specification/2026-07-28/changelog>) (specification, 2026): The authoritative list of what changed in the stateless revision, each item linked to its SEP: removal of the initialize handshake and protocol sessions, server/discover, the Multi Round-Trip Requests pattern for mid-call input, Tasks moved to an extension, cacheable list results, deterministic tool ordering and routing headers. Server and client authors can work through it as a migration checklist. _Limit: A change log rather than a guide; several items are breaking changes and SDK support for them differs by language._
- [MCP Extensions overview](<https://modelcontextprotocol.io/docs/extensions/overview>) (documentation): Explains how optional capabilities beyond the core protocol are identified, negotiated and moved through Experimental, Beta and Stable stages, with a table giving the current stage of each official extension (authorisation extensions, MCP Apps, Tasks for durable long-running work, Skills over MCP and Server Cards). It is the reference for deciding how far to rely on a given extension. _Limit: A living page with no stated date whose stage tables change as extensions move, and it does not say which clients support each extension._
- [What a Random Draw from the MCP Registry Contains, and What Tool-Use Benchmarks Contain Instead](<https://arxiv.org/abs/2609.10962>) (paper, 2026): Draws a seeded probability sample of 400 npm and stdio servers from a 24,135-server registry census and probes each over the wire, finding that fewer than half complete an initialise handshake and that optional safety annotations are frequently missing. It gives a re-runnable baseline for ecosystem quality and a caution about how curated samples flatter it. _Limit: Single-author preprint covering only npm and stdio servers from one registry snapshot._
- [From REST to MCP: An Empirical Study of API Wrapping and Automated Server Generation for LLM Agents](<https://arxiv.org/abs/2507.16044>) (paper, 2025): Examines 116 official MCP servers to see how they wrap existing REST APIs and how much of each API they expose, then tests generating servers from 80 real OpenAPI contracts with and without specification repair and tool-set reduction. API owners get a list of the specification defects that most often stop generated tools from working. _Limit: Preprint with no stated venue whose title and scope changed across versions; generation success is judged per tool rather than per end-to-end agent task._
- [MCP Inspector](<https://github.com/modelcontextprotocol/inspector>) (tool, 2024): The project's own tool for connecting to an MCP server and seeing exactly which tools, resources and prompts a client receives, with web, scriptable command-line and terminal interfaces so checks can run in CI or inside a coding agent's feedback loop. It is a sensible first step before any model-in-the-loop evaluation of a server. _Limit: Tests protocol behaviour and lets you exercise tools by hand; it does not measure whether agents choose or use the tools well._

## Context, memory and handoffs

- [Effective context engineering for AI agents](<https://www.anthropic.com/research/effective-context-engineering-for-ai-agents>) (essay, 2025): Explains how to treat an agent's context as a finite budget, covering just-in-time retrieval, compaction and structured notes, which informs how documentation and tool output should be shaped for agents. _Limit: Written from one model provider's internal practice; specific patterns may not transfer unchanged to other models or agent harnesses._
- [Context Rot: How Increasing Input Tokens Impacts LLM Performance](<https://www.trychroma.com/research/context-rot>) (paper, 2025): Holds task difficulty fixed while varying only input length across 18 models, and reports that reliability falls as inputs grow and that distractors and haystack structure change results in uneven ways. It gives tool and documentation owners a concrete reason to return short, relevant results rather than large dumps. _Limit: Vendor technical report (Chroma), not peer reviewed, using deliberately simple synthetic and conversational tasks rather than end-to-end agent workflows._
- [Context Engineering for AI Agents: Lessons from Building Manus](<https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus>) (essay, 2025): Turns production experience into design rules that bear directly on tool surfaces: keep prompt prefixes and tool lists stable so caches can be reused, mask tools instead of removing them, give related tools consistent name prefixes, leave failed actions visible, and keep compression reversible by retaining a path or URL. It works as a checklist when deciding how tools are named and what they return. _Limit: A single company's engineering essay; the recommendations are not backed by a published evaluation._
- [Memory tool (Claude API documentation)](<https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool>) (documentation): Specifies a client-side, file-shaped memory surface under /memories, where the model requests operations and the integrator runs them against storage it controls, with explicit guidance on path traversal protection, file size limits and expiry. It is a concrete reference for anyone designing persistent memory that an agent reads and writes across sessions. _Limit: Vendor documentation for one provider's tool interface, and actual behaviour depends on the integrator's handler and storage._
- [Same Context, Different Agents: A Behavioral Study of Semantic Layers, Multi-Agent Orchestration and Memory Compaction in Data Agents](<https://arxiv.org/abs/2610.20959>) (paper, 2026): Tests semantic layers, orchestration and compaction alone and in combination with seven models on 1,514 long-horizon data tasks, and reports that the same context aid helps some agent behaviours and hurts others (for example, a semantic layer can stop thorough agents from inspecting the data). Teams that publish data descriptions or semantic layers for agents get a reason to test them against varied agent behaviours, not one accuracy figure. _Limit: Preprint limited to data-agent benchmarks, and the behaviour groups are the authors' own classification._
- [Diagnosing and Mitigating Context Rot in Long-horizon Search](<https://arxiv.org/abs/2606.29718>) (paper, 2026): Identifies premature termination, where search agents give up or give uncertain wrong answers well before the context window is full, links its rate to context length, and compares seven context management methods. It supports keeping peak context low through paginated, trimmed and compact tool and search responses. _Limit: Preprint evaluated on deep-search benchmarks with four models, so implications for other tool surfaces are inferred rather than tested._
- [Agents Cannot Hand Over What They Have Not Yet Understood](<https://arxiv.org/abs/2611.18642>) (paper, 2026): Measures how much an agent's learning survives a short written note to a successor, separating a smaller loss from compressing once from a larger loss from compressing repeatedly, and reports that writing each note from the full earlier record recovers most of the gap. It is directly relevant to session continuation files, subagent briefs and context-window handoffs. _Limit: Single-author preprint using synthetic hidden-rule worlds and a fixed 300-character note budget._
- [Facts Without Rules: Boundary Metadata Collapse in Multi-Agent LLM Handoffs](<https://arxiv.org/abs/2608.29028>) (paper, 2026): Shows that handoff summaries between agents tend to keep operational facts while dropping the markers that say how those facts may be used, and that explicit constraints leak far less than vague wording while prompt-only fixes help only partly. It is a design lesson for anyone defining handoff or summary formats that carry permissions or privacy limits. _Limit: Preprint on a controlled testbed with three models, so leakage rates may differ in production systems._

## Protocols and machine-readable surfaces

- [OpenAPI Specification v3.2.0](<https://spec.openapis.org/oas/v3.2.0.html>) (specification, 2025): OpenAPI remains a practical bridge between HTTP APIs, developer docs, and agent-readable operation metadata. _Limit: An OpenAPI file can be syntactically valid while still being poor AX if operation names, examples, errors, and auth flows are unclear._
- [JSON Schema Draft 2020-12](<https://json-schema.org/draft/2020-12>) (specification, 2020): JSON Schema is a foundation for tool input contracts, structured outputs, API validation, and agent-readable constraints. _Limit: Schemas need examples, semantics, and versioning discipline; validation alone does not explain intent._
- [Arazzo Specification v1.1.0](<https://spec.openapis.org/arazzo/v1.1.0.html>) (specification, 2026): Describes sequences of API calls that achieve an outcome, including success criteria and failure actions, which is the workflow and recovery layer that per-endpoint OpenAPI descriptions leave an agent to infer. _Limit: Less widely published than OpenAPI, and it describes workflows without executing them; an agent still needs a separate way to run the calls._
- [Agent2Agent (A2A) Protocol specification](<https://a2a-protocol.org/latest/specification/>) (specification, 2026): Defines agent cards for capability discovery and a task-based exchange for delegating work between independently built agents, the agent-to-agent layer that MCP does not address. _Limit: The latest URL tracks a moving version (v1.0.1 at retrieval, after the first stable v1.0.0 release in March 2026), and published adoption figures come from the project itself rather than independent measurement._
- [AG-UI: Agent-User Interaction Protocol](<https://docs.ag-ui.com/introduction>) (specification, 2025): An open, event-based protocol for streaming agent state, UI intents and user input between an agent backend and a user-facing application, relevant to keeping people informed while an agent works. _Limit: Governed by its originating project rather than a standards body, and support varies by agent framework._
- [Agent Communication Protocols (agentproto) working group](<https://datatracker.ietf.org/wg/agentproto/about/>) (specification, 2026): Tracks the IETF process for a working group on user-to-agent, agent-to-agent and agent-to-tool communication, a standards-track venue with more procedural weight than the many individual agent drafts. _Limit: Chartered in October 2026 with milestones running to March 2028, so it has no adopted protocol yet and its scope is limited to dialog identifiers, lifecycle and context propagation rather than a full agent protocol._
- [A Survey of AI Agent Protocols](<https://arxiv.org/abs/2504.16736>) (paper, 2025): Compares agent protocols along shared dimensions, giving one place to understand design choices across MCP, A2A and related proposals before reading each specification. _Limit: A 2025 survey that predates several later protocols, including the commerce and payment protocols listed below, and it treats IBM's Agent Communication Protocol (ACP) as separate although ACP merged into A2A in August 2025._
- [Agentic AI Use Cases and Requirements (draft-agentic-ai-usecases-requirements)](<https://datatracker.ietf.org/doc/draft-agentic-ai-usecases-requirements/>) (specification, 2026): Works through six agent communication scenarios, including a long-running delegated task with an authorisation checkpoint and tool, data and API mediation between agents, and derives numbered protocol requirements from each. Protocol and platform teams can use it as a checklist for whether their design covers dialog management, identity and security in realistic flows. _Limit: An Informational Internet-Draft that is a candidate for agentproto adoption rather than an adopted working group document, so its requirements may change or be dropped._
- [Architecture for AI Agent Communications on the Internet (draft-manyfolks-agentproto-arch)](<https://datatracker.ietf.org/doc/draft-manyfolks-agentproto-arch/>) (specification, 2026): Defines the 'agentic dialog' that the IETF agentproto work is built around and decomposes it into dialog identifiers, lifecycle, recovery, structured error and progress signalling, and cancellation and interruption. It also separates the principal from the agent and the client from the server, which gives designers a shared vocabulary for interruption and recovery across vendors. _Limit: First revision of an individual Informational draft; it deliberately defines no authorisation mechanism and defers to OAuth and WIMSE work, so many details remain open._
- [RFC 9457: Problem Details for HTTP APIs](<https://www.rfc-editor.org/rfc/rfc9457.html>) (specification, 2023): The IETF format for machine-readable HTTP API errors, with type, status, title, detail and instance members plus API-specific extension members. It gives agent-facing APIs a standard error body that a client can branch on instead of parsing prose or HTML error pages. _Limit: A general HTTP standard written before AI agents; it does not define retry safety or recovery hints, which an API has to add through its own extension members._
- [RateLimit header fields for HTTP (draft-ietf-httpapi-ratelimit-headers)](<https://datatracker.ietf.org/doc/draft-ietf-httpapi-ratelimit-headers/>) (specification, 2026): Defines the RateLimit-Policy and RateLimit response headers so a server can advertise its quota policies and remaining capacity. Agent clients can then pace requests from a machine-readable signal rather than learning limits from 429 responses. _Limit: A working group Internet-Draft, not an RFC; revision 11 expires on 24 November 2026, so check for a newer revision before citing details._
- [A2A Protocol Technology Compatibility Kit (TCK)](<https://github.com/a2aproject/a2a-tck>) (repository, 2025): The A2A project's conformance suite, which runs against a live agent over gRPC, JSON-RPC and HTTP+JSON, groups tests by MUST, SHOULD and MAY requirement levels and writes compatibility reports. Teams can use it to check an implementation against the specification before other agents depend on it. _Limit: Tests protocol conformance only, not whether an agent's declared skills are accurate, and it has no tagged releases, so pin a commit (the README and recent commits disagree on the minimum Python version)._
- [A2A Inspector](<https://github.com/a2aproject/a2a-inspector>) (tool, 2025): An official A2A project tool that fetches an Agent Card, detects whether it is v1.0 or v0.3, checks it against the specification, and logs and validates every exchange over JSON-RPC, HTTP+JSON and gRPC. It shows a publisher what a calling agent will actually receive, and its card editor and AI Catalog import help when drafting discovery metadata. _Limit: Checks card and protocol conformance rather than the usefulness or accuracy of declared skills, and the current v1.0 line is published as alpha pre-releases._
- [Agent Network Protocol (ANP) specifications](<https://github.com/agent-network-protocol/AgentNetworkProtocol>) (specification, 2026): The canonical repository for the ANP 1.2 specification set, covering DID authentication, the did:wba method, naming, Agent Description documents and a .well-known Agent Discovery protocol, with a per-document status table. It shows a decentralised, DID-based approach to agent identity and discovery to set against A2A Agent Cards and MCP Server Cards. _Limit: A community specification not developed in a standards body; several parts (authorisation, meta-protocol, payments) are still drafts, and the W3C Community Group that discusses it has no standards-track status._
- [The Cost of Saying Hello: An Empirical Study of Handshake Overhead in AI Agent Communication Protocols](<https://arxiv.org/abs/2610.30151>) (paper, 2026): Measures round trips, latency, bytes and tokens consumed before useful work begins in MCP (both its 2025 and 2026 handshakes), A2A and ACP using each official SDK, and reports that token cost grows with the size of the counterpart's capability inventory. It gives concrete figures to weigh when deciding how much capability metadata to expose up front. _Limit: A single-author preprint measured on loopback and emulated latency rather than production networks, and ACP has since merged into A2A._

## Agent identity and authorization

- [WorkOS FGA: The authorization layer for AI agents](<https://workos.com/blog/agents-need-authorization-not-just-authentication>) (essay, 2026): Distinguishes on-behalf-of agents, which need scope attenuation under the acting user's own permissions, from autonomous agents, which need fine-grained scope rather than broad client-credential grants, using worked confused-deputy and shared-context scenarios. _Limit: A vendor architecture piece promoting WorkOS Fine-Grained Authorization; its one supporting statistic, an average 47-day stale-credential lifetime, is uncited in the retrieved text._
- [Agent Registration with Auth.md](<https://workos.com/blog/agent-registration-with-auth-md>) (specification, 2026): Proposes an open protocol, a discoverable /auth.md document plus three HTTP endpoints extending RFC 9728 Protected Resource Metadata, for an agent to register a new user on their behalf, a gap OAuth's browser-consent flow does not cover. _Limit: Adoption outside WorkOS's own ecosystem is unstated in the source; as an author-organisation announcement, independent implementation evidence is still needed._
- [Understanding Authorization in MCP](<https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/authorization>) (specification, 2026): Walks through the MCP authorisation flow step by step, including consent, scopes and client registration, where it now recommends pre-registration or Client ID Metadata Documents and treats Dynamic Client Registration as deprecated, plus common pitfalls such as open registration endpoints. _Limit: Remote and local transports differ, so the same authorisation pattern will not fit every deployment._
- [HTTP Message Signatures (RFC 9421)](<https://www.rfc-editor.org/rfc/rfc9421.html>) (specification, 2024): The IETF standard for signing HTTP messages, on which verified-bot schemes and several agent identity proposals build so that a request can carry a verifiable signature. _Limit: Defines the signing mechanism only; it says nothing about which signers to trust or what a verified agent may do._
- [Web Bot Auth](<https://developers.cloudflare.com/bots/reference/bot-verification/web-bot-auth/>) (documentation): Documents how bots and agents can prove operator identity on each request with HTTP message signatures instead of a spoofable user-agent string. _Limit: Vendor documentation for one network's implementation; the standards-track text is the IETF working group draft draft-ietf-webbotauth-httpsig-protocol, and like it this authenticates the operator of the agent, not the person it acts for._
- [AI Identity Management System (draft-ietf-wimse-aims)](<https://datatracker.ietf.org/doc/draft-ietf-wimse-aims/>) (specification, 2026): A multi-author Internet-Draft describing how existing standards, the WIMSE workload identity architecture and the OAuth 2.0 family, can be applied to agent authentication and authorisation without a new protocol. _Limit: An early WIMSE working group draft (revision 01) of best practices that defines no new protocol; it replaced the earlier individual draft draft-klrc-aiagent-auth and may still change substantially._
- [Agent Identity overview (Google Cloud IAM)](<https://docs.cloud.google.com/iam/docs/agent-identity-overview>) (documentation): Shows one cloud provider giving each agent its own attested, SPIFFE-based identity distinct from human and service accounts, a concrete implementation to compare with vendor-neutral proposals. _Limit: Describes one provider's implementation, which does not transfer directly to other clouds or self-hosted identity systems._
- [Agent Name Service v2 (ANS): A Domain-Anchored Identity Layer for Autonomous AI Agents (Internet-Draft)](<https://datatracker.ietf.org/doc/draft-narajala-courtney-ansv2/>) (specification, 2026): Binds an agent endpoint to the holder of its DNS domain, a specific software release and an auditable history using DNSSEC, the Web PKI, optional DANE and an append-only Merkle transparency log, and adopts DNS-AID records for discovery. Its stated threat model lets relying parties see what each check does and does not prevent. _Limit: An individual Internet-Draft with no working group adoption; normative detail sits in separate ANS specifications now hosted by a Linux Foundation project, and the earlier OWASP v1 whitepaper is superseded._
- [SI Agent Standards Initiative (NIST)](<https://www.nist.gov/super-intelligence/si-agent-standards-initiative>) (framework, 2026): A government standards programme focused on interoperability, security and identity for agents, useful for tracking where public-sector guidance on agent identity is heading. _Limit: A programme page rather than a standard; it was renamed from the AI Agent Standards Initiative in late 2026, and concrete published outputs remain limited._
- [Claim Deployments](<https://vercel.com/docs/deployments/claim-deployments>) (documentation): Documents a provision-first, claim-later flow: an agent deploys through the API, requests a transfer code valid for 24 hours and gives the person a claim URL, after which the project and supported linked databases move into their account. _Limit: One vendor's implementation of the claim step; the page covers transfer mechanics but not how the agent is identified or what happens to deployments that are never claimed._
- [Claimable Neon](<https://neon.com/docs/reference/claimable-neon>) (documentation): The same claim-later pattern for a database: an agent provisions a Postgres project without an account, an unclaimed project expires after 72 hours with storage and transfer caps, a claim code lasts 15 minutes, and discovery runs through auth.md. _Limit: Vendor documentation for one service; the expiry windows and caps are given as current values, and the page reports nothing on how often projects are claimed or abandoned in practice._
- [HTTP Message Signatures for automated traffic (draft-ietf-webbotauth-httpsig-protocol)](<https://datatracker.ietf.org/doc/draft-ietf-webbotauth-httpsig-protocol/>) (specification, 2026): The Web Bot Auth working group's adopted protocol text: it sets out how an automated client signs requests with RFC 9421, the Signature-Agent header that tells a verifier where the signer's keys live, a JWKS-based key directory and the well-known URI that serves it. Agent builders and site operators can implement against the standards-track text instead of relying on one vendor's documentation. _Limit: An early working group Internet-Draft (revision 01) with no intended RFC status recorded yet; it authenticates the operator of the client, not the person it acts for or what it is allowed to do._
- [MCP Client Registration (protocol revision 2026-07-28)](<https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration>) (specification, 2026): The normative order in which an MCP client gets an OAuth identity at a server it has never met: pre-registered credentials first, then Client ID Metadata Documents when the authorisation server advertises support, then Dynamic Client Registration, which this revision deprecates. It also requires clients to key stored credentials to the issuing authorisation server and re-register when that server changes, a concrete rule for agents that connect to many servers. _Limit: Relies on the IETF Client ID Metadata Document draft, which is not yet an RFC, and authorisation server support for it varies, so the DCR fallback remains in practice._
- [Enterprise-Managed Authorization (MCP extension)](<https://modelcontextprotocol.io/extensions/auth/enterprise-managed-authorization>) (specification, 2026): Explains how an organisation's identity provider, rather than each employee, decides which MCP servers an agent client may reach: the client exchanges the user's SSO assertion for an ID-JAG and redeems it at the server's authorisation server with the JWT bearer grant. The page gives the exact token exchange parameters and a table of identity providers and authorisation servers with documented support, which helps teams judge feasibility before building. _Limit: An opt-in official extension (listed as Stable in the ext-auth repository) that only works when the client, the enterprise IdP and the server's authorisation server all support it, and vendors target different revisions of the underlying ID-JAG draft._
- [OAuth Client ID Metadata Document (draft-ietf-oauth-client-id-metadata-document)](<https://datatracker.ietf.org/doc/draft-ietf-oauth-client-id-metadata-document/>) (specification, 2026): Lets an OAuth client use an HTTPS URL as its client\_id, pointing at a JSON metadata document the authorisation server fetches on demand, so a client can work with servers it has no prior registration with. This is the mechanism MCP now prefers over Dynamic Client Registration, and its fetching, validation and caching rules are what an authorisation server team has to implement. _Limit: A general OAuth working group draft (revision 03) that is not specific to agents and is still a work in progress._
- [Identity Assertion JWT Authorization Grant (draft-ietf-oauth-identity-assertion-authz-grant)](<https://datatracker.ietf.org/doc/draft-ietf-oauth-identity-assertion-authz-grant/>) (specification, 2026): Defines the ID-JAG: a token an enterprise identity provider issues by token exchange so that an application or agent can obtain an access token for a third-party API that already trusts that provider for SSO, without a separate consent redirect. It is the protocol beneath Cross-App Access and the MCP Enterprise-Managed Authorization extension. _Limit: A working group Internet-Draft (revision 06) with no RFC status yet, and implementations in the field track different revisions of it._
- [OAuth Identity and Authorization Chaining Across Domains (draft-ietf-oauth-identity-chaining)](<https://datatracker.ietf.org/doc/draft-ietf-oauth-identity-chaining/>) (specification, 2026): Describes how a client carries identity and authorisation from one trust domain into another by combining token exchange with the JWT bearer grant, which is the pattern an agent needs when a task crosses organisational boundaries. Several agent delegation drafts, including ID-JAG, build on it. _Limit: A general OAuth pattern rather than an agent profile; it is approved and in the RFC Editor queue but has no RFC number yet._
- [RFC 9728: OAuth 2.0 Protected Resource Metadata](<https://www.rfc-editor.org/rfc/rfc9728.html>) (specification, 2025): Lets a protected resource publish a well-known metadata document naming the authorisation servers and scopes that apply to it, so an agent client can discover how to obtain a token without prior configuration. MCP authorisation and the Auth.md proposal already listed both depend on it. _Limit: Covers metadata publication only; it says nothing about agent identity, delegation or consent._
- [A Protocol-Agnostic Threat Classification for Cross-Boundary AI Agent Authorization](<https://openid.net/wp-content/uploads/2026/10/A-Protocol-Agnostic-Threat-Classification-for-Cross-Boundary-AI-Agent-Authorization_with-Cover.pdf>) (framework, 2026): An OpenID Foundation community group threat model for agents acting across trust boundaries, covering how identity, authority and the target resource can be misread once a call leaves its home domain, with lifecycle controls framed as joiner, mover and leaver steps. Architects can turn its categories into review questions for any gateway or federation design, whatever protocol it uses. _Limit: Explicitly a threat model, not a specification or remediation guide; the authors say mitigation guidance will follow in later documents._
- [Identity Management for Agentic AI (OpenID Foundation whitepaper)](<https://arxiv.org/abs/2510.25819>) (paper, 2025): A standards-community survey of what existing OAuth, OpenID Connect and enterprise identity tools already offer for securing agents and where delegated authority, agent-specific identities and scalable access control still need work. It is useful orientation before reading the individual Internet-Drafts in this section. _Limit: A whitepaper setting an agenda rather than a specification, and it predates most of the 2026 drafts and MCP changes listed here._
- [Agentic Identity and Access Management (CoSAI)](<https://www.coalitionforsecureai.org/wp-content/uploads/2026/04/agentic-identity-and-access-control.pdf>) (framework, 2026): A design-pattern paper that treats agents as first-class identities, keeps an agent's own baseline rights separate from on-behalf-of rights, prefers short-lived task-bound entitlements and requires enforcement at every hop and at the final tool or API, illustrated end to end with an invoice-processing agent. It gives teams a reference model built on existing IAM rather than a new stack. _Limit: A coalition paper (version 1.0) whose patterns are recommendations, not an interoperable specification or conformance test._
- [NCCoE Software and Agentic AI Identity and Authorization project hub](<https://pages.nist.gov/nccoe-ai-identity/>) (documentation, 2026): NIST NCCoE's public home for its agent identity project, linking the February 2026 concept paper and a summary of the more than 600 comments it received, which records broad support for building on existing standards. The planned SP 1800 practice guide and interim outputs are to be published here. _Limit: Early project material: no practice guide or example implementation exists yet, and NIST pages now use the term 'SI agents' following a 2026 renaming, which may confuse searches._
- [Broken Gates: Re-evaluating Web Bot Defenses in the Age of LLM Agents](<https://arxiv.org/abs/2607.18659>) (paper, 2026): Measures seven solver services and eight LLM browser agents against four widely deployed bot defences and finds that the browser and account state shown to the verifier, more than challenge solving, decides whether agents get through. It is evidence for site owners that behavioural signals do not separate legitimate agents from abuse, which is the gap that explicit identity schemes such as Web Bot Auth aim to fill. _Limit: A preprint covering four defences at one point in time; vendors change their defences frequently, so the figures may not hold for long._
- [Fundamental concepts in Microsoft Entra Agent ID](<https://learn.microsoft.com/en-us/entra/agent-id/key-concepts>) (documentation, 2026): Sets out a concrete enterprise object model for agents: blueprints that hold credentials and mint tokens for many agent identities, optional paired agent user accounts, separate owner, sponsor and manager roles, and on-behalf-of flows for interactive agents versus client credentials for autonomous ones. It is a useful comparison point for the Google Cloud agent identity entry already listed. _Limit: Vendor documentation tied to Microsoft Entra and Microsoft Graph, and its constructs do not transfer directly to other identity providers._
- [Authenticate requests with Web Bot Auth (experimental), Google crawling documentation](<https://developers.google.com/crawling/docs/crawlers-fetchers/web-bot-auth>) (documentation, 2026): A second large operator's deployment notes for Web Bot Auth: a subset of Google-Agent requests are signed as https://agent.bot.goog, with the signature label to look for, an IP-based fallback, and the option to respond first and validate afterwards on latency-sensitive paths. Verifier implementers get a concrete second profile to test against besides Cloudflare's. _Limit: Vendor documentation for an experiment: Google states that not all of its agents sign and not every request is signed, so IP verification is still required._
- [When MCP Meets OAuth: Common Pitfalls Leading to One-Click Account Takeover](<https://obsidiansecurity.com/blog/when-mcp-meets-oauth-common-pitfalls-leading-to-one-click-account-takeover>) (essay, 2026): Explains, from disclosed cases, why remote MCP servers that wrap an existing API end up acting as both an authorisation server for MCP clients and a single shared OAuth client upstream, and how failing to bind consent and state to the user session lets one malicious link leak an authorisation code. It is a practical checklist for teams putting an existing OAuth-protected API behind MCP. _Limit: Vendor security research based on a handful of responsibly disclosed cases rather than a systematic measurement._

## Agentic commerce and payments

- [Agentic Commerce Protocol (ACP)](<https://github.com/agentic-commerce-protocol/agentic-commerce-protocol>) (specification, 2025): The specification repository for an open checkout protocol in which an agent passes a scoped payment token while the merchant remains merchant of record, with schemas and a changelog. _Limit: The README states the specification is maintained by OpenAI and Stripe and is in beta, with dated releases (the latest, 2026-04-17, adds cart, feed, orders, authentication and MCP); implementing it does not by itself list a merchant on any AI shopping surface._
- [Agent Payments Protocol (AP2)](<https://ap2-protocol.org/>) (specification, 2025): Specifies signed mandates that record what a person authorised an agent to buy, aimed at verifiable authorisation for payments and offered as an extension to A2A and UCP. _Limit: Partner counts are supplied by the sponsors, the site now links a v0.2 release, and further standardisation is stated to continue in FIDO Alliance working groups, so the specification may still change; independent evidence of production use was not found._
- [Universal Commerce Protocol (UCP)](<https://ucp.dev/>) (specification): An open specification for agentic commerce covering discovery, checkout and post-purchase steps, published as dated versions (for example 2026-08-25) with explicit version selection before capability negotiation, an optional AP2 Mandates extension for cryptographic proof of user authorisation, and a public repository, SDKs and reference implementations. _Limit: Written from its sponsoring companies' perspective, and cross-protocol interoperability testing is not documented on the site._
- [x402](<https://github.com/x402-foundation/x402>) (specification, 2025): An HTTP-native payment protocol built around the 402 Payment Required status code, so an agent can pay for a request in the same exchange, a different mechanism from checkout-based protocols. _Limit: Early deployments centre on stablecoin settlement, which brings custody and regulatory considerations that card-based checkout does not._
- [How Stripe is designing Checkout for AI agents](<https://stripe.dev/blog/how-stripe-is-designing-checkout-for-ai-agents>) (essay, 2026): Describes a payment page that exposes WebMCP tools progressively, so a submit tool appears only once the form is valid, and that derives form tools from the rendered HTML rather than maintaining a separate agent-only checkout. _Limit: A vendor engineering post; its efficiency figures come from its own 60 test runs across six models on a fictional shop, and WebMCP is an experimental browser capability whose API may change._
- [The "Payment" HTTP Authentication Scheme (Machine Payments Protocol core)](<https://datatracker.ietf.org/doc/draft-httpauth-payment/>) (specification, 2026): Gives HTTP 402 defined semantics: the server issues a Payment challenge in WWW-Authenticate, the client retries with a credential in Authorization, and success returns a Payment-Receipt, with payment methods defined in separate specifications. Its table of status codes and problem types (malformed credential, unknown or reused challenge, expired challenge, failed verification, policy denial after valid payment) tells an API owner exactly what an agent should receive at each failure point. _Limit: An individual Internet-Draft (revision 01, September 2026) by authors from the two companies that co-develop MPP, Tempo and Stripe, so it is work in progress rather than an RFC; mpp.dev is the sponsors' developer overview._
- [Verifiable Intent](<https://github.com/agent-intent/verifiable-intent>) (specification): Defines a layered SD-JWT chain from credential provider to user to agent, binding amount ranges, allowed line items, payees and approved merchants as machine-checkable constraints, and separates a user-confirmed Immediate mode from a delegated Autonomous mode. It gives designers a concrete way to prove afterwards that an agent purchase stayed inside the scope a person approved. _Limit: Draft v0.1 maintained by Mastercard; transport, key provisioning, enrolment and dispute resolution are explicitly out of scope._
- [Trusted Agent Protocol](<https://github.com/visa/trusted-agent-protocol>) (specification): Shows how a merchant can tell a credentialed shopping agent from anonymous automated traffic: the agent signs requests with RFC 9421 HTTP message signatures bound to the merchant domain and the operation (browsing or payment), with timestamps and session identifiers against replay, and can pass consented consumer and payment identifiers to prefill checkout. The repository includes a runnable sample with agent, key registry, verifying proxy and merchant components. _Limit: Visa-led vendor material; recognition depends on Visa-approved agents and a Visa-run key registry, and the repository offers sample code rather than versioned releases of the specification._
- [Shared payment tokens (Stripe)](<https://docs.stripe.com/agentic-commerce/concepts/shared-payment-tokens>) (documentation): Documents a concrete scoped credential for agent purchases: the agent grants a seller a token limited by currency, maximum amount and expiry, the seller can resolve it only once for a third-party processor, and webhook events report use and deactivation. It is a worked example of bounding agent spending at the API level rather than in the prompt. _Limit: Public preview vendor documentation for one provider, with regional availability limits and a preview API version that may change._
- [Product feed schema (OpenAI Agentic Commerce)](<https://developers.openai.com/commerce/specs/file-upload/products>) (specification): States the catalogue fields a merchant supplies for products to be discoverable in one assistant's shopping surface, one row per purchasable variant, with explicit value conventions: omit unknown values, never use placeholder strings such as n/a, and treat an empty value as no value rather than zero or false. It is one of the clearest public statements of what an agent-facing product feed must contain. _Limit: Vendor specification for one assistant's ingestion pipeline; ads and checkout need separate integrations, and a Draft schema view sits alongside the Stable one._
- [Native checkout overview (Google Universal Commerce Protocol guide)](<https://developers.google.com/merchant/ucp/guides/overview/native-checkout>) (documentation, 2026): Turns UCP checkout into an implementable contract: a session status lifecycle from incomplete to completed, canceled or error, a handoff point where the agent passes control to a Google interface for payment and fulfilment details, per-endpoint availability and latency targets, and advice to return structured UCP errors for payment declines. It links SDKs and a conformance test suite. _Limit: Vendor implementation guide for one platform; payment entry is deliberately kept away from the agent, so it documents a human-completed flow rather than autonomous purchase._
- [Beyond the Mandate: A Systematic Security Analysis of the Agent Payments Protocol (AP2)](<https://arxiv.org/abs/2608.23858>) (paper, 2026): Catalogues 48 threats to AP2 v0.2 across five lifecycle phases and five deployment architectures, demonstrates the eight highest-scored ones on a testbed, and describes a deployment-aware scanner. Its central lesson for designers is that signed mandates protect transaction data after signing but not the A2A messages and MCP tool calls that shape a purchase beforehand. _Limit: Preprint; threats are demonstrated on the authors' own testbed because no complete public AP2 deployment was available, and severity comes from a scoring scheme rather than observed incidents._
- [A Formal Analysis of Agent Payment Protocols](<https://arxiv.org/abs/2609.00060>) (paper, 2026): Models x402, MPP, ACP and AP2 in the Tamarin prover against a common payment lifecycle and condenses the results into 18 shared security principles about keeping delegated authority consistent with the final charge and the service delivered. Implementers get a cross-protocol list of bindings to check in their own flows. _Limit: Preprint; the models abstract specifications that are still changing, and implementation validation concentrates on x402._
- [Free-Riding the Agentic Web: A Systematic Security Analysis of x402 Payments](<https://arxiv.org/abs/2605.30998>) (paper, 2026): Traces four flaw classes in x402 deployments (cross-resource substitution, duplicate settlement races, allowance overdraft and denial of settlement) to the HTTP, scheme or SDK layer and proposes mitigations for each. Anyone charging agents per request over HTTP 402 gets concrete failure cases to test for. _Limit: Preprint centred on x402 and blockchain settlement; the authors state all findings were disclosed, so some may already be fixed in current SDKs._
- [What Is Your AI Agent Buying? Evaluation, Biases, Model Dependence, & Emerging Implications for Agentic E-Commerce](<https://arxiv.org/abs/2508.02630>) (paper, 2025): Uses a provider-agnostic sandbox (ACES) to audit how shopping agents choose products, reporting position effects that persist in text-only interfaces, penalties for sponsored tags, rewards for platform endorsements and market-share swings after model updates. For sellers and platforms it argues for continuous testing of listings against agents rather than one-off optimisation. _Limit: Preprint using a mock marketplace; observed preferences are tied to specific model versions and may not persist._
- [Whom Do AI Agents Work For? Role Assignment Induces Sponsorship Bias in LLM Recommenders](<https://arxiv.org/abs/2609.17989>) (paper, 2026): Controlled choice experiments show that naming a booking platform rather than a traveller as the agent's principal weakens the penalty agents apply to sponsored listings, and that stricter disclosure wording (Sponsored rather than Promoted) lowers paid-listing choice without closing that gap. It matters for anyone deciding how paid placement is labelled for agents and how an agent's role is worded. _Limit: Preprint based on prompted roles in travel-booking experiments, not observation of deployed shopping assistants._
- [Get In, Decide, Prove: A Merchant-Side Readiness Benchmark for Agentic Commerce](<https://arxiv.org/abs/2610.17378>) (benchmark, 2026): Measures the merchant side of an agent purchase: whether a site admits an agent (reported separately for a declared bot, a declared headless browser and a user-present browser), whether published terms are precise enough to decide a buyer mandate on total cost, cancellation, service date and variant, and what evidence of the agreement remains. Scores carry evidence coverage and missingness bounds, and a companion dataset is published on Zenodo. _Limit: Pilot preprint whose authors declare an affiliation with a company that has a commercial interest in merchant assessment; the scanner is available only on request, and the readiness weights have not been validated against purchase outcomes._

## Human control, approval and recovery

- [What You Approve Is What Executes: Consent Integrity for Black-Box LLM Agents](<https://arxiv.org/abs/2606.02668>) (paper, 2026): Names the missing 'Consent Integrity' property for agent approval dialogs, the action shown must be rendered by a trusted mediator from the real action rather than the agent's own narration, and tests a prototype against 1,330 trusted-tool abuse techniques. _Limit: The prototype analyser, renderer, and execution binder is a research system tested on the GTFOBins and tldr corpora, not a deployed product feature available to adopt directly._
- [Loopjacking: Hijacking Human-in-the-Loop Approval](<https://arxiv.org/abs/2609.21081>) (paper, 2026): Defines Loopjacking as any case where the operation a human approves does not match what a system actually executes, and reproduces both representation-based and post-approval state-substitution variants in named, released agent products. _Limit: The paper names a purposive set of tested products rather than a random or exhaustive sample, so prevalence across the wider agent-product ecosystem is not established._
- [Oversight Has a Capacity: Calibrating Agent Guards to a Subjective, Fatiguing Human](<https://arxiv.org/abs/2606.08919>) (paper, 2026): Measures inter-reviewer agreement on a hand-labelled set of 125 adversarially-weighted agent actions and models the human reviewer as fatiguing under escalation load, finding that more oversight can reduce realised safety past a point. _Limit: The reviewer-fatigue model and the 125-action labelled set are the authors' own construction; whether the same capacity limit holds for other review populations or action types is not tested._
- [Design Principles for Human-Agent Interaction](<https://arxiv.org/abs/2606.20630>) (paper, 2026): Proposes principles across the stages of an agent interaction, including when things go wrong, and applies them to existing agent systems, separating graceful failure from raw task completion as a design goal. _Limit: A position paper with an illustrative rather than statistically validated evaluation._
- [Delegating or Doing? Understanding User Behavior in Hybrid Human-Agent Interfaces](<https://arxiv.org/abs/2608.19551>) (paper, 2026): A 73-participant study of an interface with an MCP-connected assistant finding that assistance reduced interaction effort but not task time, and that the choice to delegate followed personal disposition more than task risk. _Limit: One application and one participant pool, so findings about who delegates may not generalise to other domains._
- [GoEX: Perspectives and Designs Towards a Runtime for Autonomous LLM Applications](<https://arxiv.org/abs/2404.06921>) (paper, 2024): Proposes post-facto validation, undo and damage confinement for actions an agent has already taken, a reference design for recovery when review happens after execution. _Limit: A research runtime, not a hardened dependency; teams still have to define undo semantics for their own actions._
- [Human-in-the-loop (OpenAI Agents SDK)](<https://openai.github.io/openai-agents-python/human_in_the_loop/>) (documentation): Documents how an agent run pauses for approval of sensitive tool calls and resumes from saved state, a concrete framework-level pattern for approval gates. _Limit: Specific to one SDK's run and approval model, so the mechanism does not transfer directly to other frameworks._
- [Agent Approval Laundering: Transitive Effects Beyond the Approved Invocation](<https://arxiv.org/abs/2609.28586>) (paper, 2026): Shows that approving one command or tool call can let through effects the approval never named, such as a package's install scripts or an MCP call's network access, and measures how often approval records in coding agents miss them. _Limit: The benchmark (111 approval and trace pairs, 17 holdout workflows) is the authors' own and small, and the proposed fix is shown only as an integration with one coding agent's permission hook._
- [When Consent Outlives Context: Residual Authority Replay in Long-Lived Agents](<https://arxiv.org/abs/2609.33910>) (paper, 2026): Shows that approvals persisted across tasks or sessions can be replayed later without fresh consent, and that an attacker can build up such leftover authority through harmless requests first; it also compares how eight production coding agents store approvals. _Limit: Attack gains are measured on AgentDojo and Terminal-Bench cases rather than observed incidents, and the per-agent findings describe the versions tested, whose approval storage can change between releases._
- [Do User-Authored Permission Policies Improve Protection Against AI Agent Overreach?](<https://arxiv.org/abs/2608.27443>) (paper, 2026): A randomised study of 113 people without software backgrounds: standing allow, ask and never rules cut runtime prompts but blocked less overreach than approving each action, because most rules were set to ask and unrequested actions were then approved. _Limit: One scripted day of 18 simulated actions with online participants and no real consequences, so it does not show how rules are written, revised or trusted over months of real use._
- [Let the Agent Do It? How Software Practitioners Understand and Make Permission Decisions in Agentic AI Assistants](<https://arxiv.org/abs/2610.06047>) (paper, 2026): Interviews with 18 practitioners and a survey of 115 show how developers decide whether a coding assistant may act, and turn that into requirements for permission systems, such as keeping an agent's permissions separate from the user's intent. _Limit: Relies on what practitioners report rather than logged approval behaviour, and its design implications are not built or tested in a working permission system._
- [Idempotent requests](<https://docs.stripe.com/api/idempotent_requests>) (documentation): A concrete design for retry-safe writes in Stripe's API: the client sends a unique key with a create or update, and in API v1 a retry with that key returns the saved result of the first attempt instead of running it again, so a timed-out agent can retry. _Limit: One vendor's API: key length, pruning after at least 24 hours, the v1 and v2 behaviours and errors on reused keys with different parameters are Stripe's own choices, and the page does not address agents._
- [When Neither Side Confirms: Destructive Tool Approval Across MCP Servers and Hosts](<https://arxiv.org/abs/2611.02527>) (paper, 2026): Audits source code from a sample of 1,000 MCP registry servers and 41 open-source hosts and agent SDKs to ask who actually enforces confirmation of destructive tools, and finds that most pairings have no human approval by default. Host builders get evidence for owning the approval decision (for example, prompting on any tool not annotated read-only or non-destructive) rather than leaving it to servers or elicitation. _Limit: Single-version preprint that relies on a rule-based extractor and open-source hosts only, so closed clients and later changes to defaults are not covered._
- [MCP elicitation (specification, 2026-07-28 revision)](<https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation>) (specification, 2026): The protocol baseline for asking a person for input mid-task: form mode for structured answers, URL mode for credentials, payments and third-party OAuth, distinct accept, decline and cancel outcomes, a ban on collecting secrets through form mode, and client duties to show the full URL and obtain consent before opening it. It also works through a phishing scenario, which is useful when designing consent prompts that cannot be spoofed. _Limit: The specification marks URL mode as a newer feature whose design may change, and it deliberately leaves the user interface to each client, so it does not on its own guarantee a confirmation is shown._
- [The Idempotency-Key HTTP Header Field (Internet-Draft)](<https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/>) (specification, 2026): A vendor-neutral way for a client to mark a POST or PATCH as safe to retry and for a server to answer retries, including 409 for a request still being processed and 422 for a reused key with a different payload. Agents that cannot tell whether a timed-out write succeeded need exactly this contract, and it generalises the Stripe pattern already in the list. _Limit: A working-group Internet-Draft aimed at the Standards Track, not yet an RFC, so details may still change._
- [Where Does Exactly-Once Live? Model, Harness, and Tool-Contract Effects on Duplicate Side Effects in LLM Agents](<https://arxiv.org/abs/2609.29095>) (paper, 2026): Uses LIMBO, a deterministic sandbox of six services with injected faults such as late commits and redelivery, graded against a ledger of committed effects, to ask whether duplicate charges and deployments are best prevented by the model, the harness or the tool contract. The finding that the answer depends on the fault type, with the contract dominating when a read-back cannot reveal what happened, is direct guidance for API designers. _Limit: Single-author preprint run against synthetic services rather than live systems._
- [When Should Users Check? Modeling Confirmation Frequency in Multi-Step Agentic AI Tasks](<https://arxiv.org/abs/2510.05307>) (paper, 2026): Treats where to place confirmation points in a multi-step agent task as a scheduling problem and offers a decision-theoretic model as an alternative to confirming only at the end or at every step. The observed confirm, diagnose, correct and redo cycle is a useful frame for designing intermediate checkpoints. _Limit: Peer-reviewed at CHI 2026, but the evidence comes from lab studies with 8 and 48 participants on bounded tasks, so it may not transfer to long-running or high-stakes production agents._
- [Comparing Human Oversight Strategies for Computer-Use Agents](<https://arxiv.org/abs/2604.04918>) (paper, 2026): Compares four oversight strategies across 192 live web sessions and reports that control often reaches the user too early or too late, that people judge correctness rather than safety, and that upfront plan approval can dampen scrutiny during execution. It helps teams choose between plan review, step approval and live intervention with timing in mind. _Limit: Preprint with no stated venue, drawing on one study of 48 participants on web tasks._
- [The Verifiable Action Card: Trustworthy Human-in-the-Loop Control for Secure Autonomous Agents](<https://arxiv.org/abs/2609.18411>) (paper, 2026): Proposes an approval design for agentic browsers in which the confirmation card is rebuilt from the real pending action, shown in trusted browser chrome outside page or model control, and bound to that exact action when it is dispatched. It is a constructive counterpart to the approval-integrity attacks already listed, such as Loopjacking and approval laundering. _Limit: Preprint evaluated on the authors' own 24-scenario benchmark, so its attack-success figures should not be generalised beyond that setting._
- [How we built Claude Code auto mode: a safer way to skip permissions](<https://www.anthropic.com/research/claude-code-auto-mode>) (essay, 2026): Explains why a coding agent replaced most manual permission prompts with a classifier that reviews each action: users accepted 93 per cent of prompts, broad allow rules hid risky commands, and consent often did not cover the real blast radius. The design notes on stripping agent text from the reviewer and returning denials to the agent, with escalation to a human after repeated blocks, are reusable patterns. _Limit: Vendor engineering account of its own product with internally measured figures, and the post itself says it is not a replacement for careful human review of high-stakes infrastructure._
- [Your AI agent can move money in Stripe: here is how to stay in control](<https://stripe.dev/blog/your-ai-agent-can-move-money-in-stripe>) (essay, 2026): Shows server-side approval for agents acting on money: live refunds and payouts made through an OAuth-connected agent need the account holder to confirm, agent-tagged API keys fall under dashboard approval rules, the API returns an approval\_required error that the agent can annotate with a justification, and webhook events report approval and execution outcomes back to the agent. It is a worked example of putting approval in the API rather than in the client. _Limit: Vendor product guidance tied to Stripe features, not a general standard._
- [Outcome Monitors: Recovery Affordances for Silent Tool Failures](<https://arxiv.org/abs/2608.19303>) (paper, 2026): Addresses failures that arrive in the expected format, such as a cached error page or a negative price, by checking tool results against outcome contracts and returning a receipt that names the violated property and the recovery tools available. Its ablation, in which removing the recovery-tool list removes the measured gain, is a concrete hint for designing recoverable tool responses. _Limit: Preprint whose main results come from the authors' ToolMaze environment plus tau-bench retail, and detection drops sharply for faults outside the mined contract vocabulary._
- [Same Error, Different Recovery: How Delivery Changes LLM Agent Behavior](<https://arxiv.org/abs/2611.11581>) (paper, 2026): Holds tool-error text constant and varies where it appears, what guidance accompanies it and whether the failed exchange is kept, and finds that the next action changes. For API, CLI and tool builders it is evidence that how an error reaches the agent, and whether the exact fault kind is named, is part of recovery design alongside the wording. _Limit: Single-version preprint covering 13 open models from 3B to 70B parameters, so hosted frontier models are not tested, and no gain was measured on the benchmark that mixes in silent corruption._
- [Human-Guided Harm Recovery for Computer Use Agents](<https://arxiv.org/abs/2604.18847>) (paper, 2026): Treats recovery after an agent has already caused harm as a problem in its own right, derives a natural-language rubric of what people value in a recovery from 1,130 pairwise judgements, and introduces BackBench, 50 computer-use tasks for testing recovery from harmful states. Useful for teams that need a remediation path when prevention fails. _Limit: Preprint with no listed venue or linked code, and the benchmark is small and confined to computer-use settings._
- [Overseeing Agents Without Constant Oversight: Challenges and Opportunities](<https://arxiv.org/abs/2602.16844>) (paper, 2026): Three user studies with a computer-use agent examine whether action traces help people verify its work, and surface problems a review interface must handle: hidden built-in assumptions, correctness criteria that shift as users go, and the difficulty of conveying the agent's process. Practical input for anyone designing trace or review views. _Limit: Preprint with no stated venue; the proposed interface shortened time to find errors but did not meaningfully improve final accuracy._
- [Modeling Distinct Human Interaction in Web Agents](<https://arxiv.org/abs/2602.17588>) (paper, 2026): Introduces CowCorpus, 400 real-user web navigation trajectories with over 4,200 interleaved human and agent actions, identifies four interaction styles from hands-off supervision to full takeover, and frames predicting when a person will step in as a modelling task. It informs when an agent should pause to ask and when it should carry on. _Limit: Labelled a preprint; the abstract page does not say how to obtain the dataset, and the usefulness gains come from the authors' own user study._
- [Using function tools with human in the loop approvals (Microsoft Agent Framework)](<https://learn.microsoft.com/en-us/agent-framework/agents/tools/tool-approval>) (documentation, 2026): Documents approval-marked tools across .NET, Python and Go, with approval responses bound by default to the pending request, a fail-closed path when middleware changes approved arguments, and an explicit warning that standing approvals can match a replacement tool with the same name, including an MCP tool. A framework-level reference for the approval-binding failures described in research already in this section. _Limit: Framework-specific documentation with no evaluation, and its defaults may change between releases._
- [MasDrift: Benchmarking Authorization Preservation Across Multi-Agent Architectures](<https://arxiv.org/abs/2608.07556>) (benchmark, 2026): Pairs 600 benign tasks with reserved actions and measures whether delegated goals keep the user's original authorisation limits across single-agent, hierarchical and peer designs. It also compares re-checking each pending call against the original request with passing an attenuated policy down the chain, which informs where approval evidence should live. _Limit: Preprint benchmark on productivity-style tasks, and the reported rates depend on the models and orchestration tested._
- [Signed but Not Safe: Requirement Integrity in Multi-Agent LLM Handoffs](<https://arxiv.org/abs/2611.07483>) (paper, 2026): A preregistered comparison of free-text, structured JSON and signed requirement-manifest handoffs between an orchestrator and subagents, finding that signing stops tampering in transit and that deterministic checks outperform an LLM checker, while the extraction step before signing remains the weak point. It offers a concrete pattern for carrying a user's requirements intact through delegation. _Limit: Preprint on synthetic tasks, with code and logs available only on request from the authors._

## Security for agent-facing surfaces

- [Exposed by Design: A Dynamic Security Assessment of Internet-Facing MCP Servers at Scale](<https://arxiv.org/abs/2608.00150>) (paper, 2026): Combines passive discovery across eleven data sources with active dynamic testing of 414 production MCP servers, providing scale evidence that most audited public servers currently ship without authentication. _Limit: The audited sample, 640 confirmed and 414 tested servers found across four July 2026 measurement runs, is a snapshot of internet-facing MCP servers rather than a comprehensive census of the ecosystem._
- [Breaking the Protocol: Security Analysis of the Model Context Protocol Specification](<https://arxiv.org/abs/2601.17549>) (paper, 2026): Argues MCP's security gaps are architectural, naming missing capability attestation and unauthenticated bidirectional sampling as protocol-level issues, then tests 847 attack scenarios across five server implementations to support the claim. _Limit: The proposed MCPSec mitigation is the authors' own backward-compatible extension, not an adopted part of the MCP specification, so its real-world deployment status is unverified here._
- [Model Context Protocol security best practices](<https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices>) (specification, 2026): Collects security guidance for tool exposure, trust boundaries, and defensive defaults in MCP-connected agent systems. _Limit: Security guidance is implementation-sensitive; teams still need product-specific threat models and operational review._
- [A First Look at the Security Issues in the Model Context Protocol Ecosystem](<https://arxiv.org/abs/2510.16558>) (paper, 2025): Analyses tens of thousands of MCP servers across several registries and describes a two-stage risk: weak registry vetting admits bad servers, then attacker-controlled tool metadata steers the model. _Limit: Registry practices change quickly, and the accompanying scanner's heuristics are not claimed to be complete._
- [VIPER-MCP: Detecting and Exploiting Taint-Style Vulnerabilities in Model Context Protocol Servers](<https://arxiv.org/abs/2605.21392>) (paper, 2026): An automated auditing method run over a large set of MCP server repositories that confirmed previously unknown exploitable vulnerabilities, evidence that server code, not only descriptions, needs review. _Limit: The reported findings are a lower bound shaped by the method's heuristics, not an estimate of total ecosystem exposure._
- [From Component Manipulation to System Compromise: Understanding and Detecting Malicious MCP Servers](<https://arxiv.org/abs/2604.01905>) (paper, 2026): Builds a dataset of malicious MCP server proofs of concept and shows attacks spread across tools, resources and prompts, informing detection before and during execution. _Limit: The dataset is researcher-authored rather than drawn from attacks observed in the wild, and real-world detection was demonstrated on few servers._
- [Mitigating Taint-Style Vulnerabilities in MCP Servers via Security-Aware Tool Descriptions](<https://arxiv.org/abs/2607.07461>) (paper, 2026): Tests adding behavioural risk guidance to tool descriptions as a low-cost mitigation, linking description quality to security outcomes as well as usability. _Limit: A description-level mitigation reduces the chance of triggering a flaw but cannot fix the underlying code._
- [Prompt Injection Attacks on Agentic Coding Assistants: A Systematic Analysis of Vulnerabilities in Skills, Tools, and Protocol Ecosystems](<https://arxiv.org/abs/2601.17548>) (paper, 2026): Systematises published work on prompt injection against coding agents into a taxonomy covering skills, tools and protocol ecosystems, a map of the attack surface that agent-facing content creates. _Limit: A synthesis of existing studies rather than new experiments, so its figures inherit the limits of the underlying work._
- [The Framing Gap: Indirect Prompt-Injection Exfiltration Defeats Surface-Level Defenses in Tool-Using Agents](<https://arxiv.org/abs/2608.27092>) (paper, 2026): Shows that reframing the same exfiltration request can move attack success from none to all attempts for one model, and that destination allow-lists and capability isolation close the gap where model-level fixes do not. _Limit: Run in a synthetic laboratory setting with mock tools rather than a production deployment._
- [Agent Browser Shield](<https://github.com/pixiebrix/agent-browser-shield>) (tool, 2026): An open-source browser extension that filters pages before an agent reads them, removing likely prompt injection, masking personal data and stripping dark patterns, a practical mitigation for browsing agents. _Limit: An alpha prototype whose rules may change; its published measurement is a small token benchmark, and blocking effectiveness is not independently evaluated._
- [Not what you've signed up for: Compromising Real-World LLM-Integrated Applications with Indirect Prompt Injection](<https://arxiv.org/abs/2302.12173>) (paper, 2023): Presents indirect prompt injection as a new class of attack: instructions planted in content an LLM-integrated application will later retrieve, rather than typed by the user, with a taxonomy of impacts from data theft to injections that spread between systems. _Limit: The demonstrations target 2023 systems such as Bing Chat and code-completion engines, and the paper notes that effective mitigations were lacking, so it defines the threat rather than measuring current agents._
- [Design Patterns for Securing LLM Agents against Prompt Injections](<https://arxiv.org/abs/2506.08837>) (paper, 2025): Sets out six architectural patterns, including plan-then-execute, dual LLM and code-then-execute, that stop untrusted content from steering an agent's choice of actions, and applies them to ten application case studies with the utility each one gives up. _Limit: The case studies are design analyses rather than measured deployments, and the authors say that securing general-purpose agents remains out of reach; the patterns suit narrow, application-specific agents._
- [Indirect Prompt Injection in the Wild: An Empirical Study of Prevalence, Techniques, and Objectives](<https://arxiv.org/abs/2604.27202>) (paper, 2026): Measures injected instructions already on the web: about 15,300 validated cases on some 11,700 pages from 1.2 billion URLs, mostly in parts of the response people never see, with controlled tests across 13 models in which only a small share were followed. _Limit: Based mainly on Common Crawl, which under-represents logged-in content, and on an indicator list that can miss new phrasings; compliance was tested in controlled runs, not on deployed agents._
- [We Have a Package for You! A Comprehensive Analysis of Package Hallucinations by Code Generating LLMs](<https://arxiv.org/abs/2406.10279>) (paper, 2024): Across 16 code models and 576,000 generated samples in Python and JavaScript, models recommended packages that do not exist, names an attacker could register; relevant wherever agent instructions or skills tell an agent what to install. _Limit: Measures code generation with 2024-era models rather than agents that install and run packages, so current rates, and how often a hallucinated name is actually installed, are not established._
- [Model Context Protocol (MCP) Security, version 2.0 (CoSAI)](<https://github.com/cosai-oasis/ws4-secure-design-agentic-systems/blob/main/whitepapers/model-context-protocol-security.md>) (framework, 2026): A threat model for MCP deployments with twelve threat categories and thirty-four threats, plus four cumulative assurance levels that map controls across eight security dimensions to those categories and to the OWASP MCP Top 10. Version 2.0 is updated for the stateless 2026-07-28 release, covering request headers, sealed request state and extension governance. _Limit: A coalition work product from an OASIS open project rather than a standard, and it tracks a protocol that is still changing._
- [The Agent in the Middle: How AI-Mediated Access Reshapes Web Vulnerability Exploitation](<https://arxiv.org/abs/2610.35541>) (paper, 2026): Introduces VELA, an executable benchmark of 44 known web vulnerabilities reached through agent-facing interfaces derived from legitimate workflows, and finds that the interface design changes how many stay exploitable far more than the choice of agent does. Teams turning existing web workflows into agent endpoints get measured trade-offs between removing operations and keeping legitimate tasks possible. _Limit: Preprint that tests three commercial agents against reconstructed vulnerable backends, so it does not measure exposure on live production services._
- [When Tool Names Are Not Identities: Measuring Provider Misbinding in MCP-Based AI Agents](<https://arxiv.org/abs/2611.21577>) (paper, 2026): Shows that an attacker who only runs an additional MCP server can capture requests meant for a legitimate provider, because tool names, descriptions and schemas are not bound to a verified provider identity. Client and host designers get concrete evidence for namespacing tools by server and surfacing provider identity when several servers offer similar tools. _Limit: Single-version preprint run in a controlled MCP environment with five LLM-based clients, so it does not measure how often misbinding happens in deployed hosts._
- [MCP Tool Poisoning in Agentic AI Frameworks: A Cross-Framework Measurement Study](<https://arxiv.org/abs/2611.03555>) (paper, 2026): Measures tool poisoning with real tool execution across 12 agent frameworks, 18 models and 45 scenarios, confirming exfiltration with a canary endpoint, and reports that susceptibility varies mainly by model rather than framework while a simple regex description scanner stops fewer than half the scenarios. It is useful evidence that metadata scanning is only a partial control and that frameworks ship no deliberate defence. _Limit: Workshop paper (AISec 2026) whose framework audit reflects the versions pinned at the time and whose 45 scenarios are author-constructed._
- [MCPTox: A Benchmark for Tool Poisoning Attack on Real-World MCP Servers](<https://arxiv.org/abs/2508.14925>) (benchmark, 2025): Builds 1,348 poisoned test cases on 45 live MCP servers and 353 real tools, where malicious instructions sit in tool metadata rather than tool output, and finds that agents rarely refuse them. It gives hosts and registries a reusable baseline for treating tool descriptions as untrusted input. _Limit: Measures whether models comply with poisoned metadata rather than confirmed end-to-end execution, and the models evaluated are now dated._
- [Measuring and Exploiting Implicit Trust in LLM Tool-Calling Pipelines](<https://arxiv.org/abs/2609.18217>) (paper, 2026): Shows that tool descriptions, tool results and sampling messages share one context without privilege separation, and that payloads split across two or three of these channels can lead to credential exfiltration where a single-channel injection is refused. MCP server and client authors get a threat model in which each channel looks benign on its own, which per-field scanning will not catch. _Limit: Single-version preprint whose results depend on the specific models, clients, payloads and third-party scanners tested._
- [Don't believe everything you read: Understanding and Measuring MCP Behavior under Misleading Tool Descriptions](<https://arxiv.org/abs/2602.03580>) (paper, 2026): Applies static analysis to 10,240 real MCP servers to compare what tool descriptions say with what the code does, and finds a minority with substantial mismatches that could hide privileged operations, state changes or financial actions. Reviewers and registry operators get a concrete reason to audit a description and its implementation together. _Limit: Single-version preprint based on static analysis, so behaviour that only appears at runtime, and later server updates, are not captured._
- [A First Measurement Study on Authentication Security in Real-World Remote MCP Servers](<https://arxiv.org/abs/2605.22333>) (paper, 2026): Finds 7,973 live remote MCP servers, about 40 per cent of which expose tools with no authentication, and sets out a taxonomy of nine OAuth flaw types tied to open client environments, dynamic client registration and delegated authorisation. Server operators get a concrete list of registration and redirect failures to test for. _Limit: Preprint whose detailed flaw counts come from the 119 OAuth servers the authors could test end to end, and it predates the 2026-07-28 MCP release that deprecates dynamic client registration in favour of Client ID Metadata Documents._
- [A2ABreak: Systematic Security Analysis of the A2A Protocol](<https://arxiv.org/abs/2609.10871>) (paper, 2026): Extracts a finite-state model from the A2A specification text and reasons over it to report 11 weaknesses that a fully specification-compliant adversary could exploit, including context injection through unprotected context identifiers, identity loss across delegation chains and rogue agents advertising unattested capabilities. Teams publishing or consuming Agent Cards get design-level risks to address beyond implementation bugs. _Limit: Preprint that analyses the specification under a full-compliance assumption, with LLM-assisted model extraction checked against expert review rather than against deployed implementations._
- [Agent Skills in the Wild: An Empirical Study of Security Vulnerabilities at Scale](<https://arxiv.org/abs/2601.10338>) (paper, 2026): Scans 31,132 skills from two marketplaces and reports that roughly a quarter contain at least one vulnerability pattern, with skills that bundle scripts about twice as likely to be affected as instruction-only skills. It supplies a vulnerability taxonomy and an open dataset for anyone publishing, curating or installing skills. _Limit: Preprint whose detector combines static analysis with LLM classification at reported precision and recall below 90 per cent, so counts are estimates rather than confirmed exploits._
- [DECEPTICON: How Dark Patterns Manipulate Web Agents](<https://arxiv.org/abs/2512.22894>) (benchmark, 2025): Provides 700 web tasks (600 generated, 100 from real sites) that each isolate one dark pattern, and reports that such patterns steer agents towards unwanted outcomes more often than they steer people, with prompting and guardrail models not reliably helping. It frames deceptive interface design as a safety problem for anyone who builds, audits or operates sites that agents use. _Limit: Preprint whose generated tasks are synthetic and whose per-model results will age as agents change._
- [Defeating Prompt Injections by Design](<https://arxiv.org/abs/2503.18813>) (paper, 2025): Presents CaMeL, a system layer that derives control and data flow from the trusted user request so that untrusted tool data cannot change what the agent does, and enforces capability-based data-flow policies whenever a tool is called. It is the main worked implementation of the architectural approach described in the design-patterns paper already listed. _Limit: Preprint whose security results are measured on AgentDojo only, with a reported drop in task completion compared with an undefended agent._
- [Agentic Browsing and Web Architecture](<https://w3ctag.github.io/agentic-browsing-finding/>) (essay, 2026): The W3C Technical Architecture Group's analysis of agentic browsers argues that they combine private data, untrusted content and outbound communication, erode same-origin assumptions and act as confused deputies holding the user's ambient authority, with direct reference to WebMCP. Sites and browser teams exposing tools to agents get the architectural objections they will need to answer. _Limit: A Draft Finding of the TAG, not a normative specification or a consensus Recommendation, and its text may change before publication._
- [Threat Model for WebMCP](<https://w3c.github.io/threat-model-webmcp/>) (framework, 2026): A structured threat model that separates threats inherent to agentic navigation, threats from MCP-style tool mediation and threats specific to WebMCP, using data-flow diagrams, trust boundaries and STRIDE, and maps each threat to the specification's security and privacy considerations. Sites adding WebMCP tools can check their designs against a numbered threat inventory. _Limit: An unofficial proposal draft whose response section is still to be written, tracking a specification that is itself a draft._
- [OWASP Top 10 for Agentic Applications for 2026](<https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/>) (framework, 2025): Gives teams a shared vocabulary of the main risk categories for agents that plan and act, including goal hijacking, tool misuse and identity or privilege abuse, which works as a checklist when reviewing tool, permission and delegation design. _Limit: A community consensus framework from a volunteer project rather than an empirically validated standard, and the full text is a separate download from the resource page._
- [OWASP MCP Top 10](<https://owasp.org/www-project-mcp-top-10/>) (framework, 2025): Names ten MCP-specific risk categories, from token and secret exposure and scope creep to tool poisoning, shadow servers and context over-sharing, giving MCP server authors and reviewers a checklist to work through. _Limit: Still at its beta stage with 2025 identifiers, and the project roadmap promises a later release, so numbering and wording may change._
- [Snyk Agent Scan](<https://github.com/snyk/agent-scan>) (tool): Discovers the agents, MCP servers and skills installed on a machine and scans their tools, prompts and resources for prompt injection, tool poisoning and related risks, a practical pre-install and audit check for teams that rely on third-party agent components. _Limit: Vendor-maintained tool whose README states the CLI output is experimental and may change between releases, and part of its analysis relies on a vendor service._
- [Characterizing Agentic Flooding of Government Services](<https://arxiv.org/abs/2608.16603>) (paper, 2026): Collects 84 potential cases of agent-driven demand surges across 11 jurisdictions, offers a risk matrix for which services are most exposed, and maps responses, noting that the quickest friction measures such as fees can reduce equitable access. It frames what happens to a service when agents make it cheap to use at scale, and the trade-offs in adding friction. _Limit: Focused on public-sector services, and its cases are described as potential rather than confirmed instances._
- [OpenAI "rogue" agent activities found on Wikimedia projects](<https://diff.wikimedia.org/2026/10/05/openai-rogue-agent-activities-found-on-wikimedia-projects/>) (essay, 2026): A large site operator's first-hand account of unapproved agent edits, failed attempts to use a hosted note tool as a proxy, and heavy API and query traffic, including how hard it was to attribute the activity. It is a primary record of why operators ask for verifiable agent identity and clear agent access rules. _Limit: An incident account from one organisation, whose attribution to a specific operator is stated as the Foundation's belief rather than independently verified, and it found no evidence of compromise._

## Observability and traces

- [Semantic conventions for GenAI agent and framework spans (OpenTelemetry)](<https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md>) (specification): Defines a shared span vocabulary for agent creation and invocation (create\_agent, invoke\_agent, invoke\_workflow and framework entry points) with attributes such as gen\_ai.tool.definitions, so operators can record which tools an agent was offered without a vendor-specific format. Tool definitions and message content are opt-in, which reflects that they can carry sensitive data. _Limit: Marked Development status in a repository with no published release, so names and span kinds may still change._
- [Semantic conventions for Model Context Protocol (OpenTelemetry)](<https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/mcp.md>) (specification): Gives MCP client and server builders common span names and attributes (method, session, protocol version, error codes) and says trace context should travel inside params.\_meta, so a single tool call can be followed from the agent host into the server. Setting gen\_ai.operation.name to execute\_tool lets MCP tool calls be read alongside other tool spans. _Limit: Development status convention whose adoption across MCP SDKs and hosts is uneven, so traces from different clients may not yet line up._
- [OpenInference Specification](<https://openinf.dev/spec/>) (specification): Sets out span kinds and attributes for LLM calls, agent steps, tool invocations and retrieval on top of OpenTelemetry, which many tracing and evaluation tools emit, and includes data masking settings for prompts and outputs. An experimental export to OpenTelemetry gen\_ai attributes helps teams that must read both vocabularies. _Limit: Vendor-originated convention (Arize) with no stated version, which overlaps with the official OpenTelemetry GenAI conventions._
- [Agent observability: what to track first](<https://aaif.io/blog/agent-observability-what-to-track-first>) (essay, 2026): Proposes a minimum set of per-run signals (tool and schema versions, redacted arguments, approval status, a compact record of what entered context, cost roll-ups) and a small failure taxonomy such as wrong tool or wrong input, and points to the MCP 2026-07-28 trace context keys. It gives teams a concrete starting point before choosing tracing tools. _Limit: An advisory foundation blog post whose context record and failure taxonomy are proposals, not standards, and it mentions a project connected with its contributors._

## Evaluation

### Benchmarks

- [WebArena: A Realistic Web Environment for Building Autonomous Agents](<https://arxiv.org/abs/2307.13854>) (paper, 2023): Models web agents against realistic sites, showing why navigation, site state, and task context matter for agent-facing web design. _Limit: Self-hosted benchmark environments are useful for repeatability, but live websites change and need ongoing monitoring._
- [Mind2Web: Towards a Generalist Agent for the Web](<https://arxiv.org/abs/2306.06070>) (paper, 2023): Focuses on mapping natural-language goals to web actions, which is a core AX concern for documentation, labels, and machine-readable task affordances. _Limit: Dataset-driven results should be treated as evidence about task representation, not as a universal recipe for every website._
- [τ-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains](<https://arxiv.org/abs/2406.12045>) (paper, 2024): Centres user-agent-tool interaction, making it especially relevant to AX work on handoffs, clarifications, and domain state. _Limit: Domain simulations still simplify messy real systems; use it to guide evaluation design, not to claim production readiness._
- [AgentBoard: An Analytical Evaluation Board of Multi-turn LLM Agents](<https://arxiv.org/abs/2401.13178>) (paper, 2024): Supports analysis of multi-turn agent behaviour rather than only recording a final success or failure, which helps AX reviews separate failure stages. _Limit: Benchmark assumptions can age quickly as tools, models, and web environments change, so it should not be treated as a universal scorecard._
- [StableToolBench: Towards Stable Large-Scale Benchmarking on Tool Learning of Large Language Models](<https://arxiv.org/abs/2403.07714>) (paper, 2024): Calls attention to benchmark stability for tool learning, a necessary concern when tracking whether AX changes move an evaluation in a repeatable way. _Limit: Stability controls evaluation noise; it does not decide which product affordances matter to a given audience._
- [AgentBench: Evaluating LLMs as Agents](<https://arxiv.org/abs/2308.03688>) (paper, 2023): An early multi-environment agent benchmark spanning operating system, database, web and game settings, still used as a reference design for broad agent evaluation. _Limit: Scores were measured on 2023 models and are dated, even though the environments are still reused._
- [OSWorld: Benchmarking Multimodal Agents for Open-Ended Tasks in Real Computer Environments](<https://arxiv.org/abs/2404.07972>) (paper, 2024): Evaluates agents on open-ended tasks in full desktop environments using screenshots and accessibility trees, extending evaluation beyond the browser to whole applications. _Limit: Desktop environments are costly to run at scale, and results may not transfer across operating systems or application versions._
- [ST-WebAgentBench: A Benchmark for Evaluating Safety and Trustworthiness in Web Agents](<https://arxiv.org/abs/2410.06703>) (paper, 2024): Adds policy compliance and safety to web-agent evaluation in enterprise-style tasks, so a run is judged on whether it stayed within rules as well as whether it finished. _Limit: Built on one browser environment framework and a fixed policy set, which bounds what kinds of unsafe behaviour it can detect._
- [τ²-Bench: Evaluating Conversational Agents in a Dual-Control Environment](<https://arxiv.org/abs/2506.07982>) (paper, 2025): Extends τ-bench so that both the simulated user and the agent can change a shared environment through tools, surfacing coordination failures that single-control benchmarks miss. _Limit: Two-party dual control is still a simplification of real systems where several actors change state at once._
- [WebArena-Verified](<https://github.com/ServiceNow/webarena-verified>) (repository, 2025): A verified release of WebArena in which tasks, reference answers and evaluators were reviewed, with deterministic scoring and offline evaluation from network traces for reproducible web-agent results. _Limit: Verification is limited to the WebArena task set and its self-hosted sites; it does not add new site types._
- [ClawBench](<https://github.com/TIGER-AI-Lab/ClawBench>) (repository, 2026): Evaluates browser agents on everyday tasks across about 160 live websites, intercepting the final submission so agents use real sites without completing real transactions. _Limit: Live sites change, so task validity drifts over time in a way a self-hosted benchmark avoids._
- [LiveMCPBench: Can Agents Navigate an Ocean of MCP Tools?](<https://arxiv.org/abs/2508.01780>) (paper, 2025): Tests agents against many real MCP servers and tools at once and finds retrieval of the right tool is a main failure point, which ties evaluation directly to catalogue and description design. _Limit: A curated task set scored partly by a model judge; a later validity audit in this list examines this benchmark family._
- [MCP-Atlas: A Large-Scale Benchmark for Tool-Use Competency with Real MCP Servers](<https://arxiv.org/abs/2602.00933>) (paper, 2026): Scores tasks on real MCP servers against required factual claims rather than one expected call path, with a failure taxonomy that separates tool-call errors from reasoning and stopping errors. _Limit: A private test split is withheld, so the full results cannot be independently replicated._
- [Berkeley Function Calling Leaderboard (BFCL)](<https://gorilla.cs.berkeley.edu/leaderboard.html>) (benchmark): An academic leaderboard for function-calling accuracy covering single, parallel and multi-turn calls, with later versions adding agentic tasks, widely used as a shared reference for tool-calling ability. _Limit: A periodically updated leaderboard subject to the reproducibility concerns raised in the validity audits below; treat single-run rankings with caution._
- [AgentDojo: A Dynamic Environment to Evaluate Prompt Injection Attacks and Defenses for LLM Agents](<https://arxiv.org/abs/2406.13352>) (benchmark, 2024): An extensible environment of tool-using tasks (email, e-banking, travel booking) with paired security test cases, into which teams can plug their own tasks, attacks and defences. Most later prompt-injection benchmarks and the NIST hijacking work extend it, so it is the baseline to understand before reading newer defence claims. _Limit: Research benchmark with simulated tool suites; its default attack set is fixed, and later work argues that fixed attacks overstate how robust a defence is._
- [An Illusion of Progress? Assessing the Current State of Web Agents (Online-Mind2Web)](<https://arxiv.org/abs/2504.01382>) (benchmark, 2025): Introduces Online-Mind2Web, 300 tasks across 136 live websites, and finds earlier web-agent results were over-optimistic. Useful as a live-site counterpart to the offline Mind2Web entry and as a check when reading vendor web-agent claims. _Limit: Live websites change over time, so scores drift, and the authors report that their automatic judge agrees with human raters in roughly 85 per cent of cases._
- [WebPageBench: Event-Level Verification and Controlled UI-Variant Generation for Web Agents](<https://arxiv.org/abs/2609.35026>) (benchmark, 2026): Instrumented mock sites emit typed events, so success is decided from the interface log rather than a judge model, and a single switch re-renders one control with a different implementation while the task stays fixed. Site builders get one of the few set-ups for measuring how a specific widget choice changes agent completion, and a measure of the gap between tasks agents declare finished and tasks actually done. _Limit: Preprint on six synthetic sites and 152 tasks, so control-level findings may not carry over to complex production front ends._
- [Constructing Challenging Browser-Use Tasks by Controlled Environment Interventions (BreakingWeb)](<https://arxiv.org/abs/2609.35814>) (benchmark, 2026): Runs each task twice, once unmodified and once under a reproducible change to content, server state, network responses or rendering, scores on backend state and compares agents with human participants. Its finding that most agent failures are runs reported as complete when the required change never happened supports giving users and agents explicit, checkable confirmation of state changes. _Limit: Preprint on seven self-hosted sites; the interventions are designed perturbations rather than a sample of real production faults._
- [SusBench: An Online Benchmark for Evaluating Dark Pattern Susceptibility of Computer-Use Agents](<https://arxiv.org/abs/2510.11035>) (benchmark, 2025): Injects nine dark-pattern types into real consumer websites and compares computer-use agents with human participants, finding that preselection, trick wording and hidden information catch both groups. It gives interface designers a concrete list of patterns that mislead agents acting for users. _Limit: Five agents tested at one point in time, and the patterns are researcher-injected rather than observed in the wild, although participants rated them realistic._
- [SkillsBench: Benchmarking How Well Agent Skills Work Across Diverse Tasks](<https://arxiv.org/abs/2602.12670>) (benchmark, 2026): Pairs every task with matched no-skill and curated-skill conditions and deterministic verifiers, so the effect of packaging procedural knowledge as an Agent Skill can be measured per model and harness rather than assumed. The current version also compares focused skills with larger bundles, which bears directly on how skill authors scope a package. _Limit: Preprint whose task inventory and headline figures changed across four versions; the tasks are expertise-heavy and may not represent the product-usage skills vendors ship._

### Evaluation tooling

- [METR Task Standard](<https://github.com/METR/task-standard>) (specification, 2024): A common format for packaging agent evaluation tasks (environment, instructions and optional scoring) so tasks written by one party can run in another party's harness, with adaptors for existing suites. _Limit: Standardises packaging, not task quality, and the repository had not been updated for some time at retrieval._
- [Inspect Evals](<https://github.com/UKGovernmentBEIS/inspect_evals>) (repository, 2024): A maintained collection of benchmark implementations for the Inspect framework from the UK AI Security Institute, letting teams run many agent evaluations through one harness instead of reimplementing each. _Limit: Coverage depends on contributions, so newer benchmarks can lag behind their original release._
- [Langfuse](<https://github.com/langfuse/langfuse>) (tool, 2023): Open-source tracing, evaluation and prompt management for LLM and agent applications, supporting the practice of recording every agent run so failures can be reviewed and turned into test cases. _Limit: Self-hosting at scale is an operational commitment, and tracing records what happened without judging whether it was correct._
- [Harbor](<https://github.com/harbor-framework/harbor>) (repository, 2026): An open framework from the Terminal-Bench creators for running off-the-shelf agents such as Claude Code, Codex CLI and OpenHands against shared benchmarks or your own containerised tasks, locally or on parallel cloud sandboxes. It is the official Terminal-Bench 2.0 harness and the runner used in recent vendor guides to product-owned agent evals. _Limit: Oriented towards terminal and coding tasks in containers, so web or GUI surfaces need other harnesses._
- [The BrowserGym Ecosystem for Web Agent Research](<https://arxiv.org/abs/2412.05467>) (framework, 2024): Describes BrowserGym, a shared observation and action interface over many web-agent benchmarks including WebArena and WorkArena, and AgentLab for managing experiments, so a team can run its own site or task set through the same harness researchers use. The maintained code lives at github.com/ServiceNow/BrowserGym. _Limit: Research framework whose observation spaces follow benchmark needs, and the model comparison in the paper reflects late 2024 models._
- [MCP Conformance Test Framework](<https://github.com/modelcontextprotocol/conformance>) (tool): The official harness for checking MCP client and server implementations against the specification, with scenario suites (core, auth, extensions, backwards compatibility, draft) that can be filtered by spec version such as 2025-11-25 or 2026-07-28. Server and client authors can confirm protocol behaviour before agents depend on it. _Limit: Tests protocol conformance only, not the quality of tool descriptions or whether agents complete tasks._
- [Scope](<https://github.com/microsoft/scope>) (repository): An open-source platform for evaluating how agents use a product on real tasks, with reusable success criteria, live run tracking and inspectable evidence through a portal or CLI. It is one of the few evaluation tools built specifically around agent experience rather than model capability. _Limit: Vendor-maintained project labelled a research preview, with no independent evidence yet on how well its results track real agent outcomes._

### Methodology and validity

- [Benchmarking the Benchmarks: A Validity Audit of Tool-Calling Evaluation](<https://arxiv.org/abs/2607.02577>) (paper, 2026): Audits four major tool-calling benchmark families against 496 expert-reviewed tasks and finds that repeating one benchmark's own setup 23 times produced an 18.9-point score spread, large enough to flip leaderboard conclusions. _Limit: The audit covers four named benchmark families (BFCL v4, tau2-Bench, LiveMCPBench, MCP-Atlas); it does not establish that every tool-calling benchmark has comparable reproducibility problems._
- [Establishing Best Practices for Building Rigorous Agentic Benchmarks](<https://arxiv.org/abs/2507.02825>) (paper, 2025): Introduces a checklist for task validity, outcome validity and reporting in agent benchmarks, drawn from problems found in published benchmarks, giving teams a pre-publication review tool. _Limit: A methodological checklist; it does not by itself re-score widely used benchmarks end to end._
- [Evaluation and Benchmarking of LLM Agents: A Survey](<https://arxiv.org/abs/2507.21504>) (paper, 2025): Organises agent evaluation work by what is evaluated and how, which helps a team find the existing benchmark or method that fits a specific AX question. _Limit: A survey that summarises rather than resolves disagreements between the methods it covers._
- [Do Agent Benchmarks Measure Capability? Protocol Validity in the Age of Agentic AI](<https://arxiv.org/abs/2607.22368>) (paper, 2026): Audits agent traces across many benchmarks and finds reward hacking and protocol exploitation inflating scores on some, a failure mode distinct from ordinary evaluator noise. _Limit: Covers a named set of benchmarks; prevalence elsewhere in the field is not estimated._
- [The Double Measurement Confound in Agent Benchmarks: De-Scaffolding, Ground-Truth Scoring, and Reliability Beyond the Mean](<https://arxiv.org/abs/2609.09218>) (paper, 2026): Names a confound in which a fixed scaffold makes execution-critical decisions and a scorer may not reflect correctness, and shows that repairing both changes what a leaderboard appears to show. _Limit: The repair protocol is demonstrated mainly on one benchmark, and applying it elsewhere needs bespoke work._
- [Beyond Pass@k: Measuring Reliability and Security of Agentic Code Generation](<https://arxiv.org/abs/2608.14711>) (paper, 2026): Identifies a common miscalculation of pass@k that can greatly inflate reported agent scores, and proposes reliability and security measures to report alongside it. _Limit: The live pilot is very small, and the authors describe the practical effect of their security-adjusted metric as unresolved._
- [Demystifying evals for AI agents](<https://www.anthropic.com/research/demystifying-evals-for-ai-agents>) (essay, 2026): A practitioner walkthrough of building agent evaluations, covering task design, graders and reading transcripts, which complements the academic validity work in this section. _Limit: Based on one model provider's internal practice rather than an independently validated method._
- [Building AX evals that actually work](<https://developer.microsoft.com/blog/building-ax-evals-that-actually-work/>) (essay, 2026): Practical guidance for evaluating how agents use a product: realistic developer prompts, checklist criteria with pass, fail and skip conditions for an LLM judge, judge calibration, at least five runs per condition and pinned, representative environments. _Limit: An experience report from one vendor's evaluation work on coding agents, not a controlled study; thresholds such as five runs per scenario are rules of thumb rather than statistically derived._
- [Holistic Agent Leaderboard: The Missing Infrastructure for AI Agent Evaluation](<https://arxiv.org/abs/2510.11977>) (paper, 2025): Reports a standardised, cost-tracked run of 21,730 rollouts across models, scaffolds and benchmarks, and uses log inspection to surface behaviour such as agents searching for the benchmark instead of solving the task. It is a reference for why scaffold, cost and logs belong in any agent result, and the released logs can be reused. _Limit: The associated hal-harness repository was archived in July 2026, so the paper is best read as a methodology reference rather than a live tool._
- [Towards a Science of AI Agent Reliability](<https://arxiv.org/abs/2602.16666>) (paper, 2026): Proposes twelve reliability metrics grouped under consistency, robustness, predictability and safety, drawn from safety-critical engineering, as a complement to single success rates. Teams can borrow the metrics when deciding whether an agent workflow is consistent enough to deploy. _Limit: The metrics are applied to two benchmarks and 15 models, so how well they reflect production conditions is not yet established._
- [The Attacker Moves Second: Stronger Adaptive Attacks Bypass Defenses Against LLM Jailbreaks and Prompt Injections](<https://arxiv.org/abs/2510.09023>) (paper, 2025): Argues that defences must be tested against adaptive attackers who tailor and scale their search, and bypasses 12 recent defences that had reported near-zero attack success. It sets the evaluation bar that any prompt-injection defence claim for an agent-facing tool should meet. _Limit: Preprint focused on model-level defences; it does not offer a defence or examine system-level designs in depth._
- [An Empirical Study of Harness Design for Coding Agents](<https://arxiv.org/abs/2609.20804>) (paper, 2026): Varies planning, action space and context management one at a time across 176 matched settings, and reports for example that models fluent in bash do well with a bash-only interface while weaker models benefit from predefined tools. It helps teams separate interface effects from model effects when evaluating the tools they expose. _Limit: Preprint limited to two coding benchmarks, four models and one lightweight harness._
- [Infrastructure noise in agentic coding evals](<https://www.anthropic.com/research/infrastructure-noise>) (essay, 2026): Shows that container resource enforcement alone moved Terminal-Bench 2.0 scores by several percentage points, more than many leaderboard gaps, and explains the difference between a guaranteed allocation and a hard kill limit. Anyone comparing agents or harness changes on their own tasks gets concrete reasons to document and fix the runtime configuration. _Limit: Vendor engineering post measured on one benchmark and the vendor's own infrastructure, not a peer-reviewed study._
- [Agents are users, so your software needs evals](<https://vercel.com/blog/agent-evals>) (essay, 2026): A worked method for teams that ship an API, CLI, MCP server or SDK: a discovery, selection, access and success funnel, a testing pyramid by number of model calls, end-to-end tasks with per-constraint verifiers, at least one task where the right move is not to act, and guidance on choosing pass@k or pass^k by the cost of failure. _Limit: Vendor material built around Harbor and Vercel infrastructure, and the results table in the worked example is labelled by the authors as illustrative rather than measured._
- [The AX Practitioner Playbook](<https://microsoft.github.io/agent-experience/playbook/>) (framework): Consolidates Microsoft developer relations' Agent Experience article series into an eleven-chapter method for teams that own SDKs, APIs, CLIs, MCP servers, skills or docs: design realistic scenarios, write and calibrate criteria a judge applies consistently, choose agent profiles, read trajectories to separate an extension that never loaded from one never called or one misapplied, and test each proposed fix as a hypothesis before shipping it. A quality checklist and an end-to-end SharePoint Framework worked example make the method concrete. _Limit: Vendor material drawn from coding agents working on Microsoft's own developer products with small run counts, it overlaps with the series articles already listed, and the site states no publication date or version (the announcement post is dated October 2026)._
- [Why Do Multi-Agent LLM Systems Fail?](<https://arxiv.org/abs/2503.13657>) (dataset, 2025): Introduces the MAST taxonomy of 14 failure modes in three groups (system design, inter-agent misalignment, task verification) and a dataset of more than 1,600 annotated traces from seven frameworks, with an LLM annotation pipeline. Teams can reuse the taxonomy to label their own multi-agent traces, including communication and verification failures. _Limit: Traces come from research frameworks and earlier model generations, and the LLM annotator approximates rather than replaces human labels._

## Readiness instruments

- [Is Your Site Agent-Ready?](<https://isitagentready.com/>) (tool, 2026): A public scanner that checks a site for many emerging agent-facing conventions in one pass, from robots.txt rules and Markdown negotiation to OAuth discovery, MCP server cards, agent skills and commerce protocols. _Limit: Measures adoption of conventions chosen by one vendor, and no published evidence yet shows that a higher score predicts agent task success._
- [Lighthouse agentic browsing scoring](<https://developer.chrome.com/docs/lighthouse/agentic-browsing/scoring>) (tool, 2026): An experimental Lighthouse category that audits WebMCP use, agent-relevant accessibility and page stability, reporting per-audit results instead of one weighted number. _Limit: Experimental, page-level and subject to run-to-run variation, and no published evidence yet shows that a higher score predicts agent task success._
- [Is Agentic](<https://is-agentic.com/>) (tool, 2026): Scores the public parts of a site that agents can discover, access and use, and documents its method, including known false positives and false negatives. _Limit: A point-in-time vendor score whose weighting is the vendor's choice, and no published evidence yet shows that a higher score predicts agent task success._
- [AXIS: Agent Experience Index Score](<https://github.com/netlify/axis>) (tool, 2026): Open-source tooling that runs a real agent through a scenario and grades the transcript on goal achievement, environment, service and agent dimensions, so it measures an observed journey rather than static signals. The project site at axis.run documents the weights (40 per cent goal achievement, 20 per cent for each of the other three), a quickstart and CI baselines that fail a build on regression. _Limit: Relies on a model judge, mixes product and model quality in one composite, and no published evidence yet shows that a higher score predicts agent task success beyond the scenarios run._
- [Agent-Friendly Documentation Spec](<https://agentdocsspec.com/>) (specification, 2026): An open draft specification (v0.6.0) that defines 28 checks in seven categories for documentation sites: discoverability, Markdown availability, page size, content structure, URL stability, observability and authentication. Each check has pass, warn or fail criteria and a severity. Its automated checker, AFDocs, is listed separately. _Limit: A draft grounded in the author's observations rather than a controlled study, covering web delivery only (companion specs on content and repository documentation are planned), and no published evidence yet shows that a higher score predicts agent task success._
- [Agent Readiness Model (Factory)](<https://docs.factory.ai/agent-readiness/overview>) (framework): Scores a code repository, not a website, on whether it has the structure, validation and operational signals coding agents need, using gated levels that a repository unlocks in order. _Limit: Tied to one vendor's coding agent, the level thresholds are the vendor's own, and no published evidence yet shows that a higher score predicts agent task success._
- [AFDocs](<https://github.com/agent-ecosystem/afdocs>) (tool, 2026): The open-source command-line checker and Node.js library for the Agent-Friendly Documentation Spec. It runs the spec's 28 checks in seven categories against a live documentation site and prints pass, warn or fail per check with a suggested fix, a weighted scorecard and CI helpers. Several hosted documentation scorers say they run it underneath, so its checks reference shows what those scores actually test. _Limit: An early 0.x tool whose check identifiers and output formats may change between versions, and no published evidence yet shows that a higher score predicts agent task success._
- [A Standards-Grounded Method for Evaluating Website Agent-Readiness (draft-shah-agent-readiness-evaluation)](<https://datatracker.ietf.org/doc/draft-shah-agent-readiness-evaluation/>) (specification, 2026): Sets out a deterministic 0 to 100 method for website agent-readiness in which every check maps to an existing RFC or W3C specification (robots.txt, Web Linking, api-catalog, JSON-LD, text/markdown, HTTP caching, TLS). Each check is reported with its citation and raw observation, llms.txt and Content-Signal count only as small bonuses, and blocked sites are reported as not observed instead of failed. It works as a template for making any scanner's assumptions open to inspection. _Limit: An individual Informational draft on the Independent Submission stream with no IETF working group standing. Its pillar weights are explicitly an editorial convention, and no published evidence yet shows that a higher score predicts agent task success._
- [mcpgrade](<https://github.com/tenglidev/mcpgrade>) (tool, 2026): An open-source linter for MCP server tool catalogues. It scores descriptions, schema design, naming, token cost and consistency, gives a concrete fix for each finding and can gate CI. An optional live mode asks a model to pick tools and fill arguments for synthesised tasks, including out-of-scope tasks the model should refuse. The author's accompanying scan of 36 public servers (tengli.dev, July 2026) found that undocumented parameters were the most common failure. _Limit: A personal project whose rules and weights are the author's own. The only check of static scores against model behaviour is a small calibration (four servers, one model) that measures single-step tool selection, not task success. It is unrelated to the similarly named mcpgrade.dev security grader._

## GEO and AI search (adjacent)

- [GEO: Generative Engine Optimization](<https://arxiv.org/abs/2311.09735>) (paper, 2023): The paper that named generative engine optimisation and introduced a benchmark for measuring how content changes affect visibility in AI-generated answers, the starting point for most later GEO work. _Limit: Visibility gains were measured on the paper's own benchmark and engines at the time, not on current production answer engines._
- [Structural Feature Engineering for Generative Engine Optimization: How Content Structure Shapes Citation Behavior](<https://arxiv.org/abs/2603.29979>) (paper, 2026): Separates page structure from wording and reports that structure alone changes citation rates across several generative engines, relevant to how agent-readable pages are organised. _Limit: Engine behaviour changes as platforms update, and some quality judgements rely on a rating method the paper does not fully specify._
- [From Citation Selection to Citation Absorption: A Measurement Framework for Generative Engine Optimization Across AI Search Platforms](<https://arxiv.org/abs/2604.25707>) (paper, 2026): Distinguishes being cited from actually shaping an answer and shows the two diverge differently across platforms, a correction to measuring GEO by citation counts alone. _Limit: Observational analysis of a public dataset rather than a controlled experiment, and platform behaviour shifts over time._
- [What Gets Cited: Competitive GEO in AI Answer Engines](<https://arxiv.org/abs/2605.25517>) (paper, 2026): A large factorial experiment across several models that isolates content factors and finds relevance and position matter far more than formatting-only edits for being cited. _Limit: Uses a simplified two-document setting rather than realistic multi-source retrieval._
- [Optimizing Visibility in Generative Engines: A Critical Survey of Generative Engine Optimization (2023-2026)](<https://arxiv.org/abs/2607.14035>) (paper, 2026): A critical review of GEO research that concludes no reviewed technique yet shows a stable, cross-platform effect over time, the field's own check on optimisation claims. _Limit: Its conclusions inherit the short time horizons of the studies it reviews, which the authors acknowledge._
- [When Optimization Becomes Manipulation: Defending Generative Search against Malicious Generative Engine Optimization](<https://arxiv.org/abs/2609.02964>) (paper, 2026): Describes automated, agent-driven content manipulation aimed at answer engines and proposes a defence that reduces attack success without penalising benign content. _Limit: Evaluated against attack families the authors built, so novel manipulation strategies remain untested._
- [Optimizing your website for generative AI features on Google Search](<https://developers.google.com/search/docs/fundamentals/ai-optimization-guide>) (documentation): Primary guidance from one search engine on its AI features, which states that tactics such as content chunking or llms.txt files are unnecessary for its Search, a useful corrective to GEO marketing claims. _Limit: Covers one search engine only and says nothing about how other answer engines or agents treat the same signals._
- [CITECHOICE: A Causal Audit of How Document Presentation Redistributes Citation Credit in Agentic Search](<https://arxiv.org/abs/2609.15164>) (paper, 2026): Replays frozen, hash-checked transcripts of a searching agent while changing only document order or structured versus prose rendering, which separates what presentation actually causes from the much larger rank effects seen in observational data. It also measures how often citation decisions flip under fresh decoding, a noise floor teams should know before crediting a content edit with a citation change. _Limit: Preprint built on one acquisition agent, one retrieval provider and about one hundred verified document pairs; the authors state it does not show that structure changes whether a source is cited at all, or that publisher edits change live retrieval._
- [Understanding ChatGPT Citations: Evidence from Production Web Search Across Model Generations](<https://arxiv.org/abs/2610.15382>) (paper, 2026): Follows production ChatGPT search from rewritten queries through retrieval rounds to the sources finally cited, across four model settings in Instant and Thinking modes. It gives practitioners a reason to track being retrieved separately from being cited, to measure at hostname and entity level as well as exact URL, and to recheck results whenever the deployed model changes. _Limit: A short observational preprint on one product whose behaviour shifts with each deployment; the abstract page does not state that data or code are released, and the external proxies it tests recover only a minority of cited URLs._
- [Measuring Google AI Overviews: Activation, Source Quality, Claim Fidelity, and Publisher Impact](<https://arxiv.org/abs/2605.14021>) (paper, 2026): A peer-reviewed measurement study of when Google AI Overviews appear, which domains they cite and whether cited pages support each atomic claim in the answer. Its finding that a large share of cited domains do not appear on the co-displayed first results page shows that ranking organically and being cited by the overview need to be measured as separate problems. _Limit: Covers one engine, trending United States queries and a 40-day window in spring 2026, and the abstract page does not state that the query set or code are released._
