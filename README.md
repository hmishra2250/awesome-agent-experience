# Awesome Agent Experience (AX)

A curated public library for **agent experience**: the design of product, documentation, API, tool, protocol, evaluation, and recovery surfaces so AI agents can discover, understand, safely use, and repair workflows on behalf of people.

This list is intentionally narrow. It is about **software agent experience**: web agents, tool-using LLMs, MCP/API surfaces, evaluation harnesses, retrieval, human control, and operational recovery. It is not about call-center agent experience, real-estate agents, talent agents, or generic customer-experience copy.

The field framing includes the independent opinion essay [Introducing AX: Why Agent Experience Matters](https://biilmann.blog/articles/introducing-ax/). This repository is maintained by the same author as the [Agent Experience Readiness Rubric](https://agentexperience.tech/insights/agent-readiness-rubric/); that link is provided as same-maintainer context, not as neutral endorsement.

## Scope criteria

A source belongs here when it helps answer at least one of these questions:

- Can an agent discover the right surface, instruction, tool, or document?
- Can an agent select and call tools with clear schemas, examples, and error boundaries?
- Can humans inspect, approve, interrupt, or recover the agent's work?
- Can teams evaluate agent workflows in a reproducible way?
- Can the same surface stay useful as models, tools, and protocols change?

A source does **not** belong here if it is only a launch announcement, generic AI-agent marketing, SEO filler, private experiment, paid placement, or unlicensed copy of someone else's work.

## Start here

- **If you are defining the field:** read the AX framing essay, then compare it with the practical scope criteria in this repo.
- **If you build tools or APIs:** read MCP tools/resources, OpenAPI, JSON Schema, Toolformer, ReAct, ToolLLM, and Anthropic's tool-writing guide, then the tool-description and tool-selection papers.
- **If you build websites or docs for agents:** read llms.txt, ARD v0.91, WebMCP, AGENTS.md, Markdown for Agents, WebArena, Mind2Web, WAI-ARIA, and WCAG with the limitations in mind.
- **If you run experiments:** read τ-bench, AgentBoard, StableToolBench, Designing Agent-Ready Websites, Benchmarking the Benchmarks, and the limitations before claiming readiness.
- **If you own production risk:** start with MCP security and authorization, the agent identity and authorization section (WorkOS FGA, Auth.md, Consent Integrity, Loopjacking), then design explicit approval and recovery paths.

## Agent experience framing

- [Introducing AX: Why Agent Experience Matters](<https://biilmann.blog/articles/introducing-ax/>) — A public opinion frame for AX as a discipline, useful because it states that agent-facing surfaces deserve product-design attention rather than being treated as incidental automation glue. _Limit: This is a framing essay, not a benchmark or standard; cite it as an opinionated field definition, not as proof of outcomes or ownership._

## Agent tool use and planning

- [ReAct: Synergizing Reasoning and Acting in Language Models](<https://arxiv.org/abs/2210.03629>) — Connects reasoning traces with actions, making it a useful starting point for interfaces that expose why an agent chose a tool and what happened next. _Limit: Primarily a prompting and evaluation paper; it does not by itself specify production observability, permissioning, or recovery contracts._
- [Toolformer: Language Models Can Teach Themselves to Use Tools](<https://arxiv.org/abs/2302.04761>) — Frames tool use as something models can learn from demonstrations, which is central to designing tool descriptions and examples that agents can actually use. _Limit: Uses a bounded set of tools and self-supervised data generation; production tool ecosystems add security, latency, and changing-schema problems._
- [ToolLLM: Facilitating Large Language Models to Master 16000+ Real-world APIs](<https://arxiv.org/abs/2307.16789>) — Shows how large tool corpora and tool-use data shape agent behavior, supporting AX work on catalog structure and retrieval-friendly tool metadata. _Limit: Large catalogs can hide quality variance; practical AX also needs clear scope boundaries, deprecation signals, and safe failure modes._
- [Writing effective tools for agents — with agents](<https://www.anthropic.com/engineering/writing-tools-for-agents>) — Lays out a concrete build-evaluate-refine loop for tool design, realistic multi-step evaluation tasks followed by using an agent to analyse transcripts, with five practical principles and a quantified example cutting one tool's response from 206 to 72 tokens. _Limit: All worked examples are Anthropic's own internal Slack and Asana tools; it does not address cross-vendor tool catalogues, discovery, or MCP registries._
- [The Devil Is in the Interface: Evaluating How Tool Architecture Shapes Coding Agent Behavior](<https://arxiv.org/abs/2608.11386>) — Runs 11,700 trajectories across three model actors and six tool architectures, from a bare bash tool to structured interfaces, showing that how tools are organised and exposed changes agent behaviour even when raw capability is held constant. _Limit: Findings come from repository-level issue-fixing tasks with specific model actors; whether the same architecture ranking holds for other task domains is not tested here._
- [DOCSCHISEL: Adaptive Tool Documentation Optimization Framework for LLM Agents](<https://arxiv.org/abs/2608.10037>) — Shows that no single fixed tool-documentation format generalises across tasks, models, and agent designs, then proposes a framework that analyses failed execution traces to iteratively add, remove, or refine documentation fields per tool. _Limit: The proposed framework requires access to an agent's failed execution traces to iterate on, which is not available to every team publishing a tool or API._
- [From Docs to Descriptions: Smell-Aware Evaluation of MCP Server Descriptions](<https://arxiv.org/abs/2602.18914>) — Defines 18 documentation 'smell' categories across four quality dimensions, applies them to 10,831 real MCP servers, and runs a mutation study showing that injecting or fixing smells measurably changes which tool an agent selects. _Limit: The mutation study shows description smells move selection outcomes in the tested setup; it does not rank which individual smells matter most across every model._
- [More Skills, Worse Agents? Skill Shadowing Degrades Performance When Expanding Skill Libraries](<https://arxiv.org/abs/2605.24050>) — Decomposes agent performance degradation from growing tool or skill libraries into a wrong-selection component, named skill shadowing, versus a context-overhead component, and estimates both empirically on a library scaling to 202 skills. _Limit: Findings come from one scaling experiment up to 202 skills; whether the same shadowing-versus-overhead split holds at far larger catalogue sizes is not established._
- [ToolChoiceConfusion: Causal Minimal Tool Filtering for Reliable LLM Agents](<https://arxiv.org/abs/2606.06284>) — Argues topical relevance alone is not enough to decide which tools to expose at each step, and tests a precondition-aware filtering method across 2,448 task-method-model runs, cutting token cost roughly 90 percent without hurting task success. _Limit: Evaluated with 100 tools and four backend models in a controlled multi-step task set; real production catalogues and model mixes may behave differently._

## Discovery and agent-readable web

- [WebArena: A Realistic Web Environment for Building Autonomous Agents](<https://arxiv.org/abs/2307.13854>) — Models web agents against realistic sites, showing why navigation, site state, and task context matter for agent-facing web design. _Limit: Self-hosted benchmark environments are useful for repeatability, but live websites change and need ongoing monitoring._
- [Mind2Web: Towards a Generalist Agent for the Web](<https://arxiv.org/abs/2306.06070>) — Focuses on mapping natural-language goals to web actions, which is a core AX concern for documentation, labels, and machine-readable task affordances. _Limit: Dataset-driven results should be treated as evidence about task representation, not as a universal recipe for every website._
- [llms.txt: The /llms.txt file, v2](<https://llmstxt.org/>) — Documents a proposed Markdown-based website discovery convention for helping language models and agents find the most relevant human-authored pages. _Limit: It is a proposal rather than an enforced web standard, so teams should treat it as one discoverability surface among several._
- [Agentic Resource Discovery (ARD) specification, v0.91](<https://agenticresourcediscovery.org/spec/>) — The dated, multi-vendor v0.91 proposal (authored across Google, Microsoft, and Hugging Face) distinguishes a plain catalog entry from a stricter ARD entry built for search-based discovery beyond an LLM's context window. _Limit: Status is explicitly Proposal, not final; it delegates authentication and distribution to the underlying agent or tool protocol rather than defining them itself._
- [WebMCP (Draft Community Group Report)](<https://webmachinelearning.github.io/webmcp/>) — Defines the document.modelContext API for exposing client-side tools to agents and gives a detailed public security taxonomy for agent-callable web pages, covering tool poisoning, output injection, and over-parameterised data leakage. _Limit: Published by a W3C Community Group; the spec itself states it is not a W3C Standard nor on the Standards Track, so treat it as an active proposal, not settled browser behaviour._
- [AGENTS.md](<https://agents.md/>) — A deliberately unstructured Markdown convention for repository-level agent instructions, now governed by the Agentic AI Foundation under the Linux Foundation rather than a single vendor, with adoption checkable via a linked GitHub code search. _Limit: Has no required fields or schema, so file quality varies widely between projects; the specification itself does not address how a poorly written file affects agent task success._
- [Markdown for Agents](<https://developers.cloudflare.com/fundamentals/reference/markdown-for-agents/>) — Documents an HTTP content-negotiation pattern, an Accept: text/markdown request, for serving agents an edge-converted Markdown page, with a precise, checkable policy on which headers are preserved, recalculated, or dropped. _Limit: The feature is limited to paid Cloudflare plans and to HTML-to-Markdown conversion of responses under 2 MB; it does not establish whether AI crawlers actually send the Accept header in practice._

## Evaluation and benchmarks

- [τ-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains](<https://arxiv.org/abs/2406.12045>) — Centers user-agent-tool interaction, making it especially relevant to AX work on handoffs, clarifications, and domain state. _Limit: Domain simulations still simplify messy real systems; use it to guide evaluation design, not to claim production readiness._
- [AgentBoard: An Analytical Evaluation Board of Multi-turn LLM Agents](<https://arxiv.org/abs/2401.13178>) — Supports analysis of multi-turn agent behavior rather than only recording a final success or failure, which helps AX reviews separate failure stages. _Limit: Benchmark assumptions can age quickly as tools, models, and web environments change, so it should not be treated as a universal scorecard._
- [StableToolBench: Towards Stable Large-Scale Benchmarking on Tool Learning of Large Language Models](<https://arxiv.org/abs/2403.07714>) — Calls attention to benchmark stability for tool learning, a necessary concern when tracking whether AX changes move an evaluation in a repeatable way. _Limit: Stability controls evaluation noise; it does not decide which product affordances matter to a given audience._
- [Designing Agent-Ready Websites for AI Web Agents](<https://arxiv.org/abs/2607.12056>) — Runs a controlled before/after e-commerce experiment across three browser-agent models and 300 task runs, finding an otherwise-identical agent-ready site raised strict task success from about 49 percent to about 89 percent. _Limit: The experiment uses one e-commerce site design and three specific browser-agent models; results may not transfer directly to other site types or to agent models released after the study._
- [Benchmarking the Benchmarks: A Validity Audit of Tool-Calling Evaluation](<https://arxiv.org/abs/2607.02577>) — Audits four major tool-calling benchmark families against 496 expert-reviewed tasks and finds that repeating one benchmark's own setup 23 times produced an 18.9-point score spread, large enough to flip leaderboard conclusions. _Limit: The audit covers four named benchmark families (BFCL v4, tau2-Bench, LiveMCPBench, MCP-Atlas); it does not establish that every tool-calling benchmark has comparable reproducibility problems._

## Protocols and machine-readable surfaces

- [Model Context Protocol architecture overview](<https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture>) — Gives the MCP mental model for hosts, clients, servers, tools, resources, prompts, and discovery, which is useful when designing agent-facing surfaces. _Limit: It is high-level documentation; implementation work still needs the specific dated specification pages and SDK behavior._
- [Model Context Protocol tools specification](<https://modelcontextprotocol.io/specification/2026-07-28/server/tools>) — Defines how MCP servers expose callable tools, including metadata and schemas that agents and clients use to understand possible actions. _Limit: The spec defines the contract shape; product teams still need to write clear names, descriptions, input schemas, examples, and error responses._
- [Model Context Protocol resources specification](<https://modelcontextprotocol.io/specification/2026-07-28/server/resources>) — Defines the resource layer for exposing context such as files, data, and app-specific information to agent clients. _Limit: It does not choose the semantic taxonomy or freshness policy for a particular product's resources._
- [OpenAPI Specification v3.2.0](<https://spec.openapis.org/oas/v3.2.0.html>) — OpenAPI remains a practical bridge between HTTP APIs, developer docs, and agent-readable operation metadata. _Limit: An OpenAPI file can be syntactically valid while still being poor AX if operation names, examples, errors, and auth flows are unclear._
- [JSON Schema Draft 2020-12](<https://json-schema.org/draft/2020-12>) — JSON Schema is a foundation for tool input contracts, structured outputs, API validation, and agent-readable constraints. _Limit: Schemas need examples, semantics, and versioning discipline; validation alone does not explain intent._
- [The MCP Registry](<https://modelcontextprotocol.io/registry/about>) — Explains the official MCP Registry's architecture as metadata-only infrastructure meant for downstream aggregators rather than a store end-user MCP clients query directly, and documents its namespace-based publisher trust model. _Limit: The registry was in preview status at retrieval time, so behaviour may change before general availability, and it explicitly delegates security scanning to underlying package registries instead of performing its own._
- [Exposed by Design: A Dynamic Security Assessment of Internet-Facing MCP Servers at Scale](<https://arxiv.org/abs/2608.00150>) — Combines passive discovery across eleven data sources with active dynamic testing of 414 production MCP servers, providing scale evidence that most audited public servers currently ship without authentication. _Limit: The audited sample, 640 confirmed and 414 tested servers found across four July 2026 measurement runs, is a snapshot of internet-facing MCP servers rather than a comprehensive census of the ecosystem._
- [Breaking the Protocol: Security Analysis of the Model Context Protocol Specification](<https://arxiv.org/abs/2601.17549>) — Argues MCP's security gaps are architectural, naming missing capability attestation and unauthenticated bidirectional sampling as protocol-level issues, then tests 847 attack scenarios across five server implementations to support the claim. _Limit: The proposed MCPSec mitigation is the authors' own backward-compatible extension, not an adopted part of the MCP specification, so its real-world deployment status is unverified here._

## Agent identity and authorization

- [WorkOS FGA: The authorization layer for AI agents](<https://workos.com/blog/agents-need-authorization-not-just-authentication>) — Distinguishes on-behalf-of agents, which need scope attenuation under the acting user's own permissions, from autonomous agents, which need fine-grained scope rather than broad client-credential grants, using worked confused-deputy and shared-context scenarios. _Limit: A vendor architecture piece promoting WorkOS Fine-Grained Authorization; its one supporting statistic, an average 47-day stale-credential lifetime, is uncited in the retrieved text._
- [Agent Registration with Auth.md](<https://workos.com/blog/agent-registration-with-auth-md>) — Proposes an open protocol, a discoverable /auth.md document plus three HTTP endpoints extending RFC 9728 Protected Resource Metadata, for an agent to register a new user on their behalf, a gap OAuth's browser-consent flow does not cover. _Limit: Adoption outside WorkOS's own ecosystem is unstated in the source; as an author-organisation announcement, independent implementation evidence is still needed._
- [What You Approve Is What Executes: Consent Integrity for Black-Box LLM Agents](<https://arxiv.org/abs/2606.02668>) — Names the missing 'Consent Integrity' property for agent approval dialogs, the action shown must be rendered by a trusted mediator from the real action rather than the agent's own narration, and tests a prototype against 1,330 trusted-tool abuse techniques. _Limit: The prototype analyser, renderer, and execution binder is a research system tested on the GTFOBins and tldr corpora, not a deployed product feature available to adopt directly._
- [Loopjacking: Hijacking Human-in-the-Loop Approval](<https://arxiv.org/abs/2609.21081>) — Defines Loopjacking as any case where the operation a human approves does not match what a system actually executes, and reproduces both representation-based and post-approval state-substitution variants in named, released agent products. _Limit: The paper names a purposive set of tested products rather than a random or exhaustive sample, so prevalence across the wider agent-product ecosystem is not established._

## Human control, accessibility, and recovery

- [Model Context Protocol security best practices](<https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices>) — Collects security guidance for tool exposure, trust boundaries, and defensive defaults in MCP-connected agent systems. _Limit: Security guidance is implementation-sensitive; teams still need product-specific threat models and operational review._
- [Understanding Authorization in MCP](<https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/authorization>) — Explains consent, scopes, and OAuth-oriented authorization patterns that matter when agents act through user-authorized tools. _Limit: Remote and local transports differ, so the same authorization pattern will not fit every deployment._
- [Accessible Rich Internet Applications (WAI-ARIA) 1.2](<https://www.w3.org/TR/wai-aria-1.2/>) — Defines roles, states, and properties for accessible web interfaces; AX uses this as relevant machine-readable UI semantics, not as a shortcut to agent success. _Limit: Correct ARIA use is necessary for accessibility in many interfaces, but it does not guarantee that an agent can complete a workflow._
- [Web Content Accessibility Guidelines (WCAG) 2.2](<https://www.w3.org/TR/WCAG22/>) — Sets human accessibility requirements for perceivable, operable, understandable, and robust web content; AX relevance is an inference because agent tooling often benefits from the same explicit structure. _Limit: WCAG conformance is not equivalent to agent readiness and should not be cited as evidence that agents will operate a product reliably._
- [Oversight Has a Capacity: Calibrating Agent Guards to a Subjective, Fatiguing Human](<https://arxiv.org/abs/2606.08919>) — Measures inter-reviewer agreement on a hand-labelled set of 125 adversarially-weighted agent actions and models the human reviewer as fatiguing under escalation load, finding that more oversight can reduce realised safety past a point. _Limit: The reviewer-fatigue model and the 125-action labelled set are the authors' own construction; whether the same capacity limit holds for other review populations or action types is not tested._
